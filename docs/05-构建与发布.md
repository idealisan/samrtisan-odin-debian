## 一、编译专用镜像与开发容器

本地构建一律在容器里跑，不在 macOS 宿主上跑。宿主缺 debootstrap 与 e2fsprogs 的
一堆工具，更关键的是构建需要 root 与 chroot —— 在容器里做是可丢弃的，在宿主上做
不可逆。

镜像由仓库根的 `Dockerfile` 定义，依赖清单逐条来自 CI 四个 job 的 apt 行，不是拍
脑袋列的：

```sh
docker build -t odin-build:latest .
```

基础镜像钉的是 digest（`debian:bookworm@sha256:813017…`）而不是 tag：tag 会随上游
滚动，digest 保证今天和三年后拿到的是同一层。本地已有该层时 `docker build` 不走
网络（实测确认过，标准输出里没有拉取动作）。要换基础镜像请连 digest 一起改。

起容器：

```sh
mkdir -p tmp/ccache tmp/linux-dtb tmp/linux-kernel

docker run -d --name odin-dev --privileged \
  -v /Volumes/caseSensitiveBar/odin-work:/work/odin-work \
  -v /Volumes/caseSensitiveBar/odin-work/tmp/ccache:/var/cache/odin-ccache \
  odin-build:latest

docker exec -it odin-dev bash        # 进去干活
```

需要跨容器留存的只有 ccache 与内核源码树，**都放在项目的 `tmp/` 下**
（`tmp/` 已被 git 忽略，且本项目所在的外置盘才是该占空间的地方）：

| 挂载 / 目录 | 为什么 |
|---|---|
| 仓库 → `/work/odin-work` | 源码在宿主上编辑，产物直接落在仓库的 `out/` 里，宿主能看见 |
| `tmp/ccache` → `/var/cache/odin-ccache` | ccache 跨容器复用，重建容器不丢 |
| `tmp/linux-msm8953` | 内核源码树（dtb 与 kernel 共用一棵，见第一节）；仓库挂载已经覆盖到了，不用额外挂

**为什么不用 Docker 命名卷**：命名卷存在 Docker 虚拟机的磁盘映像里，而那个映像在
**Mac 内部磁盘**上（命名卷看着"属于 Docker"，实际占的是内置盘空间）。挂项目
`tmp/` 则把开销放到外置盘，且目录可见、可随时看大小。代价是走 bind mount 比容器
本地文件系统慢（几万个小文件的编译最明显）—— 这是用可控的磁盘占用换一点速度。

`CCACHE_DIR` 在镜像里写死成 `/var/cache/odin-ccache`：ccache 4.x 的默认位置判定
规则改过（`XDG_CACHE_HOME` → `~/.cache/ccache` → `~/.ccache`），不写死迟早会出
"缓存在 A 处、卷挂在 B 处"这种查半天的事故。

`--privileged`：debootstrap / chroot / mke2fs 需要的能力不止 Docker 默认那套。这是
本地开发机上的专用容器，直接给全比逐个 `CAP_` 去试省事。

### ccache 的两条配置必须改（已在镜像与 CI 里改好）

`compiler_check` 默认 `mtime`（编译器二进制的 mtime 计入哈希）、`hash_dir` 默认
`true`（带 `-g` 时把 CWD 计入哈希）。这两条在实测里都会让命中率从 100% 掉到 0%，
详见下面第三节"缓存"。

### dtb 与 kernel 用同一棵内核树即可

```sh
make lk2nd  OUT=out
make dtb    OUT=out
make kernel OUT=out
```

**历史（2026-09-04 纠正）**：本文件此前要求"dtb 与 kernel 必须用两棵不同的内核树"，
理由是 dtb 只打 0007、kernel 打全部补丁，共用一棵会撞"0007 已应用"。那其实不是需求，
而是 workaround：冲突的唯一来源是 dtb 阶段用了裸 `patch -p1 --forward`（遇到已应用
返回 1，在 `set -e` 下失败）；而 kernel 阶段用的 `tools/ci/apply-patches.sh` 从一开始
就是幂等的。让 dtb 也走 `apply-patches.sh "$(KDIR)" patches '0007-*'`，同一棵树反复打补
丁就是安全的，于是两棵树不再需要。省掉的代价：本地不必再复制一份上千兆源码树，也不会
出现"这边打了那边没打"的状态漂移。

注意：补丁目录要用**绝对路径**或让脚本自己转（`apply-patches.sh` 会 `cd` 到内核树后再
用补丁目录；为防相对路径在 `cd` 后失效，脚本会先把两个路径都转成绝对——此前传相对路径
会导致匹配不到任何补丁却返回 0，编出的内核悄悄缺驱动。

另外 `apply-patches.sh` 现在会校验"过滤器至少匹配到一个补丁"，匹配不到就报错退出，不做
"看起来过了"的猜测。

### 本地跑 rootfs / publish 要带 `-o kernel -o dtb`

```sh
make -o kernel -o dtb rootfs-gui  OUT=out
make -o kernel -o dtb publish-gui OUT=out
```

`rootfs-*` 的依赖里有 `kernel` 与 `dtb` 两个 target。本地如果给 rootfs 传了与上面
不同的 `KDIR`，make 会认为那棵树的戳不存在、转头去编一遍内核（20+ 分钟），
而且会把 0007 打进内核树里。`-o`（`--old-file`）表达的是"这两个已是最新、别重造"，
CI 的 rootfs job 用的也是这一招。

## 二、本地构建：用 Makefile

**入口是仓库根的 `Makefile`**，不要手敲一长串 `bash tools/ci/*.sh`：

```sh
make help          # 目标与可覆盖变量一览
make print-config  # 打印当前配置（路径、钉死 SHA、变体、并行度…）
make               # 全量：dtb + kernel + lk2nd + rootfs → out/publish
make dtb           # 只编 4 个设备树
make kernel        # 只编内核与模块
make lk2nd         # 只编二级引导（完整版 + 精简版）
make rootfs        # 组装根文件系统并导出镜像（变体取 ODIN_VARIANT，默认 gui）
make rootfs-core / make rootfs-gui       # 显式指定变体
make publish-core / make publish-gui     # 产物汇总到 out/publish + SHA256SUMS
make clean         # 清 out/；make distclean 连内核源码树一起清
```

变量覆盖：

```sh
make JOBS=16 KDIR=/tmp/linux-msm8953 all
make OUT=build rootfs
make ODIN_VARIANT=core rootfs-core       # 变量与目标一致，写哪个都行
```

### 两个变体：core（无 GUI）与 gui（Plasma Mobile）

| 变体 | 内容 |
|---|---|
| `core` | 无 GUI，当服务器 / 开发基线用。产物 `odin-debian.img` |
| `gui` | Plasma Mobile + sddm + 常用工具，产物 `odin-debian-gui.img` |

- **dtb / kernel / lk2nd 与变体无关**，两个变体共用同一份产物，只编一次。
  变体维度从 `rootfs` 才开始引入。
- **core 是 gui 的子集**，所以本地默认只编 gui（`ODIN_VARIANT ?= gui`）——
  没必要为求证一个子集再花一遍 debootstrap 的时间。
- **CI 两个都编**，各一条 job，共用上一步的 kernel / dtb artifact。
- 变体相关的路径都用递归展开（`=` 而非 `:=`）：`ODIN_VARIANT` 是在
  `rootfs-core` / `rootfs-gui` 的 recipe 运行时才确定的，`:=` 会把解析期的
  默认值钉死，两个变体就串台了。
- 戳文件与输出目录都按变体分开（`out/rootfs-core`、`out/rootfs-gui`），
  否则编完 core 再编 gui，make 会认为 rootfs 已最新而跳过。
- debootstrap 的 staging 根目录也按变体分开（`/tmp/odin-rootfs-<变体>`）：
  共用一个目录时第二个变体会直接复用第一个已摆好的根，
  表现为"编了 gui，出来的却是 core"。

变体的串联路径：

```
make ODIN_VARIANT=gui  →  rootfs-gui（模式规则，$* 传变体名）
  → tools/ci/build-rootfs.sh（ODIN_VARIANT + 镜像名）
    → dist/build/setup-rootfs.sh（按变体决定装不装桌面）
```

| 变量 | 默认 |
|---|---|
| `KDIR` | `<仓库>/tmp/linux-msm8953` |
| `OUT` | `<仓库>/out` |
| `KERNEL_REPO` / `KERNEL_SHA` | `msm8953-mainline/linux` / `770e10fa15a00051eaef862e4cb2724f2f8fa568` |
| `LK2ND_VER` | `23.1` |
| `SUITE` | `bookworm` |
| `ODIN_VARIANT` | `gui`（可选 `core`） |
| `CROSS` | `aarch64-linux-gnu-` |
| `JOBS` | `nproc`（macOS 上回退 `sysctl -n hw.ncpu`） |

### 关键约定：能写成直线命令的写进 Makefile，有真逻辑的留脚本

写进 Makefile 的（原 `build-dtb.sh` / `build-kernel.sh` / `build-lk2nd.sh`，共 274 行）：

- `make dtb` —— 打 0007 → 编译 → 拷产物 → 自检
- `make kernel` —— 打全部内核补丁 → olddefconfig → 编译 → 取 vmlinuz/modules.tar → 自检
- `make lk2nd` —— 取源码 → 打 1,2,3,5 → 编完整版 → 打 4 → 编精简版 → 自检

这三段 mostly 是直线流程，做成具名 target 之后步骤一眼可见，还能单独重跑某一步。

仍然是脚本的：

| 脚本 | 为什么 |
|---|---|
| `tools/ci/fetch-kernel.sh` | 三级回退 + 重试，上游只让取 ref 能到达的 commit |
| `tools/ci/build-rootfs.sh` | debootstrap 流水线，串起下面三个 |
| `tools/build-image.sh` | 保守特性集 + 导出 + 20+ 项回读校验 |

这些是判断、循环、错误处理，写进 Makefile 只会变成一坨 `\` 续行。

Makefile 相对原来的散装脚本，多出来的是：

1. 依赖关系显式化（`rootfs` 依赖 `kernel` + `dtb`，`lk2nd` 独立）
2. `out/.stamps/` 戳文件做增量，编过的不白编第二遍
3. **`.SHELLFLAGS := -eu -o pipefail -c`** —— 每条 recipe 都跑在严格模式下。
   这是 Makefile 相对脚本最大的短板（没有 `set -u`、管道里某段失败会被吞），
   补上之后行为与脚本里的 `set -euo pipefail` 一致
4. `SUDO` 自适应：`id -u` 已是 0 就不套 `sudo`（最小容器里根本没这个命令）
5. `JOBS` 自适应 macOS

## 三、CI

`.github/workflows/release-build.yml` **只在 `release: [prereleased, released]` 与
`workflow_dispatch` 时触发**，刻意不挂 push/PR（内核几十分钟 + debootstrap，每次提交跑是浪费）。

job：`dtb`、`lk2nd`、`kernel` 并行 → `rootfs`×2（`core` / `gui`，matrix）→ `publish`。

### CI 怎么调 make

三个并行 job 各自跑一个 target：

```yaml
- run: make dtb    OUT=out
- run: make lk2nd  OUT=out
- run: make kernel OUT=out
```

`rootfs` job 特殊：它靠**下载 artifact** 拿到 kernel 与 dtb 的产物，
不是自己编的。这里用 make 的 `--old-file` 表达"这两个已是最新、不要重造"：

```yaml
- run: sudo -E make -o kernel -o dtb rootfs-${{ matrix.variant }} OUT=out
```

少了 `-o kernel -o dtb`，make 就会在 rootfs 那个 runner 上把内核重编一遍
（20+ 分钟）—— 这正是"跨 runner 传产物"与"本地依赖"的差别。

两个变体各一条 job（`strategy.matrix.variant: [core, gui]`），都下载同一份
kernel / dtb artifact。它们上传的 artifact 名带变体后缀（`odin-rootfs-core`、
`odin-rootfs-gui`），`publish` 两个都下载后再算 SHA256SUMS。
`fail-fast: false`：一条挂掉不要取消另一条，留着对比更容易定位。

### 缓存：kernel job 的 ccache

GitHub Actions 的 cache 本身是不可变归档，不能做到任意文件的增量写回。因此
workflow 不再把补丁或 `.config` 的总哈希放进一个大缓存键，而是利用 ccache
自己的**编译对象级哈希**判断每个 `.o` 是否命中；GitHub 层只把 ccache 的
16 个一级对象分片分别恢复和保存，且只保存本轮真正变化的分片。缓存写入键带
`github.run_id`，恢复使用稳定前缀，避免精确命中后快照冻结。

**两条 ccache 默认值必须改**，否则缓存"恢复成功"但完全用不上：

```sh
ccache --set-config=compiler_check=content   # 默认 mtime
ccache --set-config=hash_dir=false           # 默认 true
```

- `compiler_check` 默认 `mtime`：编译器二进制的 **mtime 计入哈希**。
  CI 每个 job 都全新 `apt-get install` 交叉编译器 ⇒ mtime 每次都变 ⇒
  4399 个编译单元全部未命中。实测：只 `touch` 编译器，命中率从 100% 掉到 0%。
- `hash_dir` 默认 `true`：带 `-g` 时把 **CWD 计入哈希**。本内核
  `CONFIG_DEBUG_INFO=y`，源码树位置一变（旧脚本用 `/tmp/linux-msm8953`，
  迁进 Makefile 后变成仓库内 `tmp/`）旧缓存整体作废。

实测对照（`debian:bookworm-slim` 容器，ccache 4.7.5，`gcc -g` 编同一文件）：

| 场景 | 默认配置 | content + hash_dir=false |
|---|---|---|
| 同目录重编 | 100% | 100% |
| 换目录（CWD 变） | **0%** | 100% |
| touch 编译器（模拟重装） | **0%** | 100% |

**改配置会让既有缓存条目全部失效一次**（哈希规则变了），下一次构建仍是全量，
再往后才稳定命中 —— 这是预期的一次性代价，别误判成"修复没生效"。

判断缓存有没有真生效，看构建末尾 `ccache -s` 的 `Hits` 行，不要看
"Cache restored successfully"：后者只说明文件下载下来了。

### 缓存：lk2nd 编译对象

lk2nd 的 Makefile 原生支持 `CCACHE=ccache`。CI 同样按编译器内容和源文件输入
缓存每个 `.o`，最终两个镜像仍保留独立的内容键缓存：输入完全不变时直接复用镜像，
补丁变化时则重新链接，但未受影响的编译对象由 ccache 命中。

### 缓存：rootfs 的 staging 层

`tmp/job-logs.txt` 显示 gui 的 Plasma 安装约 15 分钟，其中 1200 多个 arm64
包的 dpkg 解包与 qemu postinst 占绝大部分时间。rootfs job 现在还缓存每个变体
的 staging 层（包安装完成、增量修复和镜像导出前），键只包含实际影响该层的
构建脚本、initramfs、DTB 与 kernel artifact 哈希。命中后跳过内核安装、
initramfs 生成及全部 apt/dpkg 安装，只重新应用小型修复并生成镜像；改发布文档、
上传逻辑等无关文件不会使该层失配。首次建立新键仍需完整安装一次，这是预期的
冷启动成本。

staging 输入使用 Git 索引中的 blob ID、文件模式和路径计算哈希，不使用
`hashFiles('dist/build/initramfs/**')`。后者会跟随 initramfs 中构建时才补齐的
符号链接并直接报错，导致 rootfs job 在真正构建前失败。

几个踩过的坑（都在 workflow 注释里）：

- `publish` 的 `if: github.event_name == 'release'` 不能省，否则手动调试时
  `github.event.release.tag_name` 是空的，整条 run 染红
- `gh release upload` 必须显式给 `-R`：publish job 没有 `actions/checkout`，
  `gh` 无本地 `.git` 时无法推断仓库
- rootfs 必须 `sudo` + 之后 `chown`，否则 upload-artifact 读不到 root 建的 0600 镜像

## 四、版本号规则

### 严格递增，永不重用、永不修改

**版本号一旦发布就作废，只能往上开新号。** 不允许：

- 删除已发布的 Release / tag 再拿同一个号重发
- 移动已发布的 tag 指向别的提交
- 就地改写某个已发布版本的资产

理由：制品会被刷进真机，而真机只有一根 USB 线可救。号与内容一旦对不上，
"这台机器跑的是哪一版"就无从回答。

### 开发中的版本：正式号后面加简述后缀

目标版本（如 `v0.9.4`）成功之前，中间所有尝试都用：

```
v0.9.4-<简述>      例：v0.9.4-lk2nd-reboot、v0.9.4-makefile、v0.9.4-modem-fw
```

- **只有最终验证通过、正式发布的那一次，才用干净的三段式 `v0.9.4`**
- 中间版本一律 Pre-release，用来跑 CI、下载、真机验证
- 后缀用小写 ASCII + 连字符，取本次改动的核心词，一眼看出"这版在试什么"
- 禁止 `fix1` / `try2` 这类无信息量的流水号（和时间戳一样没法回溯）
- 发现中间版本有问题 → 修 → **再开新的后缀号**，不回头改
- 正式版说明里交代「经过哪几个后缀版本才收敛」以及各自踩了什么坑

### 发现问题时的标准动作

1. 立刻 `gh run cancel <run-id>` 掐掉正在跑的、已知会产出坏制品的构建（省 runner 时间）
2. 提交修复并推送
3. **开新版本号**重新发布
4. 在**新版本**说明里写明旧版本为什么作废（旧版本自身的说明不要再改）

作废的旧 Release 先留着，删除统一放最后的清理轮次，并先跟用户确认清单。

## 五、可复现性边界

| 产物 | 结论 |
|---|---|
| **DTB** | **逐字节一致（md5 相同）—— 真正可复现** |
| **lk2nd** | 尺寸一致，**md5 不同** |
| **内核 / 模块** | 尺寸一致，**md5 不同** |
| rootfs 镜像 | 含时间戳 / machine-id，不做逐字节比对 |

lk2nd 差约 376 字节 payload，但因 2048 字节页对齐填充，**总大小一模一样** →
**只看 `ls -l` 会误以为复现成功，必须比 md5。**
根因：本地与 `ubuntu-latest` 的交叉工具链版本不同。

实测佐证：v0.9.3 与 v0.9.1 的 4 个 DTB **逐字节一致**、lk2nd 也一致
（那一版只动 initramfs 与用户态，两者源码没变）。

## 六、已知历史坑

- 远程名拼写错误 **`samrtisan`**（应为 `smartisan`）—— 上游既定事实，**不要顺手改**
- `README.md:16`、`:58` 仍用旧仓库名 `odin-port/` 指代本仓库目录
- `.gitignore:27` 忽略 `dist/stage/modules/`，但其中两个文件**已在 git 索引里**
- `odin-qemu/Image` 是另一个内核（defconfig virt 变体），不代表真机内核
- `setup-rootfs.sh:5` 默认 `ODIN_ROOTFS=/mnt/debian`（陈旧 staging），手工跑**必须显式覆盖**
- `dts/build-dtb.sh` 的 dtc 1.6.x 不认 `-Wno-interrupt_map`，脚本已做版本识别
- **手工改 patch 必须同步 hunk 头行计数** —— 项目曾因 hunk 头声明 383 行、
  正文 385 行，GNU patch 按 383 行截断，dts 少两行没闭合
- **`KERNEL_SHA` 散在四处的必须一起改**：`Makefile` 的默认值、
  `.github/workflows/release-build.yml` 的 `env.KERNEL_SHA`（并进 ccache key）、
  `AGENTS.md` 与 `docs/01`、`docs/05` 里的表格。
  make 的 `KERNEL_SHA ?= ...` **不会覆盖环境变量**，所以 workflow 里的值一旦
  落后，CI 就会去取另一棵内核树 —— 本地怎么都编得过、CI 一上就挂，
  而失败点看起来跟基线毫无关系。2026-08-31 实测：换基线提交只改了 Makefile，
  CI 仍按旧 SHA 取树，补丁 0004（R69006 面板）在旧树上打不上，
  kernel job 卡在"应用补丁"就失败。**改基线时按这四处逐一核对。**
- **改 workflow 文件必须用 SSH 推送**：本机的 GitHub OAuth token 没有 `workflow`
  scope，一推 `.github/workflows/*` 就会被拒：
  ```
  ! [remote rejected] main -> main (refusing to allow an OAuth App to
    create or update workflow `.github/workflows/release-build.yml`
    without `workflow` scope)
  ```
  而全局 gitconfig 里有 `url.https://github.com/.insteadof=git@github.com:`，
  所以写 `git@github.com:...` 会被静默改写成 HTTPS、照样失败。
  用 **`git push ssh://git@github.com/<owner>/<repo> <分支>`** ——
  `ssh://` 前缀不匹配那条重写规则，能真正走 SSH。

  配套的一个坑：**Bash 的工作目录在命令之间是保留的**。
  曾经 `cd tmp/xxx` 去看东西，后面直接 `git push` 结果推的是那个子仓库
  （报 `repository not found / ...and the repository exists`），要 `pwd` 才发现。
  进子目录看完就 `cd` 回来，或者一直用绝对路径。
- **每次重刷后 sshd 主机密钥都会变**，需 `ssh-keygen -R 172.16.42.1`
  （旧记录自动留档 `known_hosts.old`），否则 SSH 被 MITM 保护挡在外面
- **从 GitHub 下大文件要去代理**：本机 `http_proxy` 是给别的功能用的，
  走它只有 0.81 MB/s、直连 3.8 MB/s。且 `gh release download` 不支持续传，
  用 `curl -L -C - --retry 8 --retry-all-errors`
