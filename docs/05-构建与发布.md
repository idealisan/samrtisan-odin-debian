## 一、本地构建：用 Makefile

**入口是仓库根的 `Makefile`**，不要手敲一长串 `bash tools/ci/*.sh`：

```sh
make help          # 目标与可覆盖变量一览
make print-config  # 打印当前配置（路径、钉死 SHA、并行度…）
make               # 全量：dtb + kernel + lk2nd + rootfs → out/publish
make dtb           # 只编 4 个设备树
make kernel        # 只编内核与模块
make lk2nd         # 只编二级引导（完整版 + 精简版）
make rootfs        # 组装根文件系统并导出镜像（依赖 kernel 与 dtb）
make clean         # 清 out/；make distclean 连内核源码树一起清
```

变量覆盖：

```sh
make JOBS=16 KDIR=/tmp/linux-msm8953 all
make OUT=build rootfs
```

| 变量 | 默认 |
|---|---|
| `KDIR` | `<仓库>/tmp/linux-msm8953` |
| `OUT` | `<仓库>/out` |
| `KERNEL_REPO` / `KERNEL_SHA` | `msm8953-mainline/linux` / `05f7e89ab9731565d8a62e3b5d1ec206485eeb0b` |
| `LK2ND_VER` | `23.1` |
| `SUITE` | `bookworm` |
| `CROSS` | `aarch64-linux-gnu-` |
| `JOBS` | `nproc`（macOS 上回退 `sysctl -n hw.ncpu`） |

### 关键约定：能写成直线命令的写进 Makefile，有真逻辑的留脚本

写进 Makefile 的（原 `build-dtb.sh` / `build-kernel.sh` / `build-lk2nd.sh`，共 274 行）：

- `make dtb` —— 打 0007 → 编译 → 拷产物 → 自检
- `make kernel` —— 打 0001-0008 → olddefconfig → 编译 → 取 vmlinuz/modules.tar → 自检
- `make lk2nd` —— 取源码 → 打 1,2,3,5 → 编完整版 → 打 4 → 编精简版 → 自检

这三段 mostly 是直线流程，做成具名 target 之后步骤一眼可见，还能单独重跑某一步。

仍然是脚本的：

| 脚本 | 为什么 |
|---|---|
| `tools/ci/fetch-kernel.sh` | 三级回退 + 重试，上游只让取 ref 能到达的 commit |
| `tools/ci/build-rootfs.sh` | debootstrap 流水线，串起下面三个 |
| `tools/build-image.sh` | 保守特性集 + 导出 + 20+ 项回读校验 |

这些是判断、循环、错误处理，写进 Makefile 只会变成一坨 `\` 续行。

Makefile 相对原来的散装脚本，多出来的是：

1. 依赖关系显式化（`rootfs` 依赖 `kernel` + `dtb`，`lk2nd` 独立）
2. `out/.stamps/` 戳文件做增量，编过的不白编第二遍
3. **`.SHELLFLAGS := -eu -o pipefail -c`** —— 每条 recipe 都跑在严格模式下。
   这是 Makefile 相对脚本最大的短板（没有 `set -u`、管道里某段失败会被吞），
   补上之后行为与脚本里的 `set -euo pipefail` 一致
4. `SUDO` 自适应：`id -u` 已是 0 就不套 `sudo`（最小容器里根本没这个命令）
5. `JOBS` 自适应 macOS

## 二、CI

`.github/workflows/release-build.yml` **只在 `release: [prereleased, released]` 与
`workflow_dispatch` 时触发**，刻意不挂 push/PR（内核几十分钟 + debootstrap，每次提交跑是浪费）。

五个 job：`dtb`、`lk2nd`、`kernel` → `rootfs`（needs 前两者）→ `publish`。

### CI 怎么调 make

三个并行 job 各自跑一个 target：

```yaml
- run: make dtb    OUT=out
- run: make lk2nd  OUT=out
- run: make kernel OUT=out
```

`rootfs` job 特殊：它靠**下载 artifact** 拿到 kernel 与 dtb 的产物，
不是自己编的。这里用 make 的 `--old-file` 表达"这两个已是最新、不要重造"：

```yaml
- run: sudo -E make -o kernel -o dtb rootfs OUT=out
```

少了 `-o kernel -o dtb`，make 就会在 rootfs 那个 runner 上把内核重编一遍
（20+ 分钟）—— 这正是"跨 runner 传产物"与"本地依赖"的差别。

几个踩过的坑（都在 workflow 注释里）：

- `publish` 的 `if: github.event_name == 'release'` 不能省，否则手动调试时
  `github.event.release.tag_name` 是空的，整条 run 染红
- `gh release upload` 必须显式给 `-R`：publish job 没有 `actions/checkout`，
  `gh` 无本地 `.git` 时无法推断仓库
- rootfs 必须 `sudo` + 之后 `chown`，否则 upload-artifact 读不到 root 建的 0600 镜像

## 三、版本号规则

### 严格递增，永不重用、永不修改

**版本号一旦发布就作废，只能往上开新号。** 不允许：

- 删除已发布的 Release / tag 再拿同一个号重发
- 移动已发布的 tag 指向别的提交
- 就地改写某个已发布版本的资产

理由：制品会被刷进真机，而真机只有一根 USB 线可救。号与内容一旦对不上，
"这台机器跑的是哪一版"就无从回答。

### 开发中的版本：正式号后面加简述后缀

目标版本（如 `v0.9.4`）成功之前，中间所有尝试都用：

```
v0.9.4-<简述>      例：v0.9.4-lk2nd-reboot、v0.9.4-makefile、v0.9.4-modem-fw
```

- **只有最终验证通过、正式发布的那一次，才用干净的三段式 `v0.9.4`**
- 中间版本一律 Pre-release，用来跑 CI、下载、真机验证
- 后缀用小写 ASCII + 连字符，取本次改动的核心词，一眼看出"这版在试什么"
- 禁止 `fix1` / `try2` 这类无信息量的流水号（和时间戳一样没法回溯）
- 发现中间版本有问题 → 修 → **再开新的后缀号**，不回头改
- 正式版说明里交代「经过哪几个后缀版本才收敛」以及各自踩了什么坑

### 发现问题时的标准动作

1. 立刻 `gh run cancel <run-id>` 掐掉正在跑的、已知会产出坏制品的构建（省 runner 时间）
2. 提交修复并推送
3. **开新版本号**重新发布
4. 在**新版本**说明里写明旧版本为什么作废（旧版本自身的说明不要再改）

作废的旧 Release 先留着，删除统一放最后的清理轮次，并先跟用户确认清单。

## 四、可复现性边界

| 产物 | 结论 |
|---|---|
| **DTB** | **逐字节一致（md5 相同）—— 真正可复现** |
| **lk2nd** | 尺寸一致，**md5 不同** |
| **内核 / 模块** | 尺寸一致，**md5 不同** |
| rootfs 镜像 | 含时间戳 / machine-id，不做逐字节比对 |

lk2nd 差约 376 字节 payload，但因 2048 字节页对齐填充，**总大小一模一样** →
**只看 `ls -l` 会误以为复现成功，必须比 md5。**
根因：本地与 `ubuntu-latest` 的交叉工具链版本不同。

实测佐证：v0.9.3 与 v0.9.1 的 4 个 DTB **逐字节一致**、lk2nd 也一致
（那一版只动 initramfs 与用户态，两者源码没变）。

## 五、已知历史坑

- 远程名拼写错误 **`samrtisan`**（应为 `smartisan`）—— 上游既定事实，**不要顺手改**
- `README.md:16`、`:58` 仍用旧仓库名 `odin-port/` 指代本仓库目录
- `.gitignore:27` 忽略 `dist/stage/modules/`，但其中两个文件**已在 git 索引里**
- `odin-qemu/Image` 是另一个内核（defconfig virt 变体），不代表真机内核
- `setup-rootfs.sh:5` 默认 `ODIN_ROOTFS=/mnt/debian`（陈旧 staging），手工跑**必须显式覆盖**
- `dts/build-dtb.sh` 的 dtc 1.6.x 不认 `-Wno-interrupt_map`，脚本已做版本识别
- **手工改 patch 必须同步 hunk 头行计数** —— 项目曾因 hunk 头声明 383 行、
  正文 385 行，GNU patch 按 383 行截断，dts 少两行没闭合
- **每次重刷后 sshd 主机密钥都会变**，需 `ssh-keygen -R 172.16.42.1`
  （旧记录自动留档 `known_hosts.old`），否则 SSH 被 MITM 保护挡在外面
- **从 GitHub 下大文件要去代理**：本机 `http_proxy` 是给别的功能用的，
  走它只有 0.81 MB/s、直连 3.8 MB/s。且 `gh release download` 不支持续传，
  用 `curl -L -C - --retry 8 --retry-all-errors`
