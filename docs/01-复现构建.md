# 一、复现构建（从零重建全部产物）

本仓库**只放源码与脚本**，不放任何二进制产物。刷机镜像、lk2nd 固件、DTB、内核模块
全部作为 GitHub Release 资产发布。这一篇讲的是：拿到这个仓库后，怎么把那些产物
**从零重新造出来**。

- 推荐路径：[CI 自动构建](#三ci-自动构建发布时触发)（发一个 Release 即可）
- 本地路径：[本地手工构建](#二本地手工构建逐个脚本跑)

---

## 〇、先决条件速查

四条构建链各自的工具依赖（CI 里由各 job 自己装，本地跑要自己备好）：

| 构建 | 需要的工具 |
|---|---|
| DTB | `device-tree-compiler`（提供 `dtc`） |
| 内核 | `gcc-aarch64-linux-gnu`、`bc`、`bison`、`flex`、`libssl-dev`、`libelf-dev`、`kmod`、`cpio`、`rsync`、`patch`（`ccache` 可选，装了就自动启用） |
| lk2nd | `gcc-arm-none-eabi`、`device-tree-compiler`、`libfdt-dev`、`make` |
| rootfs | `debootstrap`、`qemu-user-static`、`binfmt-support`、`e2fsprogs`、`android-sdk-libsparse-utils`、`kmod`、`cpio`、`parted`；**必须以 root 运行**（debootstrap / chroot / mke2fs 都要提权） |

macOS 上跑不了 rootfs 那一环（需要 chroot 进 arm64 根并注册 binfmt），请放进
Debian/Ubuntu 容器或虚拟机里跑。

## 一、钉死的外部依赖（以及为什么必须钉）

可复现的前提是输入固定。三个外部输入全部钉死，上游再动也不影响结果：

| 依赖 | 它到底是什么 | 钉在哪里 | 出处 |
|---|---|---|---|
| **内核** | 主线 Linux 的 msm8953 分支 | `msm8953-mainline/linux` @ `05f7e89ab9731565d8a62e3b5d1ec206485eeb0b`（Linux 6.19） | `tools/ci/fetch-kernel.sh:22`、`tools/ci/build-*.sh` 的 `KERNEL_SHA` 默认值、`.github/workflows/release-build.yml` 的 `env.KERNEL_SHA` |
| **lk2nd** | 二级引导程序（**不是内核**，是刷进 boot 分区、负责找 `/extlinux/extlinux.conf` 的那层） | 上游 `msm8916-mainline/lk2nd` @ tag `23.1` | `Makefile` 的 `LK2ND_VER` 默认值、workflow 的 `env.LK2ND_VER` |
| **Debian** | 根文件系统 | 套件 `bookworm`，架构 `arm64`，`--variant=minbase` | `tools/ci/build-rootfs.sh:22` 的 `SUITE` 默认值 |

> 注意表中两个 GitHub 组织名字很像但**不是一个东西**：
> 内核在 `msm8953-mainline`，lk2nd 在 `msm8916-mainline`。别看串了。

### 为什么内核必须钉到那个 commit

1. **补丁的适用性只对这一个基线成立。** `patches/0001`–`0008` 是按这个上游提交
   的上下文生成的。上游一改，补丁可能打不上，或者打上了却编出行为不同的内核。
   CI 的价值恰恰是"同一个输入必然得到同一个输出"。
2. **不能钉本地 `odin-wip` 的 HEAD。** 那个分支的 HEAD 已经含我们的 0007 补丁，
   不是上游提交，GitHub 取不到（rc1 就是这么败的：`upload-pack: not our ref`）。
3. **按 SHA 直接 fetch 不一定成功。** GitHub 只允许取"某个 ref 能到达的"提交，
   一旦 master 往前走，钉的 commit 就不是 tip 了。所以 `fetch-kernel.sh` 做了三级回退：

   ```
   1) git fetch --depth 1 origin <sha>                    # 仍是 tip 时最快
   2) git fetch --shallow-since=2026-02-07 origin master  # 按时间截断（钉住提交的前一天）
   3) git fetch origin master                             # 整支，最慢但不失败
   ```
   每级结束都 `git checkout <sha>` 并校验 `HEAD == KERNEL_SHA`——**钉不住就宁可失败**，
   绝不悄悄编出一个"上游最新版"。

### 为什么 lk2nd 钉 23.1，而且必须是 msm8916-mainline

- **不是 `msm8953-mainline/lk2nd`。** 那个仓库的设备树在 `dts/`、设备表在 `dts/rules.mk`，
  而我们的补丁路径是 `lk2nd/device/dts/msm8953/rules.mk` —— 目录结构完全不同，补丁对不上。
- **不是 19.0 / 21.0。** `lk2nd/0002` 是按 23.x 的设备表写的上下文：
  - 19.x 的设备表只有 21 个条目，行尾是两个空格；
  - 21.0 把 `flipkart-rimob` 改名成 `billion-rimob`，还缺 `qrd-sku3` / `wingtech` /
    `sdm632-mtp-3` 等条目 ⇒ `Hunk #1 FAILED`。
- 23.0 与 23.1 的 `rules.mk` 逐字节一致，取较新的 **23.1**。

### lk2nd 的上游是谁？postmarketOS 是什么角色

这一点容易混淆，先说结论：**upstream 是 `msm8916-mainline/lk2nd` 这个社区项目，
postmarketOS 只是把 lk2nd 打包进自己发行版的打包者，不是另一个上游。**

- lk2nd 由 msm8916-mainline 社区维护，仓库 `github.com/msm8916-mainline/lk2nd`。
  名字里的 `msm8916` 是项目起源的 SoC，但它同时支持 msm8953 / sdm450 / sdm632 等
  一系列同代芯片——我们用的就是它的 `lk2nd-msm8953` 构建目标。
- postmarketOS 在 `pmaports` 的 `main/lk2nd` 里提供 APKBUILD 把它打成包。
  所以设备上 lk2nd 自报版本是 `21.0-r0-postmarketOS` —— **`-postmarketOS` 只是 pmOS
  的包版本后缀**，意思是"pmOS 打包的第 21.0 版"，不代表存在另一个 lk2nd 上游分支。

三个版本号的关系（别互相套）：

| 版本 | 是什么 |
|---|---|
| `19.0` | 本机 `/Volumes/caseSensitiveBar/pmaports` 检出里的 `pkgver`。该检出是 2024-11-03 的快照，比设备上那版还旧，**与本项目的构建无关**，只是当初查线索时看到的 |
| `21.0-r0-postmarketOS` | 这台手机原本跑的那版（pmOS 打包）。我们没复用它 |
| `23.1` | **本项目构建实际用的**，上游 tag |

结论：本项目直接取上游 tag 23.1 的源码 + 打我们的补丁，**不经过 pmOS 的打包**，
所以设备上原来装的是哪个 pmOS 版本都不影响复现。

### 为什么 Debian 现装而不是复用预制镜像

`build-rootfs.sh` 从 `http://deb.debian.org/debian` 现装 bookworm/arm64，
不依赖任何"上一次构建留下来的东西"。历史上容器里的 `/mnt/debian` 是 8/23 的陈旧
staging，拿它重建会丢掉后面装进镜像的 NetworkManager 等改动（reports/013 教训）。
现装才谈得上可复现。

## 二、本地手工构建（用 make）

**入口是仓库根的 `Makefile`**，逐步跑就逐步编：

```
                 ┌─> make dtb    ──> out/dtb/*.dtb
make fetch-kernel┤
                 └─> make kernel ──> out/kernel/{vmlinuz,modules.tar}
                                              │
                                              ├─> make rootfs ──> out/rootfs/*.img
                                              │
make lk2nd ───────────────────────────────────┘（独立，不依赖内核源码）

make publish  ← 汇总上面全部产物到 out/publish 并生成 SHA256SUMS
```

依赖关系由 Makefile 声明（`rootfs` 依赖 `kernel` + `dtb`），并用 `out/.stamps/`
下的戳文件做增量 —— 编过的不会白编第二遍。

仍保留为脚本的两个（都是真逻辑，不适合写成 recipe）：

| 脚本 | 为什么还是脚本 |
|---|---|
| `tools/ci/fetch-kernel.sh` | 三级回退 + 重试：上游只让取 ref 能到达的 commit |
| `tools/ci/build-rootfs.sh` | debootstrap 流水线，串起 `setup-rootfs.sh` / `apply-staging-fixes.sh` / `build-image.sh` |

### 1. 取内核源码

```sh
make fetch-kernel          # 默认取到 ./tmp/linux-msm8953
make fetch-kernel KDIR=/tmp/linux-msm8953
```

已在该 commit 时会打印"复用"并直接退出，可以放心重跑。

### 2. 编 DTB

```sh
make dtb
```

内部会自己先跑 `fetch-kernel`（`KDIR` 默认 `./tmp/linux-msm8953`），打上
`patches/0007-*`（只打 0007：设备树只依赖它，少打就少几个失配点），
再调 `dts/build-dtb.sh` 编出四个 DTB 并拷进输出目录：

| 产物 | 说明 |
|---|---|
| `msm8953-smartisan-odin-ft8716.dtb` | 面板写死 FT8716（完整版） ← `l0` 用 |
| `msm8953-smartisan-odin-ft8716-norolesw.dtb` | 面板写死 FT8716（安全版） ← **`l0-safe` 首刷默认** |
| `msm8953-smartisan-odin.dtb` | 自动识别面板（完整版） ← 换屏后的退路 |
| `msm8953-smartisan-odin-norolesw.dtb` | 自动识别面板（安全版） |

自检：写死版含 `smartisan,odin-ft8716`；安全版不含 `usb-role-switch`。

> 注意：`dts/build-dtb.sh` 的产物落在仓库的 `dts/` 目录下，再由 `make dtb`
> 拷进输出目录。仓库里 `dts/*.dtb` 是构建产物，别手改。

### 3. 编内核与模块

```sh
make kernel
```

会打上 `patches/` 下**全部**补丁（0001–0008，CI 的价值之一就是持续证明它们仍适用），
用 `config-postmarketos-qcom-msm8953.aarch64` 作 `.config`，
`make olddefconfig` 后编 `Image modules`。产物：

- `out/kernel/vmlinuz`（`arch/arm64/boot/Image`）
- `out/kernel/modules.tar`（内核模块树，rootfs 阶段装进镜像）

自检：`panel-ft8716.ko` / `panel-r69006.ko` / `panel-nt36672.ko` 必须存在，否则退出非 0。

装了 `ccache` 会自动启用（内核 Makefile 的 `CC` 由 `CROSS_COMPILE` 拼出来，
必须显式覆盖才能走缓存），跑完会打印命中率 —— **全 0 说明缓存键或 CC 没生效，
别当成"缓存做过了"**。

构建日志 `tee` 双写：既实时输出，也留一份 `/tmp/odin-kernel-build.log`
（`modules_install` 那份是 `/tmp/odin-modules-install.log`）。

### 4. 编 lk2nd

```sh
make lk2nd
```

源码从 `https://github.com/msm8916-mainline/lk2nd/archive/refs/tags/23.1.tar.gz`
解到 `./tmp/lk2nd-src`（`LK2ND_SRC` 可覆盖），用 `patch -p1`（不是 `git apply` —— tarball 解出来没有 git 索引，
`--3way` 用不了）。两个产物分两轮：

1. 打 `lk2nd/0001`–`0003` 与 `0005` → 编出 **`lk2nd.img`**（完整版，保留全部 29 个设备条目）
2. 再打 `lk2nd/0004`（去掉 `msm8953-xiaomi-markw` 与 `sdm450-xiaomi-rosy`）→
   增量重编 → **`lk2nd-nomarkw.img`**（精简版，强制命中 odin 条目）

刷机用精简版：只有命中 odin，DTB 里的占位 compatible `smartisan,odin-panel`
才会被替换成真实面板，屏幕才会亮。

自检：精简版 `strings` 里搜不到 `xiaomi-markw`，但必须有 `smartisan-odin`。

### 5. 组装系统镜像

```sh
sudo -E bash tools/ci/build-rootfs.sh out/rootfs out/kernel out/dtb
#                                     ^输出目录  ^内核产物  ^DTB 产物
```

流程：

```
debootstrap bookworm/arm64
  → 装内核模块 + vmlinuz + depmod
  → 造 initramfs（busybox 从刚装的 arm64 根里取，不入库）
  → dist/build/setup-rootfs.sh（用户/网络/服务）
  → dist/build/apply-staging-fixes.sh（增量修复 + overlay + DTB + extlinux）
  → tools/build-image.sh（保守特性集 + 导出 sparse/raw + 逐项回读校验）
```

产物：`out/rootfs/odin-debian.img`（**1.875 GiB** raw）与 `out/rootfs/odin-debian-sparse.img`。

镜像内根文件系统只有 1.875 GiB，首启由 `odin-firstboot-resize.service` 在线扩容到
userdata 实际容量（实机约 111.9 GiB），日志在设备上的 `/var/log/odin-resize.log`。

### `tools/build-image.sh` 固化了什么

导出这一步不是简单的 `mkfs` + `dd`。它把几条**都是拿教训换来的**约束固定下来：

```sh
tools/build-image.sh <staging目录> <输出img> <blocks> [label]
# 例：tools/build-image.sh /mnt/stage out/odin-debian.img 524288 pmOS_root
#    blocks = 524288 个 4KiB 块 = 2 GiB；label 默认 pmOS_root
```

| 约束 | 为什么 |
|---|---|
| staging 必须是**未挂载的普通目录** | 挂载态复制会让超级块的 free 计数与位图不一致 |
| 特性集保守：`ro_compat ⊆ {sparse_super, large_file}` | lk2nd 的 ext2 驱动只认这套（`lib/fs/ext2/ext2.c:162-166`，它完全不检查 compat/incompat）。用发行版默认 `mkfs.ext4` 重建 ⇒ lk2nd 挂不上 ⇒ 整条引导链不执行 |
| 必须保留 `resize_inode` + reserved GDT | 否则在线扩容会在第 128 组（16 GiB）处命中 `No reserved GDT blocks, can't resize` 而 EPERM |
| 导出后 e2fsck 至干净、img2simg、check_sparse、逐项回读校验 | 任一失败即非零退出 |
| 产物 < 2147483648 字节 | GitHub Release 单个资产上限（是"小于"）。超了要等 `publish` job 报 HTTP 422 才发现，排查要跨 job，不如在这里就挡住 |

另外它会清掉 `machine-id` / `random-seed` / `journal` / `wtmp`（镜像要公开发布，
不能所有设备共用一个 machine-id），并**删掉 SSH 主机私钥**（发布安全红线）。

> 内核版本目录名**不能写死**：`scripts/setlocalversion` 在"工作树不干净"时会追加一个 `+`，
> 而 CI 里补丁是打在工作树上的（git 里永远是脏的），实际目录名是
> `6.19.0-postmarketos-qcom-msm8953+` —— 少那个 `+` 就找不到模块。

### 附：增量重建路径（历史做法，现在不推荐）

早期几版镜像是"挂载镜像就地改"出来的，那时的流程是：

```sh
# 1) 以当前镜像内容为基线建可写 staging（挂载态复制是历史 bug 的根源，必须先卸载再复制）
mount -o ro,loop dist/odin-debian.img /mnt/src && cp -a /mnt/src/. /mnt/stage/
# 2) 应用增量修复（幂等）
dist/build/apply-staging-fixes.sh /mnt/stage
# 3) 导出 + 全量校验
tools/build-image.sh /mnt/stage /mnt/img/odin-debian.new.img 524288 pmOS_root
```

还有个 Docker 容器 `odin-build`（`debian:bookworm` arm64），rootfs 在容器内的
`/mnt/debian`。

> ⚠️ **这两条都别再用。** 容器里的 `/mnt/debian` 是 8/23 的陈旧 staging，
> 不含后来装进镜像的 NetworkManager / WiFi / 自动挂载等改动，拿它重建会丢东西。
> 现在一律走"debootstrap 现装 + `build-rootfs.sh`"这条线（见本节开头），
> 历史教训见 `reports/013`。

### 常用环境变量覆盖

| 变量 | 默认 | 作用 |
|---|---|---|
| `KDIR` | `/tmp/linux-msm8953` | 内核源码落点 |
| `KERNEL_REPO` / `KERNEL_SHA` / `KERNEL_BRANCH` | 见上 | 上游基线 |
| `KERNEL_SINCE` | `2026-02-07` | `--shallow-since` 的日期（钉住提交的前一天） |
| `CROSS` | `aarch64-linux-gnu-` | 交叉编译前缀 |
| `JOBS` | `$(nproc)` | 并行度 |
| `LK2ND_VER` / `SRC` | `23.1` / `/tmp/lk2nd-src` | lk2nd 版本与源码落点 |
| `ROOT` / `SUITE` | `/tmp/odin-rootfs` / `bookworm` | rootfs staging 目录与套件 |
| `KOUT` / `DOUT` | `<OUT>/../kernel`、`<OUT>/../dtb` | build-rootfs 的内核/DTB 输入 |

> 根目录可以覆盖（`ODIN_ROOTFS`），但**不要**指向历史遗留的 `/mnt/debian`
> staging —— 那是陈旧状态，见上面"为什么现装"。

## 三、CI 自动构建（发布时触发）

流水线：`.github/workflows/release-build.yml`（`name: release-build`）。

### 触发条件

```yaml
on:
  release:
    types: [prereleased, released]
  workflow_dispatch:
```

- **只挂 Release 事件**，刻意不挂 `push` / `pull_request`：内核要编几十分钟，
  rootfs 要走一遍 debootstrap，每次提交都跑纯属浪费公共资源。
- **只用 `prereleased` + `released`，不要加 `published`。** GitHub 发布 pre-release 时
  会**同时**发 `published` 与 `prereleased`，发布正式版时会同时发 `published` 与
  `released` —— 把 `published` 也写上就会每次发布跑两遍（实测确实触发了两个 run）。
  这两个类型不重叠，正好各一次。
- `workflow_dispatch` 只是手动调试入口，不会有任何自动触发。

### 五个 job

| job | 依赖 | 做什么 | 产出 artifact |
|---|---|---|---|
| `dtb` | — | 装 dtc → `make dtb OUT=out` | `odin-dtb` |
| `lk2nd` | — | 装 `gcc-arm-none-eabi` → `make lk2nd OUT=out` | `odin-lk2nd` |
| `kernel` | — | 取 ccache 缓存 → 装工具链 → `make kernel OUT=out` | `odin-kernel` |
| `rootfs` | `needs: [kernel, dtb]` | 装 debootstrap + binfmt → 取前两个 artifact → `sudo -E build-rootfs.sh` | `odin-rootfs` |
| `publish` | `needs: [dtb, lk2nd, rootfs]`，且 `if: github.event_name == 'release'` | 汇总 → 生成 `SHA256SUMS` → `gh release upload` | 挂到 Release |

`publish` 那个 `if` 不能省：手动调试时 `github.event.release.tag_name` 是空的，
`gh release upload` 必然失败，会把整条 run 染红。

`gh release upload` 必须显式给 `-R ${{ github.repository }}`：`publish` job 没有
`actions/checkout`（只需要产物、不需要源码），`gh` 在没有本地 `.git` 时无法推断仓库，
会报 `fatal: not a git repository` —— rc3 就是死在这里。

kernel job 的 ccache 键是 `kernel-ccache-${KERNEL_SHA}-${{ hashFiles('patches/*.patch') }}`
：**补丁内容必须留在键里**，不能为了命中率牺牲正确性。

### 怎么触发一次

```sh
# 发一个 pre-release 即触发（推荐，验证链路用）
gh release create v0.1.0-rc4 --prerelease --title "v0.1.0-rc4" --notes "CI 验证"

# 或者纯调试、不产生 Release：
gh workflow run release-build.yml
```

跑到 `publish` 之后，Release 页面上会挂上：

```
lk2nd.img  lk2nd-nomarkw.img
msm8953-smartisan-odin*.dtb        （四个变体）
odin-debian.img  odin-debian-sparse.img
SHA256SUMS
```

## 四、可复现性的边界（实测结论，别含糊）

把 CI 产物与本地产物拉到一起比对，结论分三档：

| 产物 | 结论 |
|---|---|
| **DTB** | **逐字节一致（md5 相同）—— 真正可复现** |
| **lk2nd** | **尺寸一致，md5 不同** |
| **内核 / 模块** | **尺寸一致，md5 不同**（与 lk2nd 同源：编译器版本差异） |
| rootfs 镜像 | 未做逐字节比对（内含时间戳、machine-id、dnsmasq 租约等天然变量） |

### lk2nd 差在哪（可量化的那部分）

以 `lk2nd.img` 为例：

```
本地:  366608 字节  md5 521d64fcb2ab4cf534bac1f9b8440712  kernel_size 352980
CI  :  366608 字节  md5 2d6fd4b07cc4f151b1038e1783a96899  kernel_size 353356
                                                          差            +376
```

`lk2nd-nomarkw.img` 同样：总大小都是 364560 字节，`kernel_size` 351316 vs 351692，
**差 376 字节**。

也就是说：**两个构建产出的 payload 差 376 字节，但因为按 2048 字节页对齐填充，
最终镜像总大小一模一样。** 只看 `ls -l` 会误以为"复现成功"，必须比 md5。

### 根因与补全方向

根因是**工具链版本不同**（本地与 `ubuntu-latest` runner 上的
`gcc-arm-none-eabi` / `gcc-aarch64-linux-gnu` 不是同一个版本），编译产物天然不同。

要做到逐字节一致，还得两件事同时成立：

1. **钉住工具链版本** —— 不只是钉源码，交叉编译器本身也要钉到确定的版本/构建。
2. **注入 `SOURCE_DATE_EPOCH`** —— 内核与部分构建会把构建时间编进产物里，
   固定这个环境变量才能消除时间维度的差异。

在这两件事做完之前，请按"尺寸一致、内容等价、md5 不同"来理解 lk2nd 与内核的
复现结果：**功能等价已验证，逐字节未达成。**

## 五、怎么验证一份下载下来的产物是可信的

从 Releases 页面下载完，**刷之前先核一遍**。三层手段，从强到弱，按需选用。

### 1. 核 `SHA256SUMS`（首选）

Release 上挂的 `SHA256SUMS` 是 `publish` job 里
`cd out && sha256sum * | sort -k2 > SHA256SUMS` 生成的，覆盖全部产物。

```sh
# 把 SHA256SUMS 与产物放在同一个目录里，然后：
shasum    -a 256 -c SHA256SUMS      # macOS（BSD）
sha256sum       -c SHA256SUMS      # Linux（GNU coreutils）
```

全部输出 `<文件名>: OK` 才算通过。

> ⚠️ **必须用同一次发布里那份 `SHA256SUMS`。**
> 拿 run A 的校验和去验 run B 的产物，会**全部 FAILED** ——
> 但这不代表产物坏了：不同次构建的镜像内容本就不同（构建时间戳、machine-id 之类），
> 校验和本来就不一样。这个坑踩过一次，一度以为产物损坏。
> ⇒ 下载产物和 `SHA256SUMS` 要**从同一个 Release 页面、一次性取回**。

### 2. `check_sparse.py` 交叉验证（不依赖 CI，本地就能做）

即使手上没有 `SHA256SUMS`，也可以自证 sparse 版是对的：它把 sparse 解回原始字节
再与 raw 版逐字节比对。

```sh
python3 tools/check_sparse.py odin-debian-sparse.img odin-debian.img
# 期望输出 IDENTICAL，退出码 0
# 不一致则输出 DIFFERENT: N differing 4096-byte blocks 与最前面几个偏移（十六进制）
```

这是**独立于 CI 的交叉验证**：证明 sparse 解码后与 raw 完全一致，
所以刷哪个都一样。

> 注意：它把两份镜像**整体读进内存**比对，2 GiB 的 raw 版需要相应内存。

### 3. 三个魔数快检（最廉价，不需要挂载、不需要下载两份）

| 产物 | 位置 | 期望字节 | 是什么 |
|---|---|---|---|
| `odin-debian.img` | 偏移 `1080`，2 字节 | `53 ef` | ext4 超级块魔数（常写作 `0xEF53`） |
| `odin-debian-sparse.img` | 开头 4 字节 | `3a ff 26 ed` | Android sparse 魔数（值 `0xED26FF3A`） |
| `lk2nd*.img` | 开头 8 字节 | ASCII `ANDROID!` | Android bootimg 魔数 |

```sh
xxd -s 1080 -l 2 -p odin-debian.img             # → 53ef
xxd -s 0    -l 4 -p odin-debian-sparse.img      # → 3aff26ed
head -c 8   lk2nd-nomarkw.img; echo             # → ANDROID!
```

没有 `xxd` 时用 `od`（POSIX 通用）：

```sh
od -An -tx1 -j 1080 -N 2 odin-debian.img        # → 53 ef
od -An -tx1 -j 0    -N 4 odin-debian-sparse.img # → 3a ff 26 ed
```

> 这三条只证明"是这种格式、没被截断成别的东西"，**不证明内容正确** ——
> 完整性还是要看前两条。

### 下载产物放哪儿

**不要把下载的产物覆盖 `dist/` 下那两个被 git 跟踪的二进制**
（`dist/odin-debian.img` 等）—— 2 GiB 的文件改一个字节就是巨大 diff。
放到 `dist/dl/` 之类不受版本控制的地方，或者干脆放 `dist/` 之外。

`flash-all.sh` 也支持直接指定路径：

```sh
BOOT_IMG=/path/to/lk2nd-nomarkw.img \
DATA_IMG=/path/to/odin-debian-sparse.img \
  flash/flash-all.sh
```

## 六、附：公开副本与推送

源仓库有 4.7 GB 历史（含大量二进制），**不能直推公开仓库**。公开副本由脚本生成：

```sh
# 输出目录用自己专属的，多人同时协作时不会互相撞车
rm -rf /tmp/odin-<你的名字>
bash tools/prepare-public-repo.sh /tmp/odin-<你的名字> ~/.config/odin-port/replacements.txt
cd /tmp/odin-<你的名字>
git remote add origin git@github.com:idealisan/samrtisan-odin-debian.git
git push -u origin main
```

> **别共用一个输出目录。** 那份副本是 `filter-repo` 重写过的独立仓库，
> 两个人同时用同一个目录会撞车（第二次 `git remote add` 报"已存在"、
> 或者把对方的产物混进来）。各自用 `/tmp/odin-<名字>` 即可。

脚本会剔除全部二进制与超大 blob、按规则脱敏（**文件内容和提交信息都换**），
源仓库不动。脱敏规则文件刻意放在仓库**外面**——规则里必然写着要替换掉的原串，
一旦入库就等于把想藏的东西又写回公开仓库。

非 fast-forward 就重跑 prepare 再推，**绝不加 `--force`**。
