# 四、排障手册（症状 → 定位 → 解法）

这一篇是从 `WORKLOG.md` 里抽出来的**可复用排障知识**，全部来自真机或 QEMU 上的实测。
`WORKLOG.md` 是按时间的流水账（900+ 行），这里按"看到什么症状 → 怎么定位 → 怎么解"
重新组织，方便检索。

每条都给**可执行的定位命令**和**为什么会这样**。命令默认在 PC 上跑，
`$ ssh odin` 代表 `ssh user@172.16.42.1`（密码 `user`）。

## 一、方法论：先看日志是否完整

### 症状：改完之后 `dmesg | grep -c "Failed to initialize panel"` = 0，以为修好了，其实没修好

**为什么**：开着 `drm.debug` 时 vblank 日志会把 dmesg 的**环形缓冲刷爆**，
早期的错误记录被后来的日志覆盖掉。于是 grep 到"0 次失败"——**假结论**。
本项目在这上面栽过两次：一次误判面板修好了，一次误判根因是 GPU。

**定位**：先确认环形缓冲是完整的，再看结论：

```sh
$ ssh odin 'dmesg | head -3'          # 看最早记录的时间戳是不是开机那一刻
$ ssh odin 'dmesg | wc -l'
$ ssh odin 'cat /proc/cmdline'        # 确认有没有 drm.debug
```

如果最早的时间戳已经离开机很远，说明早期日志被冲掉了 —— **去掉 `drm.debug` 重启再抓**。

**通用规则**：

- 任何"日志里没这个错误"的结论，都要先验证环形缓冲是否完整。
- 用 `drm.debug` 抓日志前，先确认要抓的类别不会刷爆缓冲
  （`drm.debug=0x1ff` 之类的全开是最容易踩的）。
- **`dd` 直接写 `/dev/fb0` 不一定刷到硬件**（msm 的 fbdev 需要 damage 触发），
  不能作为"像素管道不通"的证据。

### 通用手段：定位"静默失败"

很多内核函数失败时**不打印任何日志**（例如 `dsi_host_transfer()` 开头
`if (!msg || !msm_host->power_on) return -EINVAL;`）。定位手法：

1. 给判据处的宏 / 函数**临时加打印**；
2. 只重编那一个模块：
   ```sh
   make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=drivers/gpu/drm/panel modules
   ```
3. `scp` 到设备覆盖 `.ko` + `depmod -a`，重启看日志；
4. 定位完 **revert 重编干净版**（本项目残留的 `FT8716 DBG` 打印已清零）。

## 二、传输类

### 症状：经 SSH 传大文件，每次都在 ~110MB 处断，设备随后 30 秒完全不响应 ping

**为什么**：不是带宽问题。分离测试证明纯流量 400MB 用 20s 跑完（约 20MB/s），
而是**设备端 `tar` 边读边往外吐时 USB NCM 链路会 stall**。
USB 接在繁忙的 hub 上时尤其明显。

**定位**：

```sh
# 1) 纯流量压测，排除带宽因素
$ ssh odin 'dd if=/dev/zero bs=1M count=400' > /dev/null

# 2) 看传输是不是总在同一个量级断
$ ssh odin 'tar -cf - /' | gzip > /tmp/x.tar.gz
```

**解法**：**大批量数据先在设备本地落盘，传输阶段只做顺序大文件拷贝**。
`flash/stages/10-backup.sh` 就是这么做的：设备本地 `tar` → HTTP 拉取。
详见 [02-刷入指南.md § 零](02-刷入指南.md)。

---

### 症状：`curl` 连 `172.16.42.1` 报 `code=000`，但 `ping` 和 TCP 都通

**为什么**：开发机上普遍设了 `http_proxy` / `HTTP_PROXY`
（本机这个指向 `127.0.0.1:3030`），curl 会把 `172.16.42.1` 的请求也发给代理。

**定位**：

```sh
env | grep -i proxy
curl -v http://172.16.42.1:8080/ 2>&1 | head -20   # 看是不是连到了代理
```

**解法**：

```sh
curl -C - --noproxy '*' --retry 10 --retry-delay 2 --retry-all-errors \
     -o out.tar "http://172.16.42.1:8080/rootfs-full.tar"
```

`--noproxy '*'` 不能省。`-C -` 支持**断点续传**，中途断了不用从头再来。

---

### 症状：读 `/root` 下的文件得到空结果，误判成"备份被截断"

**为什么**：`/root` 是 **0700**。用 `user` 身份（`odin_ssh`）去读会得到
**空结果而不是报错** —— 极易误判。本项目差点把一份完好的备份判成损坏。

**定位**：

```sh
$ ssh odin 'stat -c "%a %n" /root'
```

**解法**：涉及 `/root` 一律走提权通道：

```sh
# 本项目封装好了，脚本里用这个
odin_sudo <<'R'
  stat -c%s /root/odin-backup/rootfs-full.tar
R

# 手工等价形式
sshpass -p user ssh ... user@172.16.42.1 'echo user | sudo -S sh -c "..."'
```

## 三、shell / 脚本类

### 症状：脚本在 macOS 上报 `syntax error near unexpected token ';;'`

**为什么**：macOS 默认 `/bin/bash` 是 **3.2**，它解析不了 `$( )` 里带 `;;` 的 `case`
语句。最小复现都报错。

**解法**：把判定抽成一个函数，不要在命令替换里写 `case`：

```sh
# 不行
x=$(case "$f" in *.tar) echo a;; esac)

# 可以
is_binary() { case "$1" in *) file -b "$1" | grep -q text && return 1 ;; esac; return 0; }
x=$(is_binary "$f" && echo a)
```

---

### 症状：脚本报 `DEVICE_IP\uFFFD: unbound variable`

**为什么**：bash 在 C locale 下会把紧跟在 `$VAR` 后面的**中文字符当成变量名的一部分**
（`$DEVICE_IP）——先确认` 被解析成变量名 `$DEVICE_IP）...`）。

**解法**：所有变量一律写成 `${VAR}`，尤其后面要跟中文时。

---

### 症状：`ssh ... 'echo user | sudo -S bash -s' <<'EOF'` 里的命令根本没执行

**为什么**：`echo user |` 把 sudo 的 **stdin 占用了**，`bash -s` 读不到 heredoc ⇒
命令静默没跑。（之前成功的那次是 `bash /tmp/install_dtbs.sh`，脚本在远端，**不是** `bash -s`。）

**解法**：先把脚本**传到远端再执行**，不要走 `bash -s`：

```sh
sshpass -p user ssh ... user@172.16.42.1 'cat > /tmp/rn.sh' < ./local.sh
sshpass -p user ssh ... user@172.16.42.1 'echo user | sudo -S cp /tmp/rn.sh /usr/local/sbin/x.sh'
sshpass -p user ssh ... user@172.16.42.1 'echo user | sudo -S bash /tmp/rn.sh'
```

本项目的 `odin_sudo` 就是这么实现的（把密码从 stdin 喂进去，脚本也走 stdin，两段拼接）。

---

### 症状：`set -e` 下脚本静默退出，没有报错

**为什么**：`set -e` 下 `cmd && printf ...` 这种写法，当 `cmd` 返回 1 且它是
`while` 循环体的最后一条命令时，会把整个子 shell 带崩。

**解法**：用 `if/then/fi` 而不是 `&&` 短路。

---

### 症状：SSH 用 `sshpass` 传密码却一直卡在认证上

**为什么**：`ssh` 会**先试 publickey**，卡在那里，sshpass 传入的密码永远轮不上。

**解法**：

```sh
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no ...
```

本项目的 `flash/lib/common.sh` 已把这些选项固化在 `_ssh_common()` 里。

---

### 症状：在 zsh 里 `$SSHO` 一堆选项被当成一个参数

**为什么**：zsh 里变量**不做单词分割**。`$SSHO` 会被当成一个完整的参数传进去。

**解法**：要么写成 `"${=SSHO}"`（zsh 专用），要么干脆写完整选项、或把整段收进脚本文件。

---

### 症状：macOS 上 `timeout 60 cmd` 报 command not found

**为什么**：macOS 没有 GNU coreutils 的 `timeout`。

**解法**：脚本里不要依赖 `timeout`；本项目在 `common.sh` 里自己实现了
`wait_until <描述> <总超时> <间隔> <命令...>` 与 `retry <次数> <描述> <命令...>`。

## 四、systemd 类

### 症状：udev 规则里写了 `TAG+="systemd"` 和 `ENV{SYSTEMD_MOUNT_OPTIONS}=...`，U 盘插上完全不挂载

**为什么**：bookworm 的 **systemd 252** 里：

- **PID 1 不读任何 `SYSTEMD_MOUNT_*` 属性** ⇒ 光打 TAG 不会挂载任何东西；
- `/usr/bin/systemd-mount` **不读 `SYSTEMD_MOUNT_OPTIONS` 环境变量**
  （实测挂出来是默认选项）。

**定位**：

```sh
$ ssh odin 'tail -20 /var/log/odin-automount.log'
$ ssh odin 'udevadm info -q property -n /dev/sda1 | grep -E "ID_BUS|ID_FS_TYPE|ID_FS_USAGE"'
```

**解法**：必须显式调用 `systemd-mount`，且选项走**命令行 `--options=`**：

```sh
systemd-mount --no-block --collect --options="noatime,uid=1000,gid=1000,fmask=0133,dmask=0022" \
    /dev/sda1 /run/media/sda1
```

本项目把"取 fstype → 算选项 → 调 systemd-mount"收进了 `odin-automount.sh`，
因为选项要按 fstype 分流，udev 命令行里拼不出来。

**两个附带的坑**：

- `--owner=` 不能用：`systemd-mount` 会对挂载点做 chown，在 vfat/exFAT 上会失败。
  改用挂载选项里的 `uid=/gid=/fmask/dmask`。
- 以普通 user 身份手动执行 `systemd-mount` 会报
  `Interactive authentication required`（polkit）。udev 的 RUN 是 root，
  产品路径不受影响；手工测试请加 `sudo -S`。

---

### 症状：U 盘插上没反应，但同型号的另一个盘能挂

**为什么**：不少 U 盘是"**整盘一个文件系统、无分区表**"的形态（superfloppy），
这类盘**没有 `ID_PART_ENTRY_NUMBER`**。规则里加分区号限制会把它们全部排除。

**定位**：

```sh
$ ssh odin 'udevadm info -q property -n /dev/sda1 | grep ID_PART'
```

**解法**：规则里不要限定 `ID_PART_ENTRY_NUMBER`。有分区表的盘同样适用：
整盘自身的 `ID_FS_USAGE` 不是 `filesystem`（不会被挂），各分区各自挂载。

---

### 症状：dnsmasq 日志显示 `dnsmasq started (pid N)`，但 `pgrep dnsmasq` 查不到进程

**为什么会这样**：三种不同的原因，症状完全一样：

1. **配置冲突**：`/etc/dnsmasq.d/` 里有 `bind-dynamic`，与命令行 `--bind-interfaces` 互斥
   ⇒ dnsmasq 读配置后直接退出：
   ```
   dnsmasq: cannot set --bind-interfaces and --bind-dynamic
   ```
   解法：gadget 的 dnsmasq 加 `--conf-file=/dev/null`（不读系统配置）。
2. **地址还在 tentative**：usb0 刚 `addr add` 完就绑定，地址还没就绪 ⇒ 起来后又退出。
   解法：启动前轮询等待 usb0 真的出现 `172.16.42.1`，最多 10s。
3. **系统 dnsmasq 抢端口**：它用 `bind-dynamic` 绑通配地址，占住 UDP 67。
   解法：mask 系统 `dnsmasq.service`（`apply-staging-fixes.sh` 已做）。

**定位**：

```sh
$ ssh odin 'journalctl -u odin-usb-gadget -b | tail -30'
$ ssh odin 'pgrep -a dnsmasq'
$ ssh odin 'ss -lunp | grep :67'
$ ssh odin 'tail -30 /var/log/odin-usb-role.log'
```

---

### 症状：PC 只拿到 169.254 自分配地址，或 DHCP 日志 `no address available`

**为什么会这样**：两个叠加的原因：

1. **gadget 每次重启重新生成随机 MAC** ⇒ dnsmasq 当成全新客户端，
   而地址池里唯一的地址被旧 MAC 的 12h 租约占住。
2. 想写死 MAC 时发现：configfs 的 `host_addr` / `dev_addr` 文件**总是存在**
   （内核填了随机值）⇒ `[ -f host_addr ] || echo $MAC > host_addr` 这个判断恒真，
   永远跳过写入。而且**绑定 UDC 之后这两个属性不可写**（Permission denied）。

**定位**：

```sh
$ ssh odin 'ip link show usb0'                    # 看 MAC 是不是每重启都变
$ ssh odin 'cat /var/lib/misc/dnsmasq.leases'     # 看旧租约是不是占满了池子
```

**解法（`odin-usb-role.sh` 已实现）**：

- 改用 **usb0 出现后 `ip link set usb0 address`** 设置 MAC（绑定后仍然有效）；
- 地址池改为**单地址** `172.16.42.2~172.16.42.2` —— 永远只连一台电脑，
  任何 MAC 都分到同一个 IP（这正是 postmarketOS 用 unudhcpd 的原因）；
- 每次重建 gadget 前 `rm -f /var/lib/misc/dnsmasq.leases`；租约 12h → 1h；
- `dnsmasq_running()` 不能只判断 pidfile 里的 pid 是否存在（pid 会被复用），
  要校验 `/proc/<pid>/cmdline` 含 `--interface=usb0`。

---

### 症状：`echo <udc> > /sys/kernel/config/usb_gadget/*/UDC` 返回 `-EBUSY`

**为什么**：configfs 会**保留旧的 `udc_name`**，不先解绑就直接写名字必然失败。

**解法**：先空后名：

```sh
echo "" > "$CFG/UDC"
echo "$udc" > "$CFG/UDC"
```

`odin-usb-role.sh` 里就是这样，且**任何分支都 exit 0** —— 失败只留日志，
由 30s 的 `odin-usb-gadget.timer` 看门狗重试。

---

### 症状：`/sys/class/usb_role/*/role` 不存在，手动切回 device 这条后门用不了

**定位**：

```sh
$ ssh odin 'find /sys -name role'
```

**实测**：输出为空，该 sysfs 文件根本不存在。

**解法**：回退请走"改 `/extlinux/extlinux.conf` 的 `default` 再重启"，或直接用 UART 串口。

---

### 症状：`fe80::1` 连不上（IPv6 兜底通道）

**为什么**：`odin-usb6-addr.service` 加的固定 `fe80::1` **没生效**。实际可用的是
内核由 MAC 自动推导的 **EUI-64 链路本地地址**。

**定位**：

```sh
# PC 上：用组播ping 看谁回应
ping6 -c 2 ff02::1%enXX
ip -6 neigh show dev enXX
```

**解法**：

```sh
# MAC 02:00:0d:1d:00:02 → fe80::67ff:fedb:feba
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no \
    user@fe80::67ff:fedb:feba%enXX
```

这条通道的价值：当 IPv4 DHCP 挂了导致 SSH 不通、因而**无法部署修复**的死锁时，
IPv6 链路本地地址仍然可达，用它连进去部署完再重启。本项目就是这么打破死锁的。

## 五、显示类

### 症状：`Failed to initialize panel: -22`，但驱动都绑定了、供电也成功

**为什么**：**面板初始化 DCS 命令发得太早。**

```
drivers/gpu/drm/msm/dsi/dsi_host.c:1710
    dsi_host_transfer():
        if (!msg || !msm_host->power_on) return -EINVAL;   ← 静默，不打印任何日志
```

而 `panel-ft8716.c` 原先只有 `prepare/unprepare/get_modes`（**没有 `enable`**），
初始化序列全在 `prepare` 发。实机时序证明 **panel prepare 发生在 DSI 主机上电之前**
⇒ 每条命令都 `-EINVAL`，日志里却只有一句 `Failed to initialize panel: -22`，极具迷惑性。

**定位**：

```sh
$ ssh odin 'dmesg | grep -E "Failed to initialize panel|dsi|mdp5_irq" | head -20'
$ ssh odin 'cat /sys/class/drm/card0-DSI-1/status; cat /sys/class/drm/card0-DSI-1/enabled'
$ ssh odin 'dmesg | grep -c -E "packet size is too big|cmd cannot fit into BLLP|Power on failed|failed to prepare host|create packet failed|cmd dma tx failed"'
# 上面 6 个判据全是 0 ⇒ 失败来自 dsi_host_transfer() 那个静默分支
```

**解法**：把初始化序列从 `.prepare` 挪到 **`.enable`**（`off()` 相应挪到 `.disable`），
`prepare` 只保留上电 + reset。固化为
`patches/0008-drm-panel-ft8716-send-init-sequence-in-enable-not-prepare.patch`。

**顺带**：`dsi_manager.c:244` 有注释 "Enable before preparing the panel, disable after
unpreparing" —— 顺序问题在这一类驱动上是通用的排查点。

---

### 症状：`/sys/class/backlight/` 是空的，背光设备压根没出现

**为什么**：WLED（`qcom,pmi8950-wled`）probe 失败，通常是
`qcom,ovp-millivolt` **取了驱动不认的档位值** ⇒ probe 返回 `-22`。

**定位**：

```sh
$ ssh odin 'dmesg | grep -iE "wled|backlight"'
$ ssh odin 'ls /sys/class/backlight/'
```

**解法**：`qcom,ovp-millivolt` 必须是驱动 `wled_ovp_values[]` 里列的合法档位之一。
当前 DTS 用的 **29600**（`0x73a0`）是实测可用的值：
`qcom,current-limit-microamp = <20000>`、`qcom,num-strings = <2>`。

相关的一个坑：ovp 过压处理会引发 `Unbalanced enable for IRQ 39` 警告。

---

### 症状：背光设备有了、值也不是 0，但屏幕看着像没亮

**为什么**：`default-brightness` 相对 `max-brightness`（4095）**太小**。
原来写 200 只有 5%，看起来跟没开背光一样。

**定位 / 解法**：

```sh
$ ssh odin 'cat /sys/class/backlight/*/{brightness,max_brightness}'
```

当前 DTS 用 **2048**（约 50%）。点亮后实测 `brightness = 4095/4095`。

---

### 症状：DRM 和 fb0 都起来了，但屏幕上只有背光、没有登录提示

**为什么**：`extlinux.conf` 的 `append` 行**少了 `console=tty0`** —— 它是控制台上屏的开关。
少了它，屏幕只有背光没有登录提示，**看起来跟"屏没点亮"一模一样**（实机踩过）。

**定位**：

```sh
$ ssh odin 'cat /proc/cmdline | tr " " "\n" | grep console'
$ ssh odin 'cat /sys/class/vtconsole/vtcon1/bind' 2>/dev/null
```

**解法**：`append` 行末尾加上 `console=tty0`。

---

### 症状：`no GPU device was found`，`/dev/kgsl*` 不存在

**为什么**：`msm8953.dtsi` 里 `gpu: gpu@1c00000` 默认 `status = "disabled"`，
而 **odin.dts 漏了启用它**。

**定位**：

```sh
$ ssh odin 'ls /dev/dri; dmesg | grep -iE "gpu|adreno|a530"'
```

**解法**：odin.dts 补 `&gpu { status = "okay"; }`。

**已知未解**：GPU 微码 `qcom/a530_pm4.fw` / `a530_pfp.fw` 不在 Debian 的任何包里
（只有 pmOS 的 `firmware-qcom-adreno-a530` 有），**缺它不影响显示**。

---

### 症状：`fb0: sys_imageblit: framebuffer is not in virtual address space`

影响 fbcon 显示质量，**不影响屏幕点亮**。已知未解，见 `WORKLOG.md` 待办。

## 六、设备树 / lk2nd 类

### 症状：SSH 能进，但屏幕不亮；`panel@0` 的 compatible 仍是占位值

**为什么**：lk2nd 的 QCDT 表里，`msm8953-smartisan-odin` 的 board-id 是 `<0x0b 0x01>`，
`msm8953-xiaomi-markw` 是 `<0x1000b 0x01>`；而 `VARIANT_MASK=0xff` ⇒
**两者 variant_id 都是 `0x0b`**，高位 `0x10` 只是 major。

按 `dev_tree.h:81-112` 的匹配位序，两者都带 `SUBTYPE_EXACT_MATCH`（BIT 26）；
`dev_tree.c:599-608` 的规则是**位图相等时再比 major，major 大的赢** ⇒
**markw 以 major 精确匹配胜出**。lk2nd 选中 markw ⇒
占位 compatible `smartisan,odin-panel` **不会被替换** ⇒ 内核无面板驱动匹配 ⇒ 无屏。

**定位**（两个都要看）：

```sh
# 1) fastboot 下看 lk2nd 实际选中了谁
fastboot getvar all 2>&1 | grep -iE "lk2nd:|max-download-size"

# 2) 系统内看占位 compatible 有没有被替换
$ ssh odin 'tr "\000" " " < /sys/firmware/devicetree/base/compatible; echo'
$ ssh odin 'tr "\000" " " < /sys/firmware/devicetree/base/soc@0/display-subsystem@1a00000/dsi@1a94000/panel@0/compatible'
#   仍含 smartisan,odin-panel  ⇒ lk2nd 没选中 odin ⇒ 无屏
#   变成 smartisan,odin-ft8716 ⇒ 命中 ✅
```

**解法（两条路，互为保险）**：

1. **刷精简版 lk2nd**（`lk2nd-nomarkw.img`）。删掉 markw 后，
   odin 成为唯一带 `SUBTYPE_EXACT` 的候选，稳赢 ——
   已由 `lk2nd/0004` 补丁固化，并在真机上实机验证。
2. **用面板写死的 DTB**（`*-ft8716*.dtb`）。面板是否点亮与 lk2nd 选中谁无关，
   排障面小很多。**当前发布默认走这条路**（见 [02-刷入指南.md § 六](02-刷入指南.md)）。

---

### 症状：改了 `extlinux.conf` 的 `fdt` 却不生效；或启动时报找不到 markw 的 DTB

**为什么**：lk2nd 的 extlinux 解析里 **`fdt` 与 `fdtdir` 互斥**
（`lk2nd/boot/extlinux.c:394-434`）：label 里只要有 `fdtdir`，lk2nd 就用
`lk2nd,dtb-files` 拼路径并**覆盖** `fdt`。

**定位**：

```sh
$ ssh odin 'cat /proc/device-tree/model; echo'
```

**解法**：两个 label 都只写显式 `fdt`，**绝不能用 `fdtdir`**。

---

### 症状：`dtc` 报 `Properties must precede subnodes`

**为什么**：dtc 要求属性写在 `/delete-node/` 之前。

**附带坑**：内核自带的 `scripts/dtc/dtc` 是 **aarch64-musl** 二进制，
在 macOS 宿主和 debian 容器上都跑不了（exec format / 缺 musl loader）。
用发行版的 `device-tree-compiler` 包。

## 七、系统类

### 症状：能 ping 通 IP，但域名解析不了

**为什么**：路由器广播的 DNS **根本不应答**（实测那台广播 `192.168.3.1`，
但不响应 UDP 53）。

**定位**：

```sh
$ ssh odin 'resolvectl status; nmcli -t -f IP4.DNS con show <连接名>'
$ ssh odin 'dig +time=2 +tries=1 @192.168.3.1 example.com'    # 直接问那台 DNS
```

**解法**：在连接级别覆盖掉自动下发的 DNS：

```sh
nmcli con modify <连接名> ipv4.ignore-auto-dns yes ipv4.dns "1.1.1.1,8.8.8.8"
nmcli con up <连接名>
```

`systemd-resolved` 已装，它提供"按顺序尝试后续服务器"的能力，作为兜底。

---

### 症状：`apt update` 报 `Release file ... is not valid yet`

**为什么**：设备**没有 RTC**，开机时钟回到很远以前，apt 认为 Release 文件"还没生效"。

**定位 / 解法**：

```sh
$ ssh odin 'timedatectl status; date'
$ ssh odin 'systemctl is-active systemd-timesyncd'
```

`systemd-timesyncd` 已装并启用，联网后自动校时。刚开机还没同步完时先等一下再 `apt update`。
（dnsmasq 日志时间戳显示 Apr 27 之类，就是系统时钟未同步，**非故障**。）

---

### 症状：`modprobe: command not found` / `ping: command not found`

**为什么**：`debootstrap --variant=minbase` 只装 required 优先级的包，
`kmod`（提供 `modprobe`）和 `iputils-ping` 都不在其中。

**定位 / 解法**：

```sh
$ ssh odin 'command -v modprobe ping dig curl tcpdump'
```

`setup-rootfs.sh` 里已按"正常 Debian 服务器"标准把网络工具装齐
（`kmod` / `iputils-ping` / `curl` / `wget` / `bind9-dnsutils` / `net-tools` /
`traceroute` / `tcpdump` / `iperf3` / `ethtool` / `mtr-tiny`）。

**注意 `/etc/modules-load.d` 不是必然存在**：它是 kmod 提供的，minbase 装完没有，
写文件前要 `mkdir -p`。

---

### 症状：WiFi 完全没有 `wlan0`

**定位**：

```sh
$ ssh odin 'ls /sys/class/net/; rfkill list'
$ ssh odin 'journalctl -u odin-wlan-fw -b; cat /var/log/odin-wlan-fw.log'
$ ssh odin 'ls /lib/firmware/wcnss.* /lib/firmware/wlan/prima/'
```

**为什么**：`msm8953.dtsi` 里 `wcnss: remoteproc@a204000` 默认 `status = "disabled"`
（已在 odin DTS 启用）；另外 wcn36xx 要的**固件与校准数据不在任何 Debian 包里**
—— 由 `odin-wlan-fw.service` 开机从 **modem 分区的 `/image/`**（固件）与
**persist 分区**（板级校准数据 `WCNSS_qcom_wlan_nv.bin`）现取。

**实测背书**：删空 `/lib/firmware/wcnss.*` 与 `wlan/prima/` 后跑 `odin-wlan-fw.sh`
→ 退出码 0，10 个固件 + 2 个校准数据全部恢复，与删除前的备份**逐字节一致**。

## 八、构建类

| 症状 | 为什么 | 解法 |
|---|---|---|
| `rules.mk:28: recipe commences before first target` | Makefile 里**把注释插进了 `\` 续行块中间**，注释行打断续行链，后续以 tab 开头的行被当成 recipe | 注释写在块**之前** |
| CI 上编译成功，最后 `cp` 报 `No such file or directory` | 脚本 `cd` 进内核树后，`$OUT` 相对路径指到别处 | 四个脚本统一 `OUT=$(cd "$OUT" && pwd)` 转绝对路径 |
| `upload-pack: not our ref <sha>` | 钉的 SHA 不是上游提交（钉成本地已打补丁的 HEAD 了） | 钉上游基线；见 [01-复现构建.md § 一](01-复现构建.md) |
| `git fetch --depth 1 origin <sha>` 被拒 | GitHub 只允许取 ref 能到达的提交，基线被 master 甩开后不是 tip | `fetch-kernel.sh` 三级回退，见 [01](01-复现构建.md) |
| `gzip: stdin: not in gzip format` | `LK2ND_VER: 19.0` 在 YAML 里被解析成**浮点数 19**，URL 404 | YAML 里必须加引号：`LK2ND_VER: "23.1"` |
| lk2nd 补丁 `Hunk #1 FAILED` | 版本不对：19.x 设备表条目与行尾空白不同，21.0 改过名也缺条目 | 钉 tag `23.1`，见 [01](01-复现构建.md) |
| `patch: No such file or directory` 报一个带星号的文件名 | glob 写在引号里不展开：`"$REPO/lk2nd/0004-*.patch"` | 写成 `"$REPO"/lk2nd/0004-*.patch` |
| CI 日志只有最后几行，编译过程看不到 | 长命令的输出被缓冲 | 改成 `if ! cmd 2>&1 \| tee /tmp/x.log; then ...`（已改） |
| `bash: ./pack_initramfs.sh: Permission denied` / exit 126 | 脚本在 git 里是 100644，没有可执行位 | 显式 `bash tools/pack_initramfs.sh ...` |
| initramfs 的 `bin/` 在 CI 里整个不存在 | git 不跟踪空目录；`prepare-public-repo.sh` 会把 busybox 当大 blob、把符号链接按 `file(1)` 判定当二进制一并摘掉 | 骨架目录在 `build-rootfs.sh` 里重建；applet 名单走 `dist/build/initramfs-applets.txt` 文本文件 |
| `gh: fatal: not a git repository` | `publish` job 没有 `actions/checkout`，`gh` 推断不出仓库 | `gh release upload "$TAG" out/* -R "${{ github.repository }}"` |
| 一次发布触发了两个 run | 把 `published` 也写进了触发类型（GitHub 发布时会同时发两个事件） | 只用 `prereleased` + `released` |

**QEMU 的能力边界（别在这儿浪费时间）**：镜像内核的 `.config` 没有
`VIRTIO_PCI` / `VIRTIO_MMIO` ⇒ virt 机器上没有块设备/网卡，**镜像内核跑不了 QEMU**；
QEMU 用的另一个内核又不支持 exFAT。所以 **QEMU 只能验用户态**，
内核 / 硬件相关的项必须真机验证。

## 九、其它实测小抄

| 场景 | 命令 / 结论 |
|---|---|
| 手机是不是接在 Type-C Hub 上（会导致诊断误判） | `system_profiler SPUSBDataType \| grep -iE "Hub\|Android"`；刷机务必**直连** |
| fastboot 下一次性拿全信息 | `fastboot getvar all` → `lk2nd:version/model/compatible/panel`、`max-download-size`、`partition-size:userdata` |
| `lk2nd:panel` 有值 | 说明**原厂 aboot 确实透传了面板名**（经 cmdline 到 lk2nd） |
| 判断设备当前状态 | SSH 通 = 系统运行中；`fastboot devices` 有 = fastboot；都没有且 3 分钟无响应 = 掉进 9008(EDL) |
| 设备从系统内进不了 fastboot | 真机无 adbd，`/sys/kernel/reboot/mode` 只收 `cold`/`warm`/`hard`；靠"改名 `extlinux.conf` 让 lk2nd 停 fastboot"，见 [02](02-刷入指南.md) |
| 发布前的安全红线 | 镜像**不能**带 SSH 主机私钥（`git grep "BEGIN ... PRIVATE KEY"` 扫一遍）；由 `odin-ssh-hostkeys.service` 首启生成 |
| 公开副本自检 | `tools/prepare-public-repo.sh` 跑完会验证：残留二进制 0、>250KB 文件 0、敏感串 0、私钥 0 |
