# 三、系统使用（WiFi / 网络 / 存储 / 救援通道）

假定你已经刷完并拿到了 SSH（见 [02-刷入指南.md](02-刷入指南.md)）：

```sh
ssh user@172.16.42.1      # 密码 user，该用户已在 sudo 组
```

用户态组件的**源码在 `dist/build/rootfs/`**，由 `dist/build/apply-staging-fixes.sh`
幂等部署。要改请改那里再重跑脚本，不要直接改镜像内的文件，否则下次重建会丢。

| 文件 | 作用 |
|---|---|
| `usr/local/sbin/odin-usb-role.sh` | USB 角色切换唯一入口：幂等、先空后名、任何分支 exit 0、支持 `--dry-run` |

## 一、WiFi

用 `nmcli` —— 它本身就是交互式命令行，不需要改任何配置文件。

```sh
nmcli dev wifi list                              # 扫描周围网络
nmcli dev wifi connect <SSID> password <密码>     # 连接（自动建一条持久连接）
nmcli dev status                                 # 设备状态
nmcli con show                                   # 已保存的连接
nmcli con up <连接名>                             # 启用
nmcli con down <连接名>                           # 断开
nmcli con delete <连接名>                         # 删除
nmtui                                            # 文本图形界面（不想记命令就用它）
```

连上之后：

```sh
nmcli dev status              # wlan0 应为 connected
ip -4 -o addr show wlan0
ping -c 3 deb.debian.org
```

> 路由：默认走 `wlan0`（metric 600），`172.16.42.0/24` 仍走 `usb0`
> ⇒ **连 WiFi 不会影响 USB 上的 SSH 通道**。

### WiFi 固件与校准数据是怎么来的

wcn36xx 驱动要两样东西，**都不在任何 Debian 软件包里**，也不该进版本库
（二进制 + 机器相关）：

| 数据 | 来源分区 | 落点 |
|---|---|---|
| WCNSS 无线固件 `wcnss.mdt` + `wcnss.b00/b01/b02/b04/b06/b09~b12` | **modem** 分区的 `/image/` | `/lib/firmware/` |
| 板级射频校准数据 `WCNSS_qcom_wlan_nv.bin`（+ `WCNSS_wlan_dictionary.dat`） | **persist** 分区根目录 | `/lib/firmware/wlan/prima/` |

`WCNSS_qcom_wlan_nv.bin` 是**每台机器都不一样**的射频校准数据，原厂放在 persist 分区；
路径由内核 `wcn36xx.h` 的 `WLAN_NV_FILE` 定死。实测核对过：`modem:/image/wcnss.*`
与手工预置的固件十个文件 md5 全部一致，所以"开机现取"与"预置"完全等价，
还省掉了往仓库里塞二进制。

**关键在时序，不在取不取得到。** 内核的 `qcom_wcnss_pil`（remoteproc）在开机约
**10 秒**时就会索取 `wcnss.mdt`，那时 systemd 刚起来，任何 late service 都还没跑
（实测 persist 分区要到 25.9 秒才被挂载）。差这十几秒，remoteproc 就停在 `offline`，
之后补上文件它也不会自己重试。

所以这件事放在 **initramfs 里、`switch_root` 之前**：
`dist/build/initramfs/init` 会先调 `odin-wlan-fw.sh /mnt --check`，只有确实缺文件时
才把根临时挂为 rw、取完 `sync` 后立刻挂回 ro。绝大多数开机根全程只读。

**取不到一律不致命** —— 最坏结果只是没有 WiFi，绝不会拖挂启动。
日志看 `/var/log/odin-wlan-fw.log`（initramfs 阶段的消息同时打到控制台）。
固件丢了不用手工补，**重启一次就会重新取**。

另：`wcn36xx` / `qcom_wcnss_pil` 两个模块写进了 `/etc/modules-load.d/odin-wlan.conf`，
由 `systemd-modules-load` 在 `basic.target` 之前加载 —— 那时固件已在位，
所以第一次加载就成功。

> 想补其它外设的固件，照同一套路子做，完整规范见 **reports/021**。

## 二、网络管理

### 装了哪些工具

按"正常 Debian 服务器"的标准装齐：

```
iputils-ping   curl   wget   bind9-dnsutils（dig/nslookup）   net-tools（ifconfig/route）
traceroute     tcpdump   iperf3   ethtool   mtr-tiny
network-manager   wpasupplicant   iw   wireless-tools   rfkill
firmware-atheros   systemd-resolved   systemd-timesyncd   nftables
```

`NetworkManager-wait-online.service` 关了（首启已有扩容 / 日志压力，
不想再被 90s 超时拖慢）。

### 关于蜂窝网络（移动数据）

当前镜像里 **`ModemManager` 是 mask 的**，所以开箱没有移动数据。
但请注意——**这不是因为机器没有基带**：

> `setup-rootfs.sh` 里那句注释「本设备无蜂窝基带」是**错的**，已核实。
> `reports/016` 在该机上（pmOS 系统）实测：
> ```
> remoteproc0  4080000.remoteproc (qcom-q6v5-mss)  firmware = mba.mbn   ← 基带 MSS，running
> qrtr-lookup → 16 个 QMI 服务（NAS / Voice / LTE / UIMRMT / Data Port Mapper …）
> 数据通道设备：rmnet_ipa0、ipa_lan0；ipa 模块已加载
> 工具链齐备：qmicli / qmi-network / qrtr-lookup / qrtr-cfg
> ```
> 即**硬件基带是起来的**。当时只是没装 ModemManager。

本镜像 mask 它的真实原因是：**我们这套 6.19 内核 + odin DTB 上的蜂窝链路尚未验证**，
留着它只会徒增启动开销、还会去扫串口。**不要因为"要用移动数据"就随手 unmask** ——
在 MSS remoteproc / qrtr / rmnet 那条链没跑通之前，unmask 也拿不到数据连接，
反而多一个启动耗时点。

要确认这条路在本镜像上能不能走通，见 `reports/016 § 2.10`
（以及蜂窝可行性调研的结论）。真要试的话，先验证最小前提：

```sh
ls /sys/class/remoteproc/          # remoteproc0/1/2 是否都在
ls /dev/qrtr*  2>/dev/null         # qrtr 节点
command -v qmicli qrtr-lookup      # 工具链（本镜像未装，需 apt）
ls /sys/class/net/                 # 有没有 rmnet_* / ipa_lan0
```

> ⚠️ 上面这些工具本镜像**没有预装**。要装得先联网（USB 网络或 WiFi 都行），
> 且要留意开机时钟尚未校正导致的 apt 问题（见本节坑 2）。

### 坑 1：路由器广播的 DNS 可能根本不应答

**现象**：能 `ping` 通 IP，但域名解析不了。

实测那台路由器广播 DNS `192.168.3.1`，而它根本不响应 UDP 53。
`systemd-resolved` 提供了"按顺序尝试后续服务器"的能力，但更直接的修法是
在连接级别覆盖掉自动下发的 DNS：

```sh
nmcli con modify <连接名> ipv4.ignore-auto-dns yes ipv4.dns "1.1.1.1,8.8.8.8"
nmcli con up <连接名>
```

想看当前连接实际拿到的 DNS：

```sh
nmcli -t -f IP4.DNS con show <连接名>
resolvectl status
```

### 坑 2：开机时钟尚未校正，apt 拒绝 Release 文件

设备**有** RTC（PMIC 内置的 `rtc-pm8xxx`，`/dev/rtc0` 存在），但下面三条叠加，
导致开机后系统时钟仍然是错的，要等联网校时：

1. **RTC 里是无效值**：`hwclock -r -u` 读出 `1970-04-12`，从未被正确设置过
2. **RTC 写不进去**：`hwclock -w -u` 报
   `ioctl(RTC_SET_TIME) to /dev/rtc0 to set the time failed: No such device`
   —— 读是正常的（秒数在走），只是写入路径在这块硬件上不工作，
   所以"把正确时间写回 RTC 让它记住"这条路走不通
3. **内核没开 `CONFIG_RTC_HCTOSYS`**：启动时不会从 RTC 恢复系统时钟

于是刚开机、NTP 还没同步完时，`apt update` 会这样抱怨：

```
E: Release file for .../bookworm/InRelease is not valid yet
   (invalid for another 74d 14h 21min 30s).
```

判别与定位：

```sh
$ ssh odin 'date -u; hwclock -r -u; systemctl is-active systemd-timesyncd'
```

- `date` 是错的、`systemd-timesyncd` active → 等它同步完再 `apt update`
- 想确认 RTC 到底在不在：`ls /dev/rtc0` 与 `dmesg | grep rtc`

**当前对策**：`systemd-timesyncd` 已装并启用，联网后自动校时。
代价只是"刚开机到同步完成之间"以及"完全离线时"这段时间不能用 apt；
RTC 本身无法用来跨关机保持时间，因此**离线场景下的时间准确性没有保证**。

> 顺带一个容易误判的现象：`dnsmasq` 等服务的日志时间戳看起来"很旧"
> （比如显示 4 月而实际是 8 月），那是开机时钟还没校正留下的，不是故障。

### 排障常用

## 三、存储管理（U 盘 / OTG）

**插上即自动挂载**到 `/run/media/<设备名>`，不用手动 `mount`，也没装 `udisks2`：

```
U 盘插入 → udev(99-odin-automount.rules) → odin-automount.sh
        → odin-mount-opts.sh 按 fstype 分流选项
        → systemd-mount --options=... → /run/media/<设备名>
        （systemd .mount 单元，--collect 在拔盘时自动回收，因此无需 remove 规则）
```

只处理 `ID_BUS=usb` 的设备（内部 eMMC / SD 天然排除），
**有无分区表都支持**（不少 U 盘是"整盘一个文件系统"，加分区号限制会把它们全排除）。

| 文件系统 | 用户可直接写 | 中文文件名 | 备注 |
|---|---|:---:|---|
| **exFAT**（推荐） | ✅ | ✅ | 内核模块 `exfat.ko` 已随镜像，挂载时自动加载 |
| NTFS | ✅ | ✅ | `NTFS3` 编进内核；`ntfs-3g`(FUSE) 与 `ntfsfix` 也在 |
| FAT32 / vfat | ✅ | ❌ **会乱码** | 见下 |
| ext4 / btrfs / xfs / f2fs | ❌ 需 `sudo` | ✅ | POSIX 权限，根目录属主是格式化时的用户；`sudo chown` 一次即可持久生效 |

### ⚠️ FAT32 中文名会乱码

内核**未编 `CONFIG_NLS_UTF8`**（这是明确的产品决策：不为 FAT32 中文重编内核模块），
所以 vfat 默认按 `iso8859-1` 解释文件名 ⇒ 中文名会乱码。

exFAT / NTFS3 走内核内建的 UTF-16 转换（`fs/exfat/super.c:691-697`，不调用
`load_nls`），不依赖 `nls_utf8`，**中文正常**。

⇒ **需要中文名的盘，请格式化成 exFAT 或 NTFS。**

### 排障

```sh
ls -l /run/media/                                    # 已挂载了什么
tail -20 /var/log/odin-automount.log                 # 自动挂载的决策日志
udevadm info -q property -n /dev/sda1 | grep -E "ID_BUS|ID_FS_TYPE|ID_FS_USAGE"
systemctl list-units 'run-media-*.mount'             # systemd 挂载单元
cat /usr/local/sbin/odin-mount-opts.sh               # 各 fstype 的选项是怎么算的
```

> 挂载选项必须由 `systemd-mount --options=` 显式传：bookworm 的 systemd 252 里
> PID 1 **不读**任何 `SYSTEMD_MOUNT_*` 属性，`systemd-mount` 也**不读**
> `SYSTEMD_MOUNT_OPTIONS` 环境变量。所以光写 `TAG+="systemd"` 不会挂载，
> 且选项必须走命令行 —— 这也是要有 `odin-automount.sh` 这层包装的原因。

> OTG 只在 `l0`（完整版 DTB）下可用。首刷默认的 `l0-safe` 把 USB 固定为 device，
> **完全没有 OTG host**。切换方法见 [02-刷入指南.md § 七](02-刷入指南.md)。

## 四、USB 救援通道（命脉）

### 地址约定

| 侧 | 地址 |
|---|---|
| 设备（`usb0`） | **`172.16.42.1`** |
| PC | **`172.16.42.2`** |

设备侧跑 dnsmasq，**地址池只有 `172.16.42.2` 一个地址**（永远只连一台电脑，
任何 MAC 都分到同一个 IP）。PC 拿到地址后：

```sh
ssh user@172.16.42.1
```

### ⚠️ 不要删 `/etc/NetworkManager/conf.d/99-odin-usb0.conf`

```ini
[keyfile]
unmanaged-devices=interface-name:usb0
```

`usb0` 由 `odin-usb-gadget.service` 静态配置（`172.16.42.1` + dnsmasq 给 PC
`172.16.42.2`）。Debian 里 `/etc/network/interfaces` 不存在 ⇒ 默认的
`[ifupdown] managed=false` 保护不到 usb0 ⇒ **NM 会把它当普通以太网自动连接，
清掉 `172.16.42.1`，SSH 立刻失联**（无屏设备将只剩 UART 可用）。

验证：`nmcli device status` 里 `usb0` 应显示 **`unmanaged`**。

同样的道理，系统的 `dnsmasq.service` 已被 mask —— 它用 `bind-dynamic` 绑通配地址、
占住 UDP 67，会导致 gadget 的 dnsmasq 起不来 ⇒ PC 拿不到 IP。

### 自愈机制

`odin-usb-role.sh` 是角色切换的唯一入口：**幂等、先空后名、任何分支 exit 0**
（不留 failed 单元）。绑 UDC 前必须先 `echo ""` 解绑，否则 configfs 保留旧的
`udc_name`，直接写名字必返回 `-EBUSY`。

三层触发保证"拔掉再插回来 USB 网络会恢复"：

1. `odin-usb-gadget.service`（开机 oneshot）
2. `odin-usb-gadget.timer` —— **每 30s 跑一次的自愈看门狗**
3. `/etc/udev/rules.d/99-odin-usb-role.rules` —— 监听 UDC add/remove 与 typec change

（udev 的 RUN 有 60s 超时上限，脚本内 UDC 等待窗口默认 20s，长等待交给看门狗。）

排障：

```sh
journalctl -u odin-usb-gadget -f
tail -20 /var/log/odin-usb-role.log
ls /sys/class/udc
ip -4 -o addr show usb0
```

> **已知的回退缺口**：`echo device > /sys/class/usb_role/*/role` 这条手动强制切回
> device 的手段不可用 —— 实测 `find /sys -name role` 结果为空，该 sysfs 文件根本不存在。
> 要回退请走"改 `extlinux.conf` 的 `default` 再重启"，或直接用 UART。

### SSH 进不去时的三条通道

| 通道 | 触发条件 | 用法 |
|---|---|---|
| **initramfs telnet** | 启动早期每 ~5 秒自动开一次；找不到根分区时**常驻** | 主机 `telnet 172.16.42.1`（root shell，无密码） |
| 强制驻留 telnet | 在 `extlinux.conf` 的 append 行加 `odin.telnet=always` | 停在 initramfs shell 不进系统 |
| **UART 串口** | 始终可用 | `ttyMSM0` @ 115200，系统内已启用 `serial-getty`（user 登录） |

telnet 内常用：

```sh
mount -t ext4 /dev/mmcblk0pNN /mnt   # 手动挂根检查
cat /proc/cmdline; findfs LABEL=pmOS_root
```

## 五、几个系统级约定

| 项 | 值 / 说明 |
|---|---|
| 主机名 | `odin` |
| 用户 | `user` / 密码 `user`，在 `sudo` 组；`root` 密码登录已锁 |
| SSH | 密码登录已开，`PermitRootLogin no` |
| **主机密钥** | **镜像里不带**，由 `odin-ssh-hostkeys.service` 首启 `ssh-keygen -A` 生成 —— 公开发布的镜像绝不能带一把固定私钥 |

> 扩容服务无论成败都会自禁用并落标记（`/var/lib/odin-resize-done`）——
> 否则每次开机都会挂一个 failed 单元。日志里有 `No reserved GDT blocks, can't resize`
> 之类的 EPERM，说明镜像特性集被改坏了，得用 `tools/build-image.sh` 重建。

## 六、硬件视频编解码（venus / FFmpeg）

ODIN 的 msm8953 里有一颗 Qualcomm **Venus**（HFI 3xx）视频编解码硬核。
主线内核的 `qcom-venus` 驱动把它暴露成 **两个 V4L2 M2M 设备**
（decoder 与 encoder 各一个），FFmpeg 通过 `-c:v *_v4l2m2m` 直接调用。

### 能力（原厂 `media_codecs.xml` 的声明，见 reports/027）

| 方向 | 格式与最高规格 |
|---|---|
| 解码 | 4K30 hevc / h264 / vp8 / vp9；1080p mpeg4 / wmv / vc1 / divx / mpeg2；864x480 h263；720x480 divx311 |
| 编码 | 4K30 hevc / h264；1080p30 mpeg4 / vp8；864x480 h263 |

安全（DRM）路径组件（`OMX.qcom.video.decoder.avc.secure` 那一类）主线不用，忽略。

### 怎么用

```sh
# 编码：用 venus 的 H.264 编码器压一段
ffmpeg -y -f lavfi -i testsrc2=size=1280x720:rate=30:duration=10 \
       -pix_fmt nv12 -c:v h264_v4l2m2m -b:v 4M out.mp4

# 解码
ffmpeg -c:v h264_v4l2m2m -i in.mp4 -f rawvideo -pix_fmt nv12 out.raw

# 硬解 → 硬编转码
ffmpeg -c:v hevc_v4l2m2m -i in.mkv -c:v h264_v4l2m2m -b:v 4M out.mp4
```

需要的包：`ffmpeg`、`v4l-utils`（已随镜像装好）。

> ⚠️ **不要装 `mesa-venus`**。那是 VirtIO-GPU 的 Vulkan 驱动（给虚拟机用的），
> 与裸机的 qcom venus **同名不同物**。

### 固件从哪来

venus 固件（`venus.mdt` + `venus.b00`~`b04`）不在任何 Debian 包里，
取自**原厂 modem 分区**的 `/image/` 目录 —— 和 WiFi 的 `wcnss.*` 是同一处、
同一套路（详见 `reports/021` 与 `reports/029`）：

- **正常路径**：initramfs 在 `switch_root` **之前**备好
  （`odin-venus-fw.sh`）。venus 是 platform 驱动，开机早期就被 udev 加载并立刻
  `request_firmware()`，晚了就不会自己重试。
- **兜底**：`odin-venus-fw.service`（用户态），取完固件再 `modprobe -r` + `modprobe`
  重载 venus 模块 —— venus 是模块，这一步能补救。

手动触发一次：

```sh
sudo /usr/local/sbin/odin-venus-fw.sh
sudo dmesg | grep -i venus
```

### 排障

```sh
v4l2-ctl --list-devices                     # 哪个 /dev/videoX 是 venus
v4l2-ctl -d /dev/videoN --list-formats      # 它到底支持哪些格式
```

一步到位的体检脚本（看固件 / 模块 / 设备 / 格式 + 真跑一次编码再解回来）：

```sh
sudo odin-video-check.sh            # 完整体检
sudo odin-video-check.sh --quick    # 只看静态项，不跑编解码
```

排障时的两个要点：

1. **`lsmod` 里有 `venus_core` 不代表可用** —— probe 失败时模块照样在。
   判据是 `/dev/video*` 里有没有支持压缩格式的设备。
2. 内核日志里会有一条
   `truncated property 0x1007: need 20 bytes, 12 left`
   —— **这条是正常的**。本机 venus 固件回的能力表末尾一条被截断了 8 字节
   （见 `reports/029`），驱动按"属性表到此结束"处理，前面的能力全部有效。
   真正要警惕的是 `probe with driver qcom-venus failed`。
