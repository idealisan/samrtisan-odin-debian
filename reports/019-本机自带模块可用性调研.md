## 〇、先读这一段：五句话结论

1. **这台机器的硬件远比"当前能用"的丰富。** 22 个模块里，真正"主线完全没有驱动"的只有 8~9 项；有 6 项属于**主线驱动现成、只是我们没接线**（DTS 没启用 / CONFIG 没开）。
2. **又一个"上游默认 disabled"的坑：`&lpass`（ADSP）在 `msm8953.dtsi` 里是 `status = "disabled"`**，我们 DTS 没启用 ⇒ ADSP 不跑 ⇒ 整条音频链路（APR / Q6AFE / Q6ASM / 编解码）全部不加载。这是"没有声音"的根因，不是硬件问题。`&mpss`（基带）同样是默认 disabled。
3. **`reports/016` 里"光感/地磁/相机不可用"那几条不能沿用。** 016 是在**跑 markw 回落 DTB** 的环境下采集的，那几条反映的是红米 4 高配的料单，不是本机的。本报告全部重查。
4. **"pmOS 上能用"推不出"主线能用"。** pmOS 的 msm8953 内核是 `msm8953-mainline/linux` **fork**，带一批从未合入主线的补丁。有 6 个模块卡在这个差距上（详见 §五）。
5. **最难啃的几块（指纹、FM、地磁、光感）建议明确砍掉。** 它们要么主线根本没有对应设备类别（指纹），要么对"把手机当小服务器用"这个目标没有价值。

## 四、"需接线"的 6 项：具体怎么接（按可操作性排序）

### 4.1 触摸屏 —— 强烈建议第一个做（最有价值的发现）

**先说结论：`reports/016` §2.5 的"内核无 FTS 驱动"这条对 6.19 不成立。**

- 主线 6.19 `drivers/input/touchscreen/edt-ft5x06.c:1516-1529` 的 compatible 表里有完整 FocalTech 家族：`focaltech,ft5426` / `ft5452` / `ft6236` / `ft8201` / **`ft8716`** / **`ft8719`**
- `CONFIG_TOUCHSCREEN_EDT_FT5X06=m` **已开**
- 主线 DTS 先例：`sdm845-xiaomi-beryllium-ebbg.dts:21` 用 `focaltech,ft8719`

**硬件（原厂 DTS `stock.dts:6367`，`i2c@78b7000` = 主线 `&i2c_3`）：**
```
focaltech@38 { compatible = "focaltech,fts"; reg = <0x38>;
    focaltech,reset-gpio = <GPIO 64>; focaltech,irq-gpio = <GPIO 65>;
    focaltech,max-touch-number = <10>;
    focaltech,display-coords = <0 0 1080 1920>; };      // 0x438 x 0x780
novatek@01  { compatible = "novatek,NVT-ts"; reg = <0x01>;
    novatek,reset-gpio = <GPIO 64>; novatek,irq-gpio = <GPIO 65>; };
```

**★ 同 SoC 主线先例：`msm8953-xiaomi-daisy.dts:134-152`（小米 Mi A2 Lite，同一颗 msm8953）**
```
&i2c_3 {
	status = "okay";

	touchscreen@38 {
		compatible = "edt,edt-ft5406";
		reg = <0x38>;

		interrupt-parent = <&tlmm>;
		interrupts = <65 IRQ_TYPE_EDGE_FALLING>;

		reset-gpios = <&tlmm 64 GPIO_ACTIVE_LOW>;

		vcc-supply = <&pm8953_l10>;

		touchscreen-size-x = <1080>;
		touchscreen-size-y = <2280>;
	};
};
```

**逐项对照：**

| 项 | daisy（主线先例） | ODIN 原厂 DTS | 一致? |
|---|---|---|---|
| 总线 | `&i2c_3` = 78b7000 | `i2c@78b7000` | ✅ |
| I2C 地址 | `0x38` | `0x38` | ✅ |
| reset GPIO | `tlmm 64` | GPIO 64 | ✅ **同一个脚** |
| irq GPIO | `tlmm 65` | GPIO 65 | ✅ **同一个脚** |
| 供电 | `pm8953_l10` | `vcc_i2c-supply`（未展开查是哪个 LDO） | 待定 |
| 横分辨率 | 1080 | 1080 | ✅ |
| 纵分辨率 | 2280 | **1920** | ❌（我们是 1080×1920，framebuffer 亦证实） |

**四条硬参数全部对上**，说明小米和锤子在这颗 SoC 上的触摸部分用的是同一种硬件接法。这不是"参考"，是几乎可以直接抄的配置。

**接线方案：**
```
&i2c_3 {
	status = "okay";

	touchscreen@38 {
		compatible = "focaltech,ft8716", "focaltech,ft8719", "edt,edt-ft5406";
		reg = <0x38>;

		interrupt-parent = <&tlmm>;
		interrupts = <65 IRQ_TYPE_EDGE_FALLING>;

		reset-gpios = <&tlmm 64 GPIO_ACTIVE_LOW>;

		vcc-supply = <&pm8953_l10>;

		touchscreen-size-x = <1080>;
		touchscreen-size-y = <1920>;
	};
};
```
要点：
- 写多个 compatible 让内核依次匹配，**是 DT 的标准做法，不是 hack**
- `pm8953_l10` 是我们 DTS 里已有定义的 LDO（2.8 V），跟 daisy 一致。供电对不上会 probe 失败，届时需回查原厂 DTS 的 `vcc_i2c-supply` 指向哪个 LDO
- **如果本机面板是 NT36672 而不是 FT8716**，触摸可能是 Novatek —— 需改用 `novatek,nt36672a-ts` 并开 `CONFIG_TOUCHSCREEN_NOVATEK_NVT_TS`
- **还需要在 `&tlmm` 里补 GPIO 64/65 的 pinctrl 状态**（当前 `&tlmm` 只有 gpio85 / gpio61 / gpio24 / gpio38）
- 为什么会有两种候选：`reports/009` 查明原厂 LK 的面板 GPIO 识别逻辑是 `g91&&g92 → NT36672`、`g91&&!g92 → FT8716`、否则 `SHARP_FT8716` 兜底。**本机面板是 NT36672 还是 FT8716 取决于两颗 GPIO，逐台不同**

### 4.2 加速度计 + 陀螺仪（BMI120）—— 最稳的一项

**硬件**：Bosch BMI120，在 **GPIO 14/15 的软件 I2C（i2c-gpio）** 上，地址 0x68。

**第一手证据**：本机跑 pmOS 时 `iio:device1 = bmi120`（`05-hardware-full.txt:144`）、`0-0068 bmi120`（`:129`）、总线 `i2c-0 = i2c-gpio`（`:133`）。**驱动会校验 chip ID**（`bmi160_core.c:703 bmi160_check_chip_id`，只接受 `0xD3`=BMI120 / `0xD1`=BMI160），所以是真芯片在应答，不是误判。

**CONFIG 已全部就绪**：`CONFIG_BMI160_I2C=m`、`CONFIG_I2C_GPIO=y`、`CONFIG_IIO_TRIGGERED_BUFFER=m`。只差 DTS 节点。

**接线（照 markw DTB `/tmp/odin-hw/markw.dts:4035-4063` 抄）：**
```
i2c-gpio {
	compatible = "i2c-gpio";
	sda-gpios = <&tlmm 14 (GPIO_ACTIVE_HIGH|GPIO_OPEN_DRAIN)>;
	scl-gpios = <&tlmm 15 (GPIO_ACTIVE_HIGH|GPIO_OPEN_DRAIN)>;
	i2c-gpio,delay-us = <2>;
	#address-cells = <1>;
	#size-cells = <0>;

	imu@68 {
		compatible = "bosch,bmi120";
		reg = <0x68>;
		vdd-supply = <&...>;        // 需换成我们自己的 LDO
		vddio-supply = <&...>;
		mount-matrix = "0", "-1", "0", "-1", "0", "0", "0", "0", "1";
	};
};
```
三个注意点：
1. **`sda-gpios` 里写 tlmm 14/15**；016 报告里打印的 526/527 是同一对引脚加了 512 的偏移
2. `mount-matrix` 是 markw 的摆放方向，**我们不一定一样**，照抄可能导致屏幕旋转判断反了——这是纯数据不是驱动问题，后面按实机调
3. `vdd`/`vddio` 的 phandle 必须换成 `msm8953-smartisan-odin.dts` 里的 LDO（建议 l6 1.8V / l9 3.0-3.3V，但要参照原厂 DTS 的 `cam_vio` 等同域电源再定）

**⚠️ 不要抄 markw 的 `light@23`（ltr559）和 `magnetometer@2e`（yas537）** —— 那是红米的料，我们这儿没有（016 报告里它们确实没绑上，就是因为这个）。

### 4.3 蓝牙 —— 内核侧完全就绪，只差用户态

**现状（真机实测）**：`hci0` 已注册；`btqcomsmd`+`btqca`+`bluetooth` 已加载；rfkill state=1 未屏蔽；`bluetooth.target` active。**但 `bluetoothd` 未运行，`dpkg -l` 只有 `libbluetooth3`，没有任何 bluez 包，也没有 `bluetoothctl`。**

**接线步骤：**

**(a) 装 bluez**（用户态，唯一必需项）。内核侧不需要任何改动。

**(b) 可选：给 `&wcnss_bt` 加 `local-bd-address`。** 这是 HCI 子系统的**正式 DT 属性**，不是 work around：
- `btqcomsmd_setup()`（`drivers/bluetooth/btqcomsmd.c:108`）只做两件事：HCI Reset，然后打上 `HCI_QUIRK_USE_BDADDR_PROPERTY`（注释原文：*"Devices do not have persistent storage for BD address. Retrieve it from the firmware node property."*）
- `hci_sync.c:3593 hci_dev_get_bd_addr_from_property()` 会读 fwnode 的 `local-bd-address`；读不到就把 hdev 标记成 `HCI_UNCONFIGURED`，此时 `mgmt.c:614 is_configured()` 返回 false，`bluetoothctl` 会显示控制器未配置
- 主线里 `local-bd-address` 用在不少板子上（`hci_qca` / `btnxpuart` 也读它），是标准机制
- 不加也能用（由用户态 `btmgmt public-addr` 设），但**建议加**，值从原厂 persist 分区或机身标签上的 BT MAC 取
- 位置：`&wcnss_bt { local-bd-address = [xx xx xx xx xx xx]; };`（`msm8953.dtsi:2002` 已定义 `wcnss_bt` 标签）

**(c) ⚠️ 不需要固件 —— 这条容易被 pmOS 的证据误导。**
pmOS 在这台机器上确实有 `qca/nvm_00150100.bin` + `qca/rampatch_00150100.bin`（`08-peripherals-firmware.txt:125-126`，来自 pmOS 的 `firmware-qcom-msm8953` 包），我们 Debian 的 `/lib/firmware/qca/` 里没有这两个文件。但**它们对 btqcomsmd 根本用不上**：rampatch/nvm 下载走的是 `qca_uart_setup()`，那是 **hci_qca（UART 挂 QCA）**的路径；SMD 路径的 `btqcomsmd` 从不调它。**不要为蓝牙去扒原厂分区找固件。**

### 4.4 音频（扬声器 / 听筒 / 麦克风 / 耳机孔）

**硬件（原厂 DTS 实锤）：**
- 模拟编解码：`qcom,pm8953@1` 下 `8953_wcd_codec@f000`（+`@f100`），compatible `qcom,msm8x16_wcd_codec`，`qcom,dig-cdc-base-addr = <0xc0f0000>`
- 数字编解码：地址 **0xc0f0000**（原厂 DTS 与 markw DTB 两个独立来源互相印证）
- 耳机孔：mbhc 中断（`ins_rem_det` / `but_press_det` / `but_rel_det`）
- 外放：WSA881x ×4（`swr_master` 下）+ GPIO 132 的 ext-PA

**根因（为什么现在一点声音都没有）**：
1. **`&lpass`（ADSP）在 `msm8953.dtsi:2116` 是 `status = "disabled"`**，我们 DTS 没启用 ⇒ 真机只有 `remoteproc0`（wcnss）在跑
2. DTS 里没有 sound 节点

**接线步骤：**

**A1. 启用 ADSP（第一步，没有它后面全白搭）**
```
&lpass { status = "okay"; };
```
- `msm8953.dtsi:2092 lpass: remoteproc@c200000`，compatible `qcom,msm8953-adsp-pil`，主线驱动在 `drivers/remoteproc/qcom_q6v5_pas.c:1444`（已确认支持）
- 固件 `adsp.mdt`：从 **dsp 分区**（`/dev/disk/by-partlabel/dsp`，原厂 16 MiB ext4）取。照抄 `dist/build/rootfs/usr/local/sbin/odin-wlan-fw.sh` 那个"开机从原厂分区现取"的模式
- 参照 `sdm632-fairphone-fp3.dts:101` 的写法 `firmware-name = "qcom/msm8953/fairphone/fp3/adsp.mbn"`（我们可用 `firmware-name = "adsp.mbn"`）

**A2. ⚠️ 声卡机器驱动这一层有个真问题，需要实测定夺**
- markw 的 DTB 里声卡 compatible 是 **`qcom,msm8953-qdsp6-sndcard`**（`/tmp/odin-hw/markw.dts:3475`）
- **主线 6.19 的 `sound/soc/qcom/apq8016_sbc.c:329-333` 只认两个**：`qcom,apq8016-sbc-sndcard` 和 `qcom,msm8916-qdsp6-sndcard`。**没有 `qcom,msm8953-qdsp6-sndcard`**（全树 grep `sound/` 和 `drivers/` 确认）
- 两条路：
  - **(a) 先用主线现成的 `qcom,msm8916-qdsp6-sndcard` 试**。它要求必带 `mic-iomux` + `spkr-iomux` 两个 reg（`apq8016_sbc.c:315-321`，缺了直接 probe 失败返回错误码）。markw 的实配：`mic-iomux` @ `0xc051000`、`spkr-iomux` @ `0xc051004`（另有 `pri-iomux` @0xc055000、`quin-iomux` @0xc052000，主线驱动不读后两个，多写无害）
  - (b) 从 msm8953-mainline 合入 `qcom,msm8953-qdsp6-sndcard` 补丁
  - **倾向先 (a)**：(a) 是 (b) 的子集，先验证通路通不通，成本最低

**A3. 声卡节点本体（照 markw DTB 抄，节点位置/结构一致）**
- `codec@c0f0000` → `compatible = "qcom,msm8916-wcd-digital-codec"`，`reg = <0xc0f0000 0x400>`
- `&spmi_bus { pmic@1 { audio-codec@f000 { compatible = "qcom,pm8916-wcd-analog-codec"; reg = <0xf000 0x200>; ... } } }`。注意 `pm8953.dtsi:122` 的 `pmic@1` 是**空的**（只有 compatible + reg），codec 子节点要我们自己在 board DTS 里补——markw 的 DTB 就是这么做的（`markw.dts:2526-2555`）
- `sound-card@c051000` → 上面 A2 说的 compatible，带 mm1~mm4 / voicemmode1 / primary-mi2s / tertiary-mi2s 这些 dai-link

**A4. 扬声器功放**
- **死路：WSA881x（SoundWire）**。原厂 `swr_master { compatible = "qcom,swr-wcd"; }` 挂在 WCD codec 下带 4 颗 `qcom,wsa881x`（`stock.dts:6555-6585`）。但**主线 `msm8953.dtsi` 里根本没有 SoundWire 控制器节点**（grep `soundwire|swr|wsa881` 全空），而且 **`CONFIG_SOUNDWIRE is not set`**。主线虽有 `wsa881x.c`，但它是 SoundWire 从设备，没有主控制器就是废的
- **活路：GPIO 使能的外放功放 → `simple-audio-amplifier`**。原厂 codec 节点里有 `qcom,ext-pa-enable = <GPIO 132>`（`stock.dts:8329`）。主线对应：
  - `sound/soc/codecs/simple-amplifier.c:92` → `compatible = "simple-audio-amplifier"`
  - **`CONFIG_SND_SOC_SIMPLE_AMPLIFIER=m` 已开**
  - 先例 `msm8916-wingtech-wt865x8.dtsi:21`：
    ```
    audio-switch {
    	compatible = "simple-audio-amplifier";
    	pinctrl-0 = <&headphones_switch_default>;
    	pinctrl-names = "default";
    	enable-gpios = <&tlmm 120 GPIO_ACTIVE_HIGH>;
    	sound-name-prefix = "Headphones Switch";
    };
    ```
  - 我们的写法：`audio-amplifier { compatible = "simple-audio-amplifier"; enable-gpios = <&tlmm 132 GPIO_ACTIVE_HIGH>; sound-name-prefix = "Speaker Amp"; }`，挂到声卡的 `aux-devs`（参照 markw 的 `aux-devs = <aw8738>`）
  - 有效电平 high/low 需按原厂 `qcom,ext-pa-enable` 第三个 cell `0x00` 判断（下游 `0x00` 通常表示 active-high），**建议上机实测再定**
  - **注意**：这条依赖声卡，所以顺序在 A1~A3 之后，别单独立项

**A5. 用户态**：`alsa-ucm2` 配置目前**完全没有**（`/usr/share/alsa/ucm2/` 不存在），也没有 `alsa-utils`，pipewire/wireplumber 没在跑。pmOS 用的是 `soc-qcom-msm8953-ucm`，源码在 `https://github.com/msm8953-mainline/alsa-ucm-conf`（`pmaports/device/community/soc-qcom-msm8953/APKBUILD` 里有 commit 号 `b6860eae577ddea6f55834850fb4ed403f208d2f`）。这块要单独搬。

### 5.1 逐项说明"为什么不支持"

| 模块 | 不支持的原因类型 | 具体说明 |

| **电量计** | **缺驱动** | 主线无 `qcom,qpnp-fg` 驱动 |

| **地磁** | **缺整个框架** | 传感器走 SSC（ADSP sensor hub），**主线没有 SSC 框架**。这不只是缺一个驱动，是缺整个 sensor hub 子系统 |
| **指纹识别** | **缺驱动 + 内核没有这个设备类别** | 主线无 Goodix 指纹驱动；**Linux 根本没有 fingerprint 设备类别**（Android 是 HAL 直接操作 SPI 设备）。另外原厂那套 `goodixfp.mdt/.b00..b06` 是 **PIL/TZ 加载的固件**，需要 qseecom + SCM 调用，主线里没有对应的加载路径 |

### 5.2 处置建议

**值得考虑回合 fork 补丁的（3 项）**：
- 充电 `qcom,pmi8996-smbchg`、电量计 `qcom,pmi8996-fg`、振动 `qcom,pmi8950-haptics` / `qcom,spmi-haptics`
- **理由**：这三个都是 **SPMI platform 驱动**，不依赖 ADSP/modem/SSC 那些重子系统，相对干净。而且**接线方式已经完全确定**（见 §5.4），照抄即可
- 另有个旁证：我们自己的 `msm8953-smartisan-odin.dts` 里已经有 `usb_otg_vbus: otg-vbus { compatible = "qcom,pmi8950-smbchg-otg"; reg = <0x1200 0x100>; }`，其驱动 `drivers/regulator/qcom-smbchg-otg.c` 是**我们自己加的**（commit `1d12b99be`），不是主线 —— 说明同一块 PMI8950 的充电寄存器组我们已经能访问

**建议明确砍掉的（5~6 项）**：
- **指纹**：整个清单里最重的一块（要写 SPI 驱动 + TEE 固件加载 + 用户态守护），且对"手机当小服务器用"毫无帮助
- **FM**：纯 Android 功能
- **光感 / 地磁 / 通知灯**：对本项目目标没有价值
- （S5K3L8 等摄像头：如果实测确认本机是这几颗，要移植的工作量也不小，建议与摄像头整体一起评估）

### 5.3 摄像头传感器型号：只能给候选集（推翻了早前的判断）

**这段是对早期结论的更正，务必看完。**

早前据 ROM 里的组合 EEPROM 库 `libmmcamera_imx258_s5k3l8_gt24c64a_eeprom.so` 推断"本机 = IMX258 + S5K3L8"。**这个推断是错的。**

后来从 `system_4.img` 偏移 22392034 处挖出了 `/etc/camera/camera_config.xml`（4 份副本，同一份模板），结构是**候选清单**，不是本机实配：

```
CameraId 2 (FRONT)     : ov8856 | ov8856_qtech | s5k3p3st | s5k3p3st_qtech
                         eeprom = s5k3p3st_ov8856_gt24c64a
CameraId 0 (BACK)      : ov13855_sunny | imx258 | s5k3l8
                         eeprom = imx258_s5k3l8_gt24c64a
CameraId 1 (BACK_AUX)  : ov13855_mono_sunny | imx258_mono | s5k3l8_mono
                         eeprom = imx258_s5k3l8_mono_gt24c64a
```

这是**厂商 BOM 选项表**。下游相机栈开机时按顺序试每一组，靠读 EEPROM 判断实际焊了哪颗。所以：

- **后摄 ∈ {IMX258, S5K3L8, OV13855-Sunny}**
- **副后摄 ∈ {IMX258_mono, S5K3L8_mono, OV13855_mono_sunny}**
- **前摄 ∈ {OV8856, S5K3P3ST}**

这也解释了原厂 DTS 里为什么有 3 个相机槽位（BACK / BACK_AUX / FRONT，全部 `status="ok"`）—— 那不是"用户记错了"，是这机器本来就有双后摄的料单。**不该拿其中一个去否定另一个。**

**主线驱动覆盖情况：**

| 候选型号 | 主线驱动 | CONFIG | 结论（若本机是这个型号） |
|---|---|---|---|
| IMX258 | ✅ `imx258.c` | `CONFIG_VIDEO_IMX258` 未开 | 需接线 |
| OV8856 | ✅ `ov8856.c` | `CONFIG_VIDEO_OV8856` 未开 | 需接线 |
| S5K3L8 | ❌ 无 | — | 主线不支持 |
| S5K3P3ST | ❌ 无 | — | 主线不支持 |
| OV13855 | ❌ 无（主线只有 `ov13858.c`，不是 13855） | — | 主线不支持 |

**怎么一锤定音（两条路，都需要动机器，本报告未执行）：**
1. **读 EEPROM**：CCI 总线上挂的 GT24C64A（I2C 0xA0 —— 原厂 DTS `qcom,eeprom@*` 的 `qcom,slave-addr = <0xa0>` 就是它）里存着模组型号字符串。把 camss+cci 接上后 `i2cget`/`i2cdump` 读出来即可
2. **直接试**：接上 camss+cci，把候选 compatible 全写上，看哪个 probe 成功

**两条路都得先把 CAMSS/CCI 接好，所以实操顺序不变：先接 camss+cci，型号自然就知道了。不建议为定型号单独投入。**

出处 `markw.dts:2716-2727`。
**跟我们原厂 DTS 完全对得上**：`stock.dts:8913` 的 `qcom,haptic@c000` 也在 pmic@3 的 0xc000，也是 `actuator-type = "lra"`、`wave-shape = "sine"`、`play-mode = "buffer"`。**两个独立来源互相印证，可以放心抄。**
注意中断格式：markw 用 4-cell（`<0x03 0xc0 0x00 0x03 ...>`），我们原厂 DTS 写的是 2-cell（`<0x03 0xc0 0x00 0x03 0xc0 0x01>`）—— 转成主线格式要按 markw 那组来。

**④ 共同前提：`battery` 节点**（我们 DTS 现在没有，要自己加）

原厂 `stock.dts:11889 qcom,battery-data` 给出（两家供应商，数值几乎一样）：

| 参数 | ATL 版 | SCUD 版 | 说明 |
|---|---|---|---|
| `qcom,battery-type` | `smartisan_atl_3500mAh` | `smartisan_scud_3500mAh` | 两家电芯厂 |
| `qcom,max-voltage-uv` | `0x432380` = **4 402 048 µV** | 同 | 满电 4.402 V |
| `qcom,nom-batt-capacity-mah` | `0xdac` = **3500 mAh** | 同 | |
| `qcom,batt-id-kohm` | 10 | 100 | 靠电池 ID 电阻区分供应商 |
| `qcom,fastchg-current-ma` | `0xdac` = **3500 mA** | 同 | 快充上限（在 smbcharger 节点里，`:8561`） |
| `qcom,fg-profile-data` | 32 word | 另一组 | **主线用不上**，`qcom,qpnp-fg` 私有 |

我们的 `simple-battery` 该写：
```
battery {
	compatible = "simple-battery";
	charge-full-design-microamp-hours = <3500000>;
	voltage-min-design-microvolt = <3400000>;
	voltage-max-design-microvolt = <4402000>;
	constant-charge-current-max-microamp = <1000000>;
};
```
- `voltage-max-design-microvolt` 用**原厂的 4.402 V**（原厂 DTS 写 4402048 µV，016 报告实测读到 4.405 V，互相印证），比照抄 markw 的 4.385 V 准
- `voltage-min-design-microvolt`：原厂 DTS **没有**这个字段，3.4 V 是从 markw 借的通用 Li-ion 值。**推测**
- `constant-charge-current-max-microamp`：markw 是 1 A。原厂快充能到 3.5 A，但那是 `qcom,qpnp-smbcharger` 的私有属性，主线 `simple-battery` 的语义不一样。**接充电驱动时要按驱动语义重定，别直接把 3500 填进去**

## 八、对 `reports/016` 的两处更正与一处推翻

### 8.1 更正一：电量计的 compatible 是 `qcom,pmi8996-fg`，不是 pmi8994

016 §2.11 写的是 `qcom-pmi8994-fg`。但 markw DTB 里实际的 compatible 字符串是 **`qcom,pmi8996-fg`**（`markw.dts:2669`）—— pmi8994 是**驱动/模块名**，pmi8996 才是 **DT compatible**。

**这个区别很要紧：写 DTS 必须用 `qcom,pmi8996-fg`，写 pmi8994 匹配不上。**

### 8.2 更正二：smbcharger 的 SPMI 地址 0x1000

016 报告里"smbchager@1000"那个地址来自 markw 环境，而原厂 DTS 的 `qcom,qpnp-smbcharger` 是个 `spmi-dev-container`、**没有写 reg**（`stock.dts:8536`，只有 `qcom,pmic-revid` 指向 pmic@2 的 revid）。
后来 markw DTB 的实配证明 **0x1000 是对的**（pmic@2 上的 SMBC 基址）。**可以直接用。**

### 8.3 推翻：016 里"光感/地磁/相机不可用"那几条不能沿用

016 §2.13 的那张表**是在跑 markw 回落 DTB 的环境下采集的**（`lk2nd` 的 QCDT 表没有本机条目，最终加载了 `/boot/msm8953-xiaomi-markw.dtb`，016 §1.1 自己写明"不是 markw"）。因此：

- 016 的「光感 = ltr559 未绑定」「地磁 = yas537 未绑定」—— ltr559@0x23、yas537@0x2e 是**红米的料**，本机根本没有。本机光感是 **TCS3400**。这两条结论对本机无效
- 016 的「摄像头传感器 s5k3l8 / ov5670 未绑定」—— 同样是 markw 的传感器，不是本机的
- 016 §2.5 的「内核无 FTS 驱动，若本机触摸是 FTS 系列，主线无驱动」—— **这条对 pmOS 6.17 成立，对主线 6.19 不成立**（见 §4.1）

## 九、一个贯穿全篇的结构性发现：主线 6.19 与 msm8953-mainline fork 的差距

**我们给 ODIN 编的内核是纯主线 6.19 + pmOS 的 config**（源码 `/Volumes/caseSensitiveBar/linux-msm8953/`，分支 `odin-wip`，在 Linux 6.19 之上只有 7 个自己的 commit：3 个面板驱动、SMBCHG OTG VBUS regulator、FUSB301 typec、Smartisan vendor prefix、ODIN DTS）。

**但 016 报告里记录的"音频/充电/振动/相机都能用"，是本机跑 postmarketOS 时的状态，而 pmOS 的内核不是主线**，是 `https://github.com/msm8953-mainline/linux`（见 `pmaports/device/community/linux-postmarketos-qcom-msm8953/APKBUILD` 的 `url=`），带了一批**从未合入主线**的补丁。

**因此"pmOS 上能用"推不出"主线能用"。** 受影响的 6 个模块：
- 声卡机器驱动 `qcom,msm8953-qdsp6-sndcard`（主线只有 `qcom,msm8916-qdsp6-sndcard`）
- 充电 `qcom,pmi8996-smbchg`
- 电量计 `qcom,pmi8996-fg`
- 振动 `qcom,pmi8950-haptics` / `qcom,spmi-haptics`
- S5K3L8 / S5K3P3ST / OV13855 摄像头传感器驱动
- 传感器 SSC（ADSP sensor hub）整套框架

**判断技巧**：想知道某个 compatible 主线有没有，直接 `grep -rn "<compatible>" /Volumes/caseSensitiveBar/linux-msm8953/drivers/` 比查 wiki 快且准。

## 十一、建议的动手顺序

| 顺序 | 模块 | 理由 |
|---|---|---|
| 1 | **触摸屏** | 主线驱动现成、CONFIG 现成，接线量小；有触摸才有 UI；且有同 SoC 先例可照抄 |
| 2 | **加速度计 + 陀螺仪** | CONFIG 全开，只差一个节点，且有本机实测先例。**最稳的一项** |
| 3 | **蓝牙** | 内核侧完全就绪，只差装 bluez |
| 4 | **音频**（含 ADSP） | 工作量中等，卡在机器驱动 compatible 的二选一上，需先做 A2 的验证 |
| 5 | **相机闪光灯** | 单行改动，顺手做 |
| 6 | **摄像头** | 工作量大，且传感器型号未定 |
| 7 | **电量计 / 充电** | 需回合 fork 补丁，优先级取决于要不要低电量保护 |
| 8 | **振动马达** | 优先级最低 |

**关于电池/充电对"当热点用"的影响**：现在**完全看不到电池状态**（没有 charger 驱动 ⇒ 没有 `power_supply` 设备）。后果是不知道剩余电量、不知道有没有插着电、没有低电量保护。**但不会因为没驱动就充不了电**——PMI8950 的充电是硬件自主管理，插上 USB 就会充，不需要内核参与。所以"当热点用"在功能上不受影响，只是**不可观测**。长期跑建议至少把电量计搞定。
