# 041 — 我们与上游的关系：钉在 6.19.5 错过了 f_ncm 修复，基线升到 7.1.3

日期：2026-09-05　状态：**基线已升级**，CI 待验证

---

## 一、结论

我们不是"落后几天的同一根分支"，而是**钉在一根被上游放弃的分支上**：

| | |
|---|---|
| 旧基线 | `770e10fa15a0`，分支 `6.19.5/main`，**该分支的 tip**，提交日 2026-03-01 |
| 新基线 | `7213855948c7`，分支 `7.1.3/main`，提交日 2026-07-19 |
| 差距 | `git rev-list --count 770e10fa..72138559` = **33279 个提交** |

上游（pmOS 的 `msm8953-mainline/linux`）**按内核稳定版开新分支，旧分支到 tip 就不再推进**：

```
6.19.5/main   770e10fa15a0   2026-03-01（我们的旧钉点，就是这根的 tip）
7.0.9/main    5be94b504b80   2026-04-02
7.0.2/main    72a42b40898f   2026-05-23
7.1.3/main    7213855948c7   2026-07-19  ← 我们升到这里
```

**为什么这很关键**：光盯"我钉的这根分支有没有新提交"是永远看不到更新的 ——
`6.19.5/main` 从 3 月到现在一个提交都没有，看起来"我们是最新的"。
真正的进展都在新分支上。判断"是否落后"必须看**分支列表**，不是看分支的提交数。

## 二、最直接的代价：我们错过了一个已知修复

038 号报告里那个把系统搞坏的内核 Oops（`if_nlmsg_size()` 踩到已释放的 gadget），
上游早就修好了，而且是**一整套**：

| commit | 日期 | 标题 |
|---|---|---|
| `ec35c1969650` | 2026-03-09 | usb: gadget: f_ncm: Fix net_device lifecycle with device_move |
| `e1eabb072c75` | 2026-03-11 | usb: gadget: u_ether: Fix race between gether_disconnect and eth_stop |
| `e002e92e88e1` | 2026-03-16 | usb: gadget: u_ether: Fix NULL pointer deref in eth_get_drvinfo |

三个都**晚于我们的钉点 16~23 天**。我们 3 月之后还在这个坑里反复投入了
`v0.9.6-usb-oops`、`v0.9.7-ncm-panic` 两个版本，其中：

- `patches/0011`（`ncm_unbind` 时清 `netdev->dev.parent`）是**我们自己写的同类补救**。
  上游的 `ec35c1969650` 是正规解法（用 `device_move` 管理 netdev 生命周期），
  0011 现在属于重复且更劣的实现 —— **已删除**，原件移到 `tmp/superseded-patches/`。
- 038 报告里"方案 B（修 `rtnl_link_get_size()` 的竞态）"因此**不再需要**。

**教训**：一个专项排查了很久的 bug，动手前先确认上游有没有修过。
查的方法不是搜 issue，而是看我们钉点之后新分支上有没有相关 commit。

### 配置漂移：olddefconfig 会静默丢弃 14 个符号

`make olddefconfig` 对"符号已不存在"是**静默丢弃**，不报错也不提示。
所以先算出来再逐个确认，别等编完才发现少了什么。

我方 config 启用、但 7.1.3 已无此符号的 14 项，逐一定性：

| 符号 | 性质 | 对我们的影响 |
|---|---|---|
| `ARM64_PAN`、`ARM64_LSE_ATOMICS`、`ARM64_USE_LSE_ATOMICS` | arm64 上已无条件开启，选项被移除 | 无（本来就该开） |
| `CRYPTO_AES_ARM64_CE` | 被 `CRYPTO_AES_ARM64_CE_BLK` 取代 | 无（config 里已有 `=y`） |
| `CRYPTO_GHASH` | 通用 GHASH 合并进架构实现 | 无（`CRYPTO_GHASH_ARM64_CE` 仍在） |
| `CRYPTO_SM3_GENERIC`、`CRYPTO_SM3_ARM64_CE` | 合并为 `CRYPTO_SM3` | 无（config 里已有 `=m`） |
| `CRYPTO_RNG_DEFAULT` | 移除 | 无（`CONFIG_CRYPTO_RNG=y` 仍在） |
| `NFS_V4_1` | NFS Kconfig 重构（`NFS_V4_0` 体系） | 无（`NFS_V4_2=y` 隐含 4.1） |
| `NF_CT_PROTO_UDPLITE` | 移除 | 无（UDPLITE 连跟踪，本机不用） |
| `MDIO_BUS` | 改名为 `MDIO` | 无 —— msm8953 上没有以太网 PHY；且 `PHYLIB` 不依赖 `MDIO`，不会连带被关掉 |
| `ARCH_ENABLE_MEMORY_HOTREMOVE`、`SLUB_CPU_PARTIAL`、`KVM_GENERIC_MMU_NOTIFIER` | 内部符号，由别的选项 `select` | 无 |

### 新增符号：315 个，与本机硬件无关

按 `qcom|msm|dsi|panel|venus|smbchg|wcn|dwc3|extcon|typec|mdio|gadget|ncm|ecm|rndis`
筛完，命中的全是**别的机器的驱动**（别的 panel、别的 MDIO 控制器、
`INTERCONNECT_QCOM_ELIZA`、`USB_DWC3_GOOGLE`、`USB_DWC3_IMX`…）。
这些默认 `=n` 是对的，不需要我们额外开。

## 五、升级过程中撞到并已修的两处上游改名

### 5.1 DTB 编译失败：PDM 引脚状态标签改名（已修）

`dtb` job 报 6 条 `phandle_references`，指向 `cdc_pdm_lines_act` 等不存在的标签。
真因不是接线错，是 7.1.3 把 `msm8953.dtsi` 里 `&tlmm` 下那 6 个状态按
`pinctrl-names` 统一改了名（`_act` → `_default`、`_sus` → `_sleep`），
**引脚与电气参数一字未改**（gpio67~74、`cdc_pdm0`、8mA / 2mA + bias-disable）。
上游所有 msm8953 板子同步改的，我们照改即可。改完本地四个 DTB 全编过。

### 5.2 pmi8950 充电芯片：从"借 pmi8996 的数据"变成"有自己的数据"

这个不是编译问题，是**我们设备上的真实行为变化**，值得单独记一笔：

| | 6.19.5 | 7.1.3 |
|---|---|---|
| `pmi8950.dtsi` 的 compatible | `qcom,pmi8996-smbchg`（借的） | `qcom,pmi8950-smbchg`（**新增**） |
| 附带手段 | 靠 DT 属性 `smbchg-lite` 打补丁 | 属性删掉，`smbchg_lite` 写进 `smbchg_pmi8950_data` |
| iterm / ilim 表 | pmi8996 的 | **pmi8994 的** |
| `reset_otg_on_oc` | true | true（**不变**） |
| `smbchg_lite` | true（来自 DT 属性） | true（来自 data，**不变**） |

结论：上游补上了 PMI8950 的正经支持，我们等于从"用 pmi8996 的参数凑合"
换成"用上游认定的 pmi8950 参数"。**这是修好，不是回归** ——
只有 iterm / ilim 两张表变了（充电终止电流与输入限流档位），
OTG 相关的两个开关位与之前完全一致。真机验收时留意的点：
充电电流档位可能与旧版略有差异。

## 六、已知风险（待 CI + 真机验收回答）

1. ~~编译能否过~~（已排除大部分）：逐个核对过 `include/drm/drm_panel.h`、
   `include/drm/drm_mipi_dsi.h` 在两版之间只多了一个像素格式
   `MIPI_DSI_FMT_RGB101010`；`hfi_parser.c` 两版**完全没动**；
   我们三块面板驱动用到的 API（mipi_dsi_* / drm_panel_* / devm_gpiod_get /
   devm_regulator_bulk_get / drm_panel_of_backlight）签名全部不变。
2. ~~DTB 能否编过~~：见 5.1，已修，本地四个 DTB 与 Makefile 全部自检通过。
3. **行为回归**：仍需跑完整的 16 项真机验收才算数
   （USB 网络、WiFi、屏幕、音频、OTG）。5.2 的充电参数变化也在其中。

**不做的假设**：不假设"升了基线 OTG 掉电就好了"。040 号报告已经量过，
那个的根因是电池内阻约 0.54Ω，是硬件问题，升基线不会改变它。
本次升级的收益是**拿到上游已修好的 f_ncm 生命周期问题**，以及不再错过后续修复。
