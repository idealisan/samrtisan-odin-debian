# 020 蜂窝网络（移动数据）可行性调研

调研对象：**Smartisan U2 Pro（ODIN）**，SoC = **骁龙 626（MSM8953 Pro）**，
主线 Linux 6.19（`config-postmarketos-qcom-msm8953.aarch64`）+ Debian 12。

> ⚠️ 两点前提，写在前头：
> 1. **本设备 SoC 是骁龙 626（MSM8953 Pro），不是 SDM450。** 两者 msm-id 不同
>    （我们 0x125，SDM450 是 0x152）。pmOS wiki 上那页 `Snapdragon 450/625/626/632 (MSM8953)`
>    是**按 SoC 归类的大页，对这台机器没有专门记录**，只能当参考。
> 2. **"pmOS 上能用"推不出"主线能用"** —— pmOS 的内核是 `msm8953-mainline/linux` fork。
>    不过本次调研确认：**蜂窝这一块主线是支持的**，见下文。

## 结论：**能做**

不是"也许"。**硬件、固件、驱动、内核配置、用户态工具五样都齐了**，只差把它们接起来。
我们的内核配置已经和"实测打通电话"的 Fairphone 3 主线配置**逐项一致，一个 CONFIG 都不用改**。

## 一、硬件与固件：都有，而且是完整的一套

真机 `mount -o ro /dev/disk/by-partlabel/modem`（modem 分区，原厂 96 MiB vfat）：

```
    238464  mba.mbn      ← MBA（Modem Boot Authenticator），MSS PIL 第一阶段加载器
      7964  modem.mdt    ← MDT 头（ELF 头 + 各 segment 元数据）
       788  modem.b00 … 11124736 modem.b18 … 1048576 modem.b20     ← 各段，合计约 43 MB
```

缺 `b03/b14/b15`（MDT 元数据里就没有这些段，正常）。

`verinfo/ver_info.txt`：
```
"modem": "MPSS.TA.2.3.c1-00167-8953_GEN_PACK-1.104080.1.124490.2"
```
`MPSS` = Modem Peripheral SubSystem，`8953_GEN_PACK` = 就是 msm8953 的 modem 固件包。

**关键点**：驱动 `qcom_q6v5_mss.c` 里
`hexagon_mba_image` 默认 `"mba.mbn"`、`hexagon_mdt_image` 默认 `"modem.mdt"`
（`qcom_q6v5_mss.c:2066`），**和我们分区里的文件名完全一致** —— 也就是说不写
`firmware-name` 也行，把文件拷到 `/lib/firmware/` 就会被自动找到。

同分区还顺带发现 `adsp.mdt` / `venus.mdt` / `cmnlib` / `widevine` / `cpe_9335` / `goodixfp`
等一整套 PIL 固件（跟蜂窝无关，但说明这台机器的 modem 分区是完整的原厂固件镜像，不是被裁剪过的）。

EFS/NV 数据在 `modemst1` / `modemst2` / `fsg` 分区，**这些分区都在，我们从未动过**。

## 二、设备树为什么不通：`mpss` 是上游默认 disabled

`msm8953.dtsi:1421`：
```
mpss: remoteproc@4080000 {
	compatible = "qcom,msm8953-mss-pil";
	status = "disabled";     ← 上游 SoC 级默认值
};
```

**这跟 WiFi 的 `wcnss` 完全同一个剧本** —— 上游默认关，全靠机型 DTS 自己 opt-in。
我们 DTS 里只启用了 `&wcnss`，`&mpss` 没动，所以真机只有 `remoteproc0`（wcnss）一个。

节点本身**很完整**：mba/mpss memory-region、smd-edge（label="modem"）、interrupts、
power-domains(cx/mx/mss)、halt-regs 全在；`rmtfs@f2d00000`（`qcom,rmtfs-mem`）也在 dtsi 里。

> ⚠️ **命名坑**：节点标签是 **`mpss`**，不是 `mss`。
> 写 `&mss { status = "okay"; }` 匹配不到任何节点（编译期就报引用未定义）。
> `reports/016` 里的 `qcom-q6v5-mss` 是**驱动名**不是节点标签 —— 照着抄会白折腾一轮。
> （同理 ADSP 的标签是 `lpass` 不是 `adsp`。）

### 决定性先例：Fairphone 3

`arch/arm64/boot/dts/qcom/sdm632-fairphone-fp3.dts:145`。
注意 **`sdm632.dtsi` 第一行就是 `#include "msm8953.dtsi"`** —— SDM632 就是 msm8953 的马甲。

```dts
&mpss {
	firmware-name = "qcom/msm8953/fairphone/fp3/mba.mbn",
			"qcom/msm8953/fairphone/fp3/modem.mbn";
	pll-supply = <&pm8953_l7>;
	status = "okay";
};
```

就这三行。FP3 在 postmarketOS 上是有移动数据的主力机型之一。

## 四、用户态：基本都有，只差两个服务

真机现状（刷入我们的镜像后）：
- `modemmanager 1.20.4` ✅ 已装
- `libqmi-utils 1.32.2`（含 `qmicli`）✅ 已装
- `libmbim-utils` ✅ 已装
- `network-manager 1.42.4` ✅ 已装

**只是 ModemManager 被我们 mask 了**（`dist/build/setup-rootfs.sh`，原因见 §六）。

真正缺的是这两个，**Debian 12 官方仓库里就有**，可直接 apt：
- **`tqftpserv` 1.0-4** —— "TFTP server working over the **QRTR** protocol"。
  **modem 启动的必需依赖**：modem 固件是通过 QRTR 上的 tqftpserv 喂给 modem 的，
  不是走 `request_firmware`。这也解释了 pmOS 为什么"modem 相关固件文件要拷进 /tmp"。
  非 Motorola 机型一般用标准 tqftpserv 就行。
- **`rmtfs` 1.0-2** —— "Qualcomm Remote Filesystem Service"。
  让 modem 读写 `modemst1`/`modemst2`/`fsg` 里的 **EFS/NV 数据**。

Debian **没有**（需要从 msm8953-mainline 源码编译，但**都不影响上网**）：
- `q6voiced` —— 语音通话的音频路由
- `qrtr`（qrtr-ns 服务发现）

## 五、怎么做（按顺序）

### ① 设备树：`arch/arm64/boot/dts/qcom/msm8953-smartisan-odin.dts` 追加

```dts
&mpss {
	firmware-name = "qcom/msm8953/smartisan/u2pro/mba.mbn",
			"qcom/msm8953/smartisan/u2pro/modem.mdt";
	pll-supply = <&pm8953_l7>;
	status = "okay";
};
```

- **`pll-supply` 是硬要求**：`msm8953_mss.proxy_supply` 要求 `.supply = "pll"` @100000 µA，
  不填 probe 直接失败。
- `pm8953_l7` **我们 odin.dts:243 里已经有了**（1.8–1.9 V）。
  而且**原厂 stock.dts 证实了这一点**：原厂 `qcom,mss@4080000` 的
  `vdd_pll-supply` = phandle 0x105 = `regulator-name="pm8953_l7"`，min 1800000 / max 1900000 µV。
  **FP3、原厂、我们的定义三方一致** —— 这是本次调研最硬的一个确认。
- 固件路径可以不写（驱动默认 `mba.mbn` + `modem.mdt`，拷到 `/lib/firmware/` 根即可），显式写更干净。

> ⚠️ `firmware-name` 的扩展名**不要照抄 FP3 的 `modem.mbn`**。
> 我们分区里是 `modem.mdt` + `.bXX` 段，**没有 `modem.mbn`**。
> `qcom_mdt_read_metadata()` 是按传入的名字去拼 `.bXX` 段名的，写 `modem.mbn` 会去找
> `modem.bXX`（确实同名，碰巧能用），但语义上应该是 `modem.mdt`。
> **最稳的做法：`firmware-name` 里两个名字都不带扩展名歧义，或直接省略让它走默认值。**

### ② 固件提取：照抄 `odin-wlan-fw.sh` 的模式

新增 `dist/build/rootfs/usr/local/sbin/odin-modem-fw.sh`：
开机挂载 `/dev/disk/by-partlabel/modem`，把 `mba.mbn` + `modem.mdt` + `modem.b00…b20`
拷到 `/lib/firmware/qcom/msm8953/smartisan/u2pro/`。约 43 MB。

**沿用"开机从原厂分区现取"而不是把固件塞进镜像的理由**（与 WiFi 那份一致）：
固件是二进制、且带机器相关信息，不该进版本库；modem 分区我们从不动，数据永远在。

### ③ 内核：**不用动**

### ④ 用户态：见 §六

### ⑤ 验证

```sh
dmesg | grep -i mss            # 看 modem 是否 boot
mmcli -L                       # 看 modem 是否被识别
qmicli -d qrtr://0 --wds-start-network="apn=<APN>,ip-type=4" --client-no-release-cid
```
成功的话会出现两个接口（rmnet 接 modem + 一个虚拟的传数据），再 `udhcpc` 拿 IP。

## 六、`setup-rootfs.sh` 里那句错误的注释（已修正）

**原样**（错误）：
```sh
# 本设备无蜂窝基带，ModemManager 只徒增启动开销并会扫描串口
chroot $R systemctl mask ModemManager.service
```

两处都错：
- **"本设备无蜂窝基带"是错的** —— 有基带硬件、有完整 modem 固件、有 modemst/fsg 分区。
  这是继"没有 WiFi 硬件""没有 RTC"之后，**第三次把"配置/验证没做到位"当成"硬件没有"**。
- **"会扫描串口"也不成立** —— ModemManager 走 QRTR，不是串口扫描。

**已改为**（commit `00bd1de`）：说明设备**有**基带（骁龙 626 的 MSS，固件在原厂 modem 分区），
mask 的真实原因是"**6.19 + odin DTB 上的蜂窝链路尚未实机验证**"（DTS 里 `&mpss` 还是上游默认
disabled，WiFi 当初就是这么被挡住的），并写明想试的人该怎么做（装 tqftpserv + rmtfs、
在 DTS 启用 `&mpss`、unmask ModemManager）。

**在验证通过之前不默认启用**，免得开机多一个必然会失败的探测。

## 七、风险与未知（如实说）

### 1. 数据接口由谁创建 —— **没 100% 锁定**

pmOS 和 FP3 的配置**都没开** `CONFIG_WWAN` / `CONFIG_QCOM_BAM_DMUX` / `CONFIG_QCOM_IPA`
—— 即不是 bam-dmux、不是 IPA、也不是 USB QMI_WWAN。但内核里唯一能给这类老 SoC 建 modem
数据网卡的驱动就是 `qcom_bam_dmux.c`（建 `wwan0`），而它依赖 `CONFIG_WWAN`。
这与 wiki"出现两个接口"的描述对不上。

**判断**：要么 pmOS 通用配置漏了 `CONFIG_WWAN` 而各设备自己补，要么 ModemManager 1.20 走 QRTR
有别的建链方式。**这一环只能实机验证。**

**但不影响先做 ①~④** —— 因为 modem 没起来之前根本谈不上数据接口。

**若拉起 modem 后 `mmcli` 能识别却拿不到数据接口**：补开 `CONFIG_WWAN=m` +
`CONFIG_QCOM_BAM_DMUX=m`，并在 `&mpss` 里加 `bam-dmux` 子节点、在 dtsi 补 `bam_dmux_dma` 节点
（照抄 `msm8916.dtsi:1919`：`reg = <0x04044000 0x19000>`、SPI 29、`num-channels=<6>`、
`qcom,powered-remotely`）。

> ⚠️ **这是本次调研里唯一有风险的猜测**：`0x04044000` 是从 msm8916/8917/8937/8939 抄的
> （四者同址），但**原厂 stock.dts 里查不到对应节点**，msm8953 上是否同址**未经验证**。

### 2. SIM 卡供电未验证

UIM regulator（通常 `pm8953_l11` 之类）在原厂 DT 里没专门核对。
若 ModemManager 读不到 SIM，需再补 `vdd-uim` 相关节点。

### 3. 双卡

本设备是**双卡**（用户确认）。卡切换需要 pmOS 的 `msm-modem-uim-selection`，Debian 没有，得自己编。
**单卡应该能直接用。**

### 4. 语音通话

要额外折腾（`q6voiced` 不在 Debian，需源码编）。**上网不受影响。**

### 5. 全流程未实机跑过

第一次可能卡在 modem 固件认证（TZ）或 rmtfs 的分区配置上。

## 九、与 `reports/016` 的对照

`reports/016` §2.10 / §2.13 记录了这台机器跑 pmOS 时的实测：

```
remoteproc0  4080000.remoteproc (qcom-q6v5-mss)  firmware = mba.mbn   ← 基带 MSS，running
```

> ⚠️ **一处未解决的矛盾**：016 的记录显示当时用的是 `rmnet_ipa0` + `ipa_lan0`、**ipa 模块已加载**，

## 十、方法论备忘

1. **依据优先级**：本机的原厂 DTS / 原厂分区实际内容 > 本机跑 pmOS 时的第一手采集（`reports/016`、
   `evidence/device-probe/`）> 主线同 SoC 机型 DTS > pmOS wiki（仅参考）。
2. **不要把"我们没接好线"误判成"硬件没有"**。
3. **注意节点标签与驱动名的区别**（`mpss` / `lpass` vs `qcom-q6v5-mss` / `qcom-q6v5-pas`）。
