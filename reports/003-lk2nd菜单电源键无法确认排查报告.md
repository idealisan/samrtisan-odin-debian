# 检查报告 003 — lk2nd 菜单电源键无法确认选项问题排查

| 项目 | 内容 |
|------|------|
| 报告编号 | ODIN-CHK-003 |
| 检查日期 | 2026-08-22 |
| 起因 | 实机反馈：当前预构建 lk2nd 固件菜单中，电源键无法确认选项（音量−此前已确认失效） |
| 检查深度 | 源码级 + **成品固件反汇编级**（`odin-port/lk2nd/bin/lk2nd.img` 与 `refs/lk2nd/build-lk2nd-msm8953/` MD5 一致：`d40dc6ae…`，可直接分析实际运行代码） |
| 结论 | 软件链路逐环验证**无错误**；失效根因指向运行时 PON 寄存器读取未生效，需实机串口定位；已确认可用绕过方案 |

## 一、验证过的完整链路（均无问题）

### 1.1 菜单选择逻辑（menu/menu.c → 反汇编 `display_fastboot_menu` @0x8f6301e8）

- 等键循环轮询 `lk2nd_keys_pressed()`（0x8f630560 / 0x8f6305f0 两处调用）；
- 按下→等待释放→5ms 防抖→按键分发；
- 分发常量实测：
  - `cmp r4, #0x119`（=281，本仓库 KEY_POWER）→ **执行选中项 action**（0x8f630694 `blx r3`）
  - `cmp r4, #0x115` → sel--（向上）
  - `cmp r4, #0x116` → sel++（向下）

> 注：本 LK 树 `include/dev/key-codes.h` 用 CAF 旧键值定义
> （VOLUMEUP=0x115、VOLDOWN=0x116、POWER=0x119、HOME=0x122），
> published_keys[]、keys.c、菜单 switch 全部使用同一套宏，**内部自洽，非问题**。

### 1.2 键值解析回退链（keys.c → 反汇编 `lk2nd_keys_pressed` @0x8f62e104）

```
KEY_POWER(0x119) → DT 键表(空, odin 未定义 gpio-keys)
                 → 回退 bl 8f624414 <pm8x41_get_pwrkey_is_pressed>
```
`IS_ENABLED(WITH_DEV_PMIC_PM8X41)` 编译期恒真（build config.h:78），守卫被优化掉，调用真实存在。

### 1.3 电源键寄存器读取（pm8x41_get_pwrkey_is_pressed 反汇编 @0x8f624414）

- 构造 SPMI 读命令：`movt r3,#0x1008` → slave_id=0、periph=0x08、offset=0x10
- 即 PM8953 PON 外设 0x800 的 `INT_RT_STS`，测试 bit0（KPDPWR_ON）
- **与原厂 boot.img DTB 一致**：原厂 `qcom,power-on@800` 挂在 `qcom,pm8953@0` 下，
  pon_1(KPDPWR) → linux,code 0x74(KEY_POWER)，证明 ODIN 电源键物理接在 PM8953 KPDPWR ✅

### 1.4 其他排除项

| 排除项 | 证据 |
|--------|------|
| 上游已知 bug | GitHub lk2nd issue 搜索 "power key select" 无结果 |
| single_key 模式干扰 | odin 设备描述未设 `lk2nd,single-key-navigation`；反汇编 `ldrb [r6,#20]`=0 走正常分支 |
| SPMI 初始化缺失 | `target_init()` → `spmi_init(PMIC_ARB_CHANNEL_NUM,…)`；SPMI_CORE_V2=1；max_periph=256 |
| CAF 告警菜单走不同路径 | menu_keys_detect.c 同样路由到 `lk2nd_keys_pressed(KEY_POWER)`，同一链路 |

## 二、关键关联发现（统一根因假说）

三个按键的检测数据源：

| 按键 | 数据源 | 实测状态 |
|------|--------|----------|
| 音量+ | TLMM GPIO85 直读（不经过 PMIC） | ✅ 可用 |
| 音量− | PM8953 PON `INT_RT_STS` bit1（RESIN_ON），SPMI 读 | ❌ 失效 |
| 电源 | PM8953 PON `INT_RT_STS` bit0（KPDPWR_ON），SPMI 读 | ❌ 失效 |

**两个失效键恰好共用同一读取源**（PON INT_RT_STS 的 SPMI 读取），唯一可用键不经 PMIC。
这强烈暗示二者不是两个独立 bug，而是同一根因：LK 阶段对该板 PON 实时状态的 SPMI 读取
未返回有效数据（读到 0 = 永远"未按下"）。报告 002 中将音量−归因于"硬件接 GPIO86"
可能只对了一半——若 PON 读取本身无效，则无论接线如何都检不到。

静态分析无法进一步定位的原因：

1. `pm8x41_reg_read()` **忽略 `pmic_arb_read_cmd()` 返回值**——总线错误被静默吞掉，
   失败与"未按下"在软件上不可区分；
2. V2 仲裁器通道表 `chnl_tbl` 为 malloc 未清零内存，依赖 `spmi_lookup_chnl_number()`
   正确填充（slave0/periph8 → 表项 8）；该项异常同样只能实机观测；
3. PON RT 状态位是否受 XBL/TZ 遗留配置影响，无法离线判断。

## 三、定位建议（需实机 + UART，暂缓执行）

1. 在 `pm8x41_get_pwrkey_is_pressed()` 加 `dprintf(INFO, "PON_RT_STS=%#x\n", pwr_sts)`
   并打印 `pmic_arb_read_cmd()` 返回值，重建带串口的调试固件；
2. 对比按下/松开电源键两次输出：
   - 返回值非 0 且 STS 位翻转 → 读取正常，问题在别处（回到测试场景分析）；
   - 返回值非 0 但恒 0 → PON RT 位未生效；
   - 返回错误 → SPMI 通道表/仲裁器问题，进一步 dump chnl_tbl[8]。

## 四、立即可用的绕过方案

在 `odin-port/lk2nd/msm8953-smartisan-odin.dts`（及补丁 0002）的 `&lk2nd` 节点加一行：

```dts
lk2nd,single-key-navigation;
```

效果（device.c:135–137 解析，menu.c:93–119 生效）：菜单内任意可用键
（音量+）**短按=向下导航，长按 >1 秒=确认选择**，完全绕开电源键确认与音量−方向键。
代价：失去独立的上/下方向与电源确认。
