## 第 3 章 extlinux.conf ↔ lk2nd 解析器对照

### 【主张核验】

镜像内 `/extlinux/extlinux.conf`（debugfs 实读）：

```
default l0
menu title ODIN Debian (mainline 6.19)
timeout 30

label l0
    kernel /boot/vmlinuz
    initrd /boot/initramfs.cpio.gz
    fdtdir /boot/dtbs
    append console=ttyMSM0,115200n8 earlycon=msm_serial_dm,0x78af000 root=/dev/disk/by-label/pmOS_root rootwait rw
```

| 主张 | 结论 |
|---|---|
| conf 各指令均在 lk2nd 支持范围内 | ✅ 属实（`kernel/initrd/fdtdir/append/default` 全部在 token_map 中；`menu title`、`timeout` 被当作 CMD_UNKNOWN 静默忽略——lk2nd 无倒计时菜单语义，直接启动 default label） |
| fdtdir 会递归扫描子目录 | ❌ 不递归。仅按固定模板拼路径逐个试探 |
| dtb 按 lk2nd,dtb-files 文件名匹配选择（非 compatible 运行时匹配） | ✅ 属实 |
| 当前 conf 的 fdtdir /boot/dtbs（dtb 在 qcom/ 子目录）能找到 dtb | ⚠️ **文件层面能找到，但整个 extlinux 路径因文件系统不兼容而根本不会执行**（见新发现 1，致命） |

源码核对（refs/lk2nd）：

1. **指令支持**：`lk2nd/boot/extlinux.c:44-60` token_map 收录 `label/default/kernel/linux/fdtdir/devicetreedir/fdt/devicetree/fdtoverlays/devicetree-overlay/initrd/append`。本 conf 用到的 5 种全部在列 ✅。
2. **fdtdir 解析**（extlinux.c:394-432）：对 `lk2nd_device_get_dtb_hints()` 返回的每个名字，只尝试三种固定模式：
   - `{dtbdir}/qcom/{name}.dtb`（arm64 风格）
   - `{dtbdir}/qcom-{name}.dtb`（arm32 风格）
   - `{dtbdir}/{name}.dtb`（扁平）
   **不做目录列举、不递归**。
3. **hints 来源**：`lk2nd/device/device.c:130-131` 从 lk2nd 自身 DTB 的 `/lk2nd` 节点读 `lk2nd,dtb-files` 字符串列表（`lkfdt_stringlist_get_all`）；odin 对应 `lk2nd/device/dts/msm8953/msm8953-smartisan-odin.dts:17` = `"msm8953-smartisan-odin"`。即**按文件名精确匹配**，与目标 dtb 内容/compatible 无关。
4. **判定**：fdtdir=`/boot/dtbs` 时第一候选为 `<挂载点>/boot/dtbs/qcom/msm8953-smartisan-odin.dtb` —— 镜像内该路径确实存在（debugfs `ls /boot/dtbs/qcom` 见 44362 字节 dtb）✅。
5. 附带核验：conf 使用绝对路径，`normalize_path`（extlinux.c:348-358）会拼出 `<root>//boot/...` 双斜杠；`ext2_walk`（lib/fs/ext2/dir.c:178-180"consume multiple seperators"）可正确消费多斜杠，不构成问题。

### 【新发现问题】

1. **[致命] 镜像文件系统是现代 ext4 特性集，lk2nd 的 "ext2" 驱动在挂载阶段直接拒绝 → 整条 extlinux 启动链不会执行。**
   - 启动入口 `lk2nd/boot/boot.c:50`：对所有叶子块设备执行 `fs_mount(mountpoint, "ext2", bdev->name)`，只有这一种文件系统驱动。
   - 挂载白名单 `lib/fs/ext2/ext2.c:163`：`s_feature_ro_compat & ~(SPARSE_SUPER|LARGE_FILE)` 非零即返回错误。
   - 实测镜像超级块（raw 偏移 1024 处，od 逐字读取）：`s_feature_compat=0x3C`、`s_feature_incompat=0x2C2`（filetype|extent|64bit|flex_bg）、`s_feature_ro_compat=0x46B`（sparse_super|large_file|**huge_file|dir_nlink|extra_isize|metadata_csum**）。0x46B & ~0x3 = 0x468 ≠ 0 → **mount 必失败（err=-3）**。
   - 即使绕过该检查：驱动代码完全没有 extent 映射解析（inode i_block 仅按 ext2 传统直接/间接块解释），而镜像所有 inode 均为 extent 格式（debugfs stat 根 inode 输出 "EXTENTS:"），文件一个字节都读不出来。
   - 后果推演：`lk2nd_scan_devices()` 所有分区挂载失败 → 打印 "Bootable file system not found. Reverting to android boot." → 回落 android boot 流程 → 无法启动 Debian。
   - 上游文档明确此约束：`Documentation/boot.md:26` "The file shall be stored at an **ext2** formated partition"。dist/lk2nd.img 二进制内也确认编入了 extlinux 支持（strings 可见 `%s/extlinux/extlinux.conf` 等），问题不在 lk2nd.img，而在 userdata 镜像的 mkfs 方式。
   - **修复方向**：重建镜像时用纯 ext2 特性集，例如 `mkfs.ext2 -O ^has_journal,^ext_attr,^resize_inode,^dir_index,^extent,^64bit,^flex_bg,^huge_file,^dir_nlink,^extra_isize,^metadata_csum`（保留 filetype/sparse_super/large_file）；只读早期引导无需日志，同时规避未实现的 journal 重放。
2. **[低] FLASH.md:43 "lk2nd 负责解析 userdata 里的 ext4" 表述与实现不符**（实际只认 ext2 兼容特性集），误导排障方向，应随问题 1 一并修正文案。
3. **[信息] `timeout 30` 无效**：解析器忽略该指令，不存在 5 秒/30 秒倒计时进 fastboot 菜单的行为；设备将无条件启动 default label（对刷机流程反而更省事，但与用户对 extlinux 惯例的预期不同）。

### 【证据】

- `docker exec odin-build debugfs -R "cat /extlinux/extlinux.conf" /mnt/img/odin-debian.img` → 上文全文
- `debugfs -R "ls -l /boot/dtbs/qcom"` → `msm8953-smartisan-odin.dtb, 44362 B`
- refs/lk2nd 源码行号：extlinux.c:44-60（token_map）、394-432（三模板试探）、device.c:23-26/130-131（hints）、boot.c:45-63（16MiB 门槛+ext2 挂载+回落打印）、ext2_fs.h:347-361（INCOMPAT_SUPP 仅 filetype|meta_bg）、ext2.c:163（ro_compat 白名单）

## 第 9 章 【致命→已修复】lk2nd 无法读取现代特性集 ext4（独立复审核心发现）

### 问题
第 3 章复核中确认：lk2nd 唯一文件系统后端为 `lib/fs/ext2`（lib/fs/fs.c 仅注册
ext2_init），其挂载函数 `ext2.c:163` 硬性拒绝 ro_compat 中除 sparse_super/large_file
外的任何特性，且无 extent 解析能力。而 odin-debian.img 使用 Debian 默认 mkfs 特性集
（extents/64bit/metadata_csum/huge_file/dir_nlink/extra_isize）⇒ lk2nd 挂载即失败，
**extlinux 启动链整体不可达，刷入后无法引导 Linux**。

旁证闭环：pmOS 官方 msm8953 设备 `deviceinfo_boot_filesystem="ext2"`——pmOS 方案中
lk2nd 只读独立的传统 ext2 boot 分区（或链载 boot 分区 512K 偏移处的真 boot.img），
从不读取现代 ext4 根分区。008 报告"ext4 驱动+extlinux 解析器存在"仅基于字符串判断，
属误判；此前所有会话均未实测过完整启动链。

### 修复（本仓库 commit 待填）
以保守特性集重建根镜像，内容与原镜像完全一致：
```
mke2fs -t ext4 -O ^extents,^64bit,^metadata_csum,^huge_file,^dir_nlink,^extra_isize,^resize_inode \
       -I 256 -b 4096 -L pmOS_root -d /mnt/debian rootfs.img 296572
```
- 新特性表：has_journal ext_attr dir_index filetype flex_bg sparse_super large_file
  —— ro_compat 仅剩驱动允许集 ✅；flex_bg/filetype 为 incompat 但该驱动不校验
  incompat 且二者为历史常规配置 ✅
- 批量改造（earlycon/DNS/wcnss/initramfs）先折入 staging 再整体灌入，
  逐项回读验证：extlinux append 行、initramfs md5(c0ddc565)、vmlinuz 大小、
  wcnss×10、sudo setuid 04755、ssh 密钥×3、serial-getty@ttyMSM0 链接、.odin-debian 标记
- e2fsck 干净；img2simg 重生成 sparse；check_sparse = IDENTICAL
