## 二、lk2nd-msm8953 的真实显示架构（证据齐全）

构建配置 `LK2ND_DISPLAY ?= cont-splash`（project/lk2nd.mk），display/rules.mk 据此：
- **不编译** `lk2nd/display/panel/`（含 GCDB 包装层与 `lk2nd_oem_panel_name`）
- 编译 `cont-splash/` 模式，其 `target_display_init()` 全文仅一行逻辑：

```c
if (fbcon_display() || mdp_setup_cont_splash())
        display_image_on_screen();     // 纯帧缓冲复用，零 DSI 操作
```

部署形态（FLASH.md）：原厂 aboot 完好留在 aboot 分区，lk2nd.img 刷入 boot 分区，
被 aboot 当作"内核"跳转。因此真实启动链是：

```
原厂 aboot(GPIO91/92 strap 检测 → DSI 初始化 → 画 splash)
   └─ cmdline 携带 mdss_mdp.panel=...（stock mbn 内实存该字符串）
        ↓ 跳转
lk2nd(cont-splash)：parse-cmdline.c 解析上一棒 cmdline
   → 得 panel.name 与 initialized 标志 → 复用帧缓冲显示菜单
   → 启动主线内核时以 panel.name 替换占位 compatible
```

## 三、结论修正

| 此前认知 | 事实 |
|---|---|
| lk2nd 自己初始化面板，默认 R69006/HX8399C 有选错风险 | lk2nd 从不初始化 DSI；面板由**原厂 aboot**检测并初始化 |
| 需要 GPIO 检测补丁实现自动识别 | **自动识别由架构天然提供**（aboot straps + cmdline 名字透传 + DT 替换），三分批次全覆盖 |
| r69006 批次有黑屏风险 | r69006 不在 aboot strap 逻辑中=出厂即如此；若真存在此类机器，原厂系统同样处理（cmdline 给出 aboot 实际选择的面板名） |
| 补丁0001 的 GCDB 面板库参与运行 | 在 lk2nd 构建形态下为死代码（无害）；仅在改用 lk1st/直接刷 aboot 分区部署时才生效 |
| 补丁0003 的 GPIO 检测会运行 | 同上为死代码；`oem panel` 的"实时切换"在 cont-splash 下只重绘帧缓冲，无法真正重初始化 DSI |

这也解释了 reports/002/003 能在真机上看到菜单的原因（复用的原厂 splash 帧缓冲）。
