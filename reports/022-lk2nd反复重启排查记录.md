# 022 — lk2nd 反复重启：排查记录与已排除的假设

日期：2026-08-30　状态：**未解决**，但已排除两条假设并找到下一步的诊断手段

---

## 一、现象

把 `/extlinux/extlinux.conf` 改名（我们进入 fastboot 的标准手法）并重启后，
设备**反复重启 lk2nd**，必须人工按住电源键才能让它停在 lk2nd 的 fastboot 界面。
无干扰的情况下几乎不可能自动进入 fastboot ⇒ 刷机/调试循环无法全自动。

**一个重要的纠偏**：早期日志里"设备进入 fastboot (30s)"那几次成功，
其实是**用户按了电源键**的结果，不是自动达成的。之前误以为自动流程已经跑通。

## 二、真机取证

```
/dev/mmcblk0p21 (boot, 64MB)
  offset 0      : "ANDROID!"   ← lk2nd 本体（fastboot 里叫 lk2nd 分区，size 0x80000）
  offset 524288 : "ANDROID!"   ← 残留的原厂 Android 引导镜像（fastboot 里叫 boot，size 0x3f80000）
```

## 三、已排除的假设

### 假设 1：lk2nd 回退引导残留的 Android 镜像 → 起不来 → 重启

据此写了 `lk2nd/0005-lk2nd-go-to-fastboot-instead-of-android.patch`：
`lk2nd/boot/boot.c` 在 `lk2nd_scan_devices()` 末尾置 `boot_into_fastboot`，
`app/aboot/aboot.c` 在 `lk2nd_boot()` 之后重新判断并 `goto fastboot`。

二进制级确认补丁**确实进了出货镜像**（`strings` 对比）：

| | 字符串 |
|---|---|
| v0.9.3 | `boot: Bootable file system not found. Reverting to android boot.` |
| v0.9.4-lk2nd-reboot | `boot: Bootable file system not found. Reverting to fastboot.` |

**但真机行为毫无变化，仍然循环。** ⇒ 假设 1 不成立，或至少不是主因。

教训：补丁进没进镜像（`strings` 能验）和补丁有没有用（行为变没变）是两回事。
只验前者会得出虚假的安全感。

### 假设 2：panic → `PANIC_REBOOT_MODE` 重启 → 重启原因读不回来 → 循环

查证链条：

| 环节 | 事实 | 出处 |
|---|---|---|
| panic 后做什么 | `platform_halt()` → `reboot_device(PANIC_REBOOT_MODE)` | `platform/msm_shared/debug.c:182-189` |
| 该模式是什么 | `PANIC_REBOOT_MODE ?= FASTBOOT_MODE` | `lk2nd/project/lk2nd.mk:20` |
| 走哪条分支 | `USE_PON_REBOOT_REG=1` ⇒ 写 PON 寄存器 | `project/msm8953.mk:147` |
| 写入方式 | `value = REG_READ(PON_SOFT_RB_SPARE); value \|= (reason << 2); REG_WRITE(...)` | `reboot.c:128-131` |
| `FASTBOOT_MODE` 的值 | `0x02`（`USE_PON_REBOOT_REG` 分支下的枚举） | `reboot.h:35-38` |
| 读回函数 | **`check_hard_reboot_mode()` 有真实实现**，读 `PON_SOFT_RB_SPARE`，返回 `(v & 0xFC) >> 2`，且读后擦除 | `platform/msm_shared/reboot.c:84-95` |
| 是否参与编译 | `reboot.o` 仅在 `ENABLE_REBOOT_MODULE=1` 时编入；msm8953 确实设了 | `rules.mk:714`、`project/msm8953.mk:127,144` |

⇒ **读回路径是完整的**，假设 2 不成立。

期间走过的弯路：`grep check_hard_reboot_mode` 时加了 `grep -i 8953` 过滤，
把 `platform/msm_shared/reboot.c` 里的实现滤掉了，一度误判成"只有弱实现"。
**查东西时别用想当然的过滤条件先剪枝。**

## 四、顺带确认的其它事实

- `WITH_LK2ND_BOOT` 全树只在 `app/aboot/aboot.c` 出现 4 次，**没有任何 .mk 定义它**。
  但系统确实靠 extlinux 启动，所以 `#if WITH_LK2ND_BOOT` 应该为真 ——
  这个矛盾尚未查清（可能是 LK 构建系统的 DEFINES 机制间接注入）。
  **注意**：0005 补丁就写在这个 `#if` 块里，如果该宏为假，补丁就是死代码。
  这可以解释它为什么毫无效果，是下一步要优先确认的点之一。
- 另一处 `lk2nd_boot()`（`aboot.c:4674`，在 `target_is_emmc_boot()` 分支内）
  同样会回退 Android 镜像，0005 未改，已在该补丁说明中注明。
- `target/msm8953/init.c:81-83` 残留一套**旧式魔数**（`FASTBOOT_MODE 0x77665500`、
  `RECOVERY_MODE 0x77665502`），与 `reboot.h` 里 `USE_PON_REBOOT_REG` 分支的
  `FASTBOOT_MODE 0x02` 是**两套不同的约定**。`init.c` 未 include `<reboot.h>`，
  所以不冲突，但也说明这块代码是拼起来的、状态不清。

## 五、下一步：做诊断构建，让 panic 信息留在屏幕上

现在缺的是**现场信息**。设备一 panic 就重启，`dprintf(CRITICAL, ...)` 一闪而过，
用户看不清（串口也没接）。

**把 `PANIC_REBOOT_MODE` 设成 `NO_REBOOT`**：

```make
# lk2nd/project/lk2nd.mk:20
PANIC_REBOOT_MODE ?= NO_REBOOT
```

`platform_halt()` 此时会走到 `dprintf(CRITICAL, "HALT: spinning forever...")` 并**停住不重启**。
于是 panic 原因会**留在屏幕上**，用户可以直接读（或拍照）。拿到那行字，
就能知道到底是什么在 panic——这比继续猜有效得多。

代价：这一版是**纯诊断用**，不能日常使用（会卡死，要长按电源）。

## 六、为什么这件事迭代成本高

每验证一次 lk2nd，都要：
1. 本地/CI 编出 lk2nd → 刷入（需要先在 fastboot 里）
2. 而进入 fastboot 恰恰是坏掉的那一步 ⇒ **每次都要用户按电源键**

这就是"修它"和"用它"互相卡住的鸡生蛋问题。诊断构建能一次性拿到最多信息，
比一次次盲改划算。
