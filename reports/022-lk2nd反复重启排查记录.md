# 022 — lk2nd 反复重启：排查记录与已排除的假设

日期：2026-08-30　状态：**未解决**，但已排除两条假设并找到下一步的诊断手段

---

## 一、现象

把 `/extlinux/extlinux.conf` 改名（我们进入 fastboot 的标准手法）并重启后，
设备**反复重启 lk2nd**，必须人工按住电源键才能让它停在 lk2nd 的 fastboot 界面。
无干扰的情况下几乎不可能自动进入 fastboot ⇒ 刷机/调试循环无法全自动。

**一个重要的纠偏**：早期日志里"设备进入 fastboot (30s)"那几次成功，
其实是**用户按了电源键**的结果，不是自动达成的。之前误以为自动流程已经跑通。

## 二、真机取证

```
/dev/mmcblk0p21 (boot, 64MB)
  offset 0      : "ANDROID!"   ← lk2nd 本体（fastboot 里叫 lk2nd 分区，size 0x80000）
  offset 524288 : "ANDROID!"   ← 残留的原厂 Android 引导镜像（fastboot 里叫 boot，size 0x3f80000）
```

## 三、已排除的假设

### 假设 1：lk2nd 回退引导残留的 Android 镜像 → 起不来 → 重启

据此写了 `lk2nd/0005-lk2nd-go-to-fastboot-instead-of-android.patch`：
`lk2nd/boot/boot.c` 在 `lk2nd_scan_devices()` 末尾置 `boot_into_fastboot`，
`app/aboot/aboot.c` 在 `lk2nd_boot()` 之后重新判断并 `goto fastboot`。

二进制级确认补丁**确实进了出货镜像**（`strings` 对比）：

| | 字符串 |
|---|---|
| v0.9.3 | `boot: Bootable file system not found. Reverting to android boot.` |
| v0.9.4-lk2nd-reboot | `boot: Bootable file system not found. Reverting to fastboot.` |

**但真机行为毫无变化，仍然循环。** ⇒ 假设 1 不成立，或至少不是主因。

教训：补丁进没进镜像（`strings` 能验）和补丁有没有用（行为变没变）是两回事。
只验前者会得出虚假的安全感。

### 假设 2：panic → `PANIC_REBOOT_MODE` 重启 → 重启原因读不回来 → 循环

查证链条：

| 环节 | 事实 | 出处 |
|---|---|---|
| panic 后做什么 | `platform_halt()` → `reboot_device(PANIC_REBOOT_MODE)` | `platform/msm_shared/debug.c:182-189` |
| 该模式是什么 | `PANIC_REBOOT_MODE ?= FASTBOOT_MODE` | `lk2nd/project/lk2nd.mk:20` |
| 走哪条分支 | `USE_PON_REBOOT_REG=1` ⇒ 写 PON 寄存器 | `project/msm8953.mk:147` |
| 写入方式 | `value = REG_READ(PON_SOFT_RB_SPARE); value \|= (reason << 2); REG_WRITE(...)` | `reboot.c:128-131` |
| `FASTBOOT_MODE` 的值 | `0x02`（`USE_PON_REBOOT_REG` 分支下的枚举） | `reboot.h:35-38` |
| 读回函数 | **`check_hard_reboot_mode()` 有真实实现**，读 `PON_SOFT_RB_SPARE`，返回 `(v & 0xFC) >> 2`，且读后擦除 | `platform/msm_shared/reboot.c:84-95` |
| 是否参与编译 | `reboot.o` 仅在 `ENABLE_REBOOT_MODULE=1` 时编入；msm8953 确实设了 | `rules.mk:714`、`project/msm8953.mk:127,144` |

⇒ **读回路径是完整的**，假设 2 不成立。

期间走过的弯路：`grep check_hard_reboot_mode` 时加了 `grep -i 8953` 过滤，
把 `platform/msm_shared/reboot.c` 里的实现滤掉了，一度误判成"只有弱实现"。
**查东西时别用想当然的过滤条件先剪枝。**

## 四、顺带确认的其它事实

- `WITH_LK2ND_BOOT` 全树只在 `app/aboot/aboot.c` 出现 4 次，**没有任何 .mk 定义它**。
  但系统确实靠 extlinux 启动，所以 `#if WITH_LK2ND_BOOT` 应该为真 ——
  这个矛盾尚未查清（可能是 LK 构建系统的 DEFINES 机制间接注入）。
  **注意**：0005 补丁就写在这个 `#if` 块里，如果该宏为假，补丁就是死代码。
  这可以解释它为什么毫无效果，是下一步要优先确认的点之一。
- 另一处 `lk2nd_boot()`（`aboot.c:4674`，在 `target_is_emmc_boot()` 分支内）
  同样会回退 Android 镜像，0005 未改，已在该补丁说明中注明。
- `target/msm8953/init.c:81-83` 残留一套**旧式魔数**（`FASTBOOT_MODE 0x77665500`、
  `RECOVERY_MODE 0x77665502`），与 `reboot.h` 里 `USE_PON_REBOOT_REG` 分支的
  `FASTBOOT_MODE 0x02` 是**两套不同的约定**。`init.c` 未 include `<reboot.h>`，
  所以不冲突，但也说明这块代码是拼起来的、状态不清。

## 五、下一步：做诊断构建，让 panic 信息留在屏幕上

现在缺的是**现场信息**。设备一 panic 就重启，`dprintf(CRITICAL, ...)` 一闪而过，
用户看不清（串口也没接）。

**把 `PANIC_REBOOT_MODE` 设成 `NO_REBOOT`**：

```make
# lk2nd/project/lk2nd.mk:20
PANIC_REBOOT_MODE ?= NO_REBOOT
```

`platform_halt()` 此时会走到 `dprintf(CRITICAL, "HALT: spinning forever...")` 并**停住不重启**。
于是 panic 原因会**留在屏幕上**，用户可以直接读（或拍照）。拿到那行字，
就能知道到底是什么在 panic——这比继续猜有效得多。

代价：这一版是**纯诊断用**，不能日常使用（会卡死，要长按电源）。

## 六、为什么这件事迭代成本高

每验证一次 lk2nd，都要：
1. 本地/CI 编出 lk2nd → 刷入（需要先在 fastboot 里）
2. 而进入 fastboot 恰恰是坏掉的那一步 ⇒ **每次都要用户按电源键**

这就是"修它"和"用它"互相卡住的鸡生蛋问题。诊断构建能一次性拿到最多信息，
比一次次盲改划算。

## 七、与 pmOS 版的差异对比（2026-08-30 补充）

pmaports 在 **GitLab**（不是 GitHub）：`https://gitlab.com/postmarketOS/pmaports`
（`main/lk2nd/APKBUILD`）。

`_build()` 的实际命令：

```sh
make LK2ND_VERSION="$pkgver-r$pkgrel-postmarketos" TOOLCHAIN_PREFIX=arm-none-eabi- <project>
```

msm8953 那一行是 `_build lk2nd-msm8953` —— **没有任何额外选项**。
（对比：`msm8952-xiaomi-land` 传了 `LK2ND_DTBS=`、`LK2ND_ADTBS=`；
  `msm8226-htc-memul` 传了 `SCRATCH_ADDR` 等；msm8953 是裸的。）

⇒ **差异不在编译选项**。剩下的只有两处：

| 维度 | pmOS 版 | 我们的 |
|---|---|---|
| 版本 | master 上是 19.0；设备原厂那份是 **21.0-r0** | **23.1** |

所以嫌疑集中在：**21.0 → 23.1 之间的行为变化**，或**我们的 0001/0003 改的

注：设备上原厂那份的版本串来自 `evidence/live-device-backup/STATE.txt`：
`project = lk2nd-msm8953`、`version = 21.0-r0-postmarketos`。

## 八、诊断构建（进行中）

新增 `lk2nd/0006-lk2nd-DIAGNOSTIC-halt-on-panic.patch`：

```diff
-PANIC_REBOOT_MODE ?= FASTBOOT_MODE
+PANIC_REBOOT_MODE ?= NO_REBOOT
```

`NO_REBOOT` 在 `debug.c:172` 是 `(~0U)`，`platform_halt()` 的判断
`if (PANIC_REBOOT_MODE != NO_REBOOT)` 因此为假，落到打印后 `for(;;)` 停住。
panic 原因会留在屏幕上。

用 `workflow_dispatch` 触发 CI 编出产物（不建 Release，避免污染版本号）。

## 九、★ 21.0 与 23.1 的决定性差异（2026-08-30，用户建议对比版本）

先量化两个版本的差异（只列与本次排查相关的文件）：

| 文件 | 21.0 vs 23.1 |
|---|---|
| `lk2nd/boot/boot.c` | **相同** |
| `platform/msm_shared/reboot.c` | **相同** |
| `target/msm8953/init.c` | **相同** |
| `target/msm8953/rules.mk` | **相同** |
| `project/msm8953.mk` | **相同** |
| `lk2nd/boot/extlinux.c` | 有变化（688 → 710 行） |
| `app/aboot/aboot.c` | 有变化（5781 → 5782 行） |
| **`lk2nd/project/lk2nd.mk`** | **有变化（+2 行）** |
| **`platform/msm_shared/debug.c`** | **有变化（+13 行）** |

后两个正是 panic 重启机制所在。差异原文：

**`lk2nd/project/lk2nd.mk`（23.1 新增）**
```make
+PANIC_REBOOT_MODE ?= FASTBOOT_MODE
```

**`platform/msm_shared/debug.c` 的 `platform_halt()` 被重写**

21.0（无条件进 dload 模式）：
```c
dprintf(CRITICAL, "HALT: reboot into dload mode...\n");
arch_clean_cache_range(MEMBASE, MEMSIZE);
reboot_device(NORMAL_DLOAD);
```

23.1（可配置，默认 FASTBOOT_MODE）：
```c
/* Additional options not defined in reboot.h */
#define NORMAL_REBOOT	0
#define NO_REBOOT	(~0U)
...
if (PANIC_REBOOT_MODE != NO_REBOOT) {
	dprintf(CRITICAL, "HALT: reboot into " _STR(PANIC_REBOOT_MODE) "...\n");
	if (PANIC_REBOOT_MODE == NORMAL_DLOAD)
		arch_clean_cache_range(MEMBASE, MEMSIZE);
	reboot_device(PANIC_REBOOT_MODE);
}
dprintf(CRITICAL, "HALT: spinning forever...\n");
for (;;) ;
```

⇒ **21.0 根本没有"panic 后重启进 fastboot"这条路径**，`platform_halt()` 只会去
`NORMAL_DLOAD`（EDL，一个稳定终止态）。23.1 新增了该机制并默认指向
`FASTBOOT_MODE`，于是：panic → 请求 fastboot 重启 → 再 panic → 循环。

这与用户"21.0 不会循环"的观察完全吻合。

同时这也解释了 `WITH_LK2ND_BOOT` 那个疑点：
该宏全树只在 `app/aboot/aboot.c` 出现 4 次（`WITH_LK2ND_BOOT` 的使用处），
**没有任何 .mk 定义它**。而 `lk2nd/project/base.mk` 里其它 `LK2ND_*` 开关
（如 `LK2ND_FORCE_FASTBOOT`、`LK2ND_FASTBOOT_DELAY`、`DEBUG_FBCON`）都有明确的
`ifeq (...) DEFINES += ...` 处理，唯独它没有。
⇒ 0005 补丁（写在 `#if WITH_LK2ND_BOOT` 块里）极可能是**死代码**，
这解释了它为什么对行为毫无影响。

### 待验证：这条循环到底是不是 panic

`NO_REBOOT` 版（0006）能一次性判定：
- **设备停住不重启** → 确认是 panic，屏幕上的字会指出原因
- **仍然循环** → 不是 panic，是 boot 分区 512KB 处那个残留 Android 镜像
  被引导后自己重启（那就得走 21.0 或 `fastboot erase boot`）

### 两个备选方案

| 路线 | 改动 | 风险 |
|---|---|---|
| A. 留在 23.1，改 `PANIC_REBOOT_MODE` | 一行（`NO_REBOOT` 或 `NORMAL_DLOAD`） | 小；但若真凶不是 panic 则无效 |
| B. 退回 21.0 | 需按 21.0 的设备表**重新生成** 0001-0004（WORKLOG 记过：21.0 设备表条目与 23.x 不同，原补丁会 `Hunk #1 FAILED`） | 中；但能回到用户验证过不循环的基线 |

用户已同意先试 A。
