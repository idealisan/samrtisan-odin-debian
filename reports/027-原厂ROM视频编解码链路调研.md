## 0. 结论速览

| 项 | 结论 |
|---|---|
| **venus 固件在哪** | **只在 modem 分区（`NON-HLOS.bin`）里**，路径 `/IMAGE/VENUS.MDT` + `VENUS.B00`~`B04`。system 分区里**一个 venus 固件都没有**（`/vendor/firmware` 只有 `libpn548ad_fw.so`，`/etc/firmware` 只有 `cpp_firmware_v1_*.fw` 这类摄像头固件）。 |
| **怎么拿到** | `NON-HLOS.bin` 是**裸 FAT16**（不是 MBN 容器），可直接只读解析。本仓库工具：`tmp/rom-video-probe/fat16ls.py` / `fat16extract.py`。 |
| **固件身份** | **Venus 3xx（固件内字符串 `Venus332` / `Venus3AdjustDefaultCfg_3332`）**，HFI 3xx，PAS_ID=9，签名日期 2018-05-22，HW_ID `000460E100110022`，DEBUG=2。DTB 里 `qcom,hfi-version = "3xx"` 与之吻合。 |
| **原厂 venus 内存** | `venus_region@0`：shared-dma-pool / **reusable** / **size 8 MiB** / **alloc-ranges 0x80000000..0x90000000** / align 4 MiB。挂在**独立的 PIL 设备 `qcom,venus@1de0000`** 上，**不是**挂 vidc 节点上。 |
| **主线现在的内存** | `&venus_mem` = **no-map / 固定 0x91400000 / 7 MiB**，挂在 venus 自己身上。**地址窗口与原厂完全不重叠。** |
| **declared 能力** | 解码到 4K30（hevc/h264/vp8/vp9），编码到 4K30（hevc/h264）+ 1080p30（mpeg4/vp8）+ 864x480（h263）。全部带 `.secure` 变体。 |
| **关键差异** | ① 固件内存窗口/大小不符；② 主线无 PIL 代理投票 + **OPP 表压根没挂上**；③ 主线走 `use_tz` 的 SCM PAS 路径。详见 §7。 |

## 1. venus 固件：位置、格式、提取方法

### 1.1 `NON-HLOS.bin` 是裸 FAT16，不是 MBN 容器

```
偏移 0x0  BPB: "MSDOS5.0"  FAT16  label="NO NAME"
  bytes/sector = 512        sectors/cluster = 32 (16 KiB)
  reserved     = 1          num FATs = 2      sectors/FAT = 24
  root entries = 512        total sectors = 0x30000 = 196608 (正好 100 MiB)
  FAT1 @ 0x200   根目录 @ 0x6200   数据区 @ 0xA200
```

不需要 `pil-splitter` 之类的工具，标准 FAT16 解析即可。本仓库已有只读实现：

```sh
# 列目录
python3 tmp/rom-video-probe/fat16ls.py      <ROM>/NON-HLOS.bin image
# 抽文件
python3 tmp/rom-video-probe/fat16extract.py <ROM>/NON-HLOS.bin image/venus.mdt out/

# 或者直接在 macOS 上只读挂载（等价，未在本机尝试）
hdiutil attach -readonly -imagekey diskimage-class=CRawDiskImage <ROM>/NON-HLOS.bin
```

根目录只有两个子目录：`VERINFO`、`IMAGE`。`IMAGE` 即 `/image/`（与真机 modem 分区内的
`/image/` 一一对应）。

### 1.2 venus 固件文件清单（原汁原味的偏移 / 大小 / md5）

`<ROM>/NON-HLOS.bin` → `/IMAGE/`：

| `VENUS.B00` | 3741 | `0x3A76200` (61,301,248) | 212 | `3ae53e72639241af332066d4acc04bd4` |
| `VENUS.B01` | 3742 | `0x3A7A200` (61,317,632) | 6,600 | `6349df477c3bb07cf3f1d078d815eb44` |
| `VENUS.B02` | 3743 | `0x3A7E200` (61,334,016) | 903,464 | `f9fb73a1eeab7434fe8a204060176e73` |
| `VENUS.B03` | 3799 | `0x3B5E200` (62,251,520) | 29,048 | `42a9b3b157465aa7cb0bc631528b2400` |
| `VENUS.B04` | 3801 | `0x3B66200` (62,284,288) | **32** | `0d68af0904dd698b16ffc9cd28b9b0c8` |
| `VENUS.MDT` | 3802 | `0x3B6A200` (62,300,672) | 6,812 | `afb361669ab2ae3d92c94d101e1db72b` |

同目录下的兄弟固件（供对照）：`ADSP.*`(B00~B13)、`WCNSS.*`、`GFX.*`、`CMNLIB(64).*`、
`CPPF.*`、`WIDEVINE.*`、`MBA.MBN`、`QDSP6M.QDB`、`CPE_9335.*`、`GOODIXFP.*`、`SMPLAP(32|64).*`。

### 1.3 `VENUS.MDT` 的段布局（决定主线 `venus_mem` 需要多大）

ELF32 / machine 0x28 (ARM) / 5 个 program header：

```
[i] type    off        vaddr      paddr      filesz   memsz     align
[0] 0x0     0x0        0x0        0x0        212      0x0       0x0      ← 哈希段 (.b00)
[1] 0x0     0x1000     0xfa00000  0xfa00000  6600     0x2000    0x1000
[2] 0x1     0x3000     0x0        0xf500000  903464   0xdc928   0x100000 ← 主代码 (.b02)
[3] 0x1     0xdf928    0x100000   0xf600000  29048    0x3f0000  0x100000 ← .b03
[4] 0x1     0xe6aa0    0x4ff000   0xf9ff000  32       0x20      0x4      ← .b04（填充）
```

- 最小 paddr = `0xF500000`，最大末端 = `0xFA02000`
- **`qcom_mdt_get_size()` = `0x502000` = 5,251,072 B = 5.008 MiB**

主线 `firmware.c` 的准入条件：

```c
if (*mem_size < fw_size || fw_size > VENUS_FW_MEM_SIZE)   /* VENUS_FW_MEM_SIZE = 6*SZ_1M */
```

5.008 MiB < 6 MiB ⇒ 尺寸检查能过；7 MiB 的 `venus_mem` 也够。**所以"固件大小不够"这条可以先排除**
（真不够会报 `fail to load video firmware`，不是现在的 `Unsupported property`）。

### 1.4 签名 / 版本线索

`VENUS.MDT` 与 `VENUS.B01` 尾部是标准的 MBN 签名证书链（X.509 DER + 签名）：

```
01 000000000000000E SW_ID
02 000460E100110022 HW_ID        ← msm8953 硬件 ID
03 0000000000000002 DEBUG        ← 2 = debug/未上锁
04 0011 OEM_ID
05 000000C8 SW_SIZE
06 0022 MODEL_ID
07 0001 SHA256
CA: "SANDIEGO" / "General OEM rootca" / "OEM attestation CA" / "SecTools Test User"
有效期: 160709095909Z ~ 360704095909Z（CA）
签名时间: 180522164848Z                        ← 2018-05-22 16:48:48
```

`VENUS.B02`（真正的固件代码）里的版本字符串：

```
Venus3
Venus332
Venus3AdjustDefaultCfg_3332
```

源码文件名（说明这是 Venus 3xx 的 host driver 代码）：

```
venus_firmware.c  venusCoreController.c  VenusHostDriver.c  venus_hfi_queue.c
venus_hw_reset.c  venus_ocmem.c  venus_reg_shared.c  venus_diag.c  venus_common.c
venus_venc_h265.c  venus_venc_hal.c  venus_venc_rate_control.c  venus_venc_bitstream.c
VenusCoreCtrl  VenusRoundRobinTask  VenusSignal
VENUS_FW_STACK_CHK
```

固件支持的 HFI 属性（抽样，说明这是功能完整的 Venus 3xx HFI 栈）：

```
HFI_CMD_SYS_INIT            HFI_CMD_SYS_RELEASE_RESOURCE
HFI_MSG_SYS_PROPERTY_INFO   HFI_PROPERTY_SECURE_SESSION
HFI_PROPERTY_PARAM_CODEC_SUPPORTED(隐含)  HFI_PROPERTY_PARAM_BUFFER_COUNT_ACTUAL
HFI_PROPERTY_PARAM_UNCOMPRESSED_FORMAT_SELECT
HFI_PROPERTY_PARAM_PROFILE_LEVEL_SUPPORTED(隐含)
HFI_VIDEO_DOMAIN_DECODER    HFI_RESOURCE_OCMEM
HFI_COLOR_FORMAT_NV12 / NV12_UBWC / NV21 / NV12_4x4TILE
HFI_BUFFER_OUTPUT2          HFI_CTRL_INIT_CLK_DN
```

> 没有找到 `VIDC-` 开头的版本串，也没有 build_id。`Venus332` + `Venus3AdjustDefaultCfg_3332`
> 是目前能拿到的最强版本证据，与 DTB 的 `qcom,hfi-version = "3xx"` 一致。

### 1.5 system 分区里确实没有 venus 固件（已确认）

```
/vendor/firmware/  →  只有 libpn548ad_fw.so            （NFC）
/etc/firmware/     →  只有 cpp_firmware_v1_*.fw 等      （摄像头 CPP）
/vendor/etc/       →  没有任何 media_codecs / media_profiles
```

**结论：venus 固件只能来自 modem 分区。真机上的 `/dev/disk/by-partlabel/modem` 的
`/image/` 目录，与 `NON-HLOS.bin` 的 `/IMAGE/` 是同一份东西。**

## 6. 顺带：system_*.img 的正确打开方式（踩坑记录）

任务描述里说 `system_*.img` 是"未压缩的 squashfs 分块，可以直接 grep"。**这个前提是错的**，
值得记下来，免得下次再绕路：

1. **它们是 ext4，不是 squashfs。**
   `system_1.img` 偏移 0x400 有一个标准 ext4 超级块：
   `inodes=193920 blocks=774155 log_bs=2 (4 KiB) inodes_per_group=8080
    blocks_per_group=32768 inode_size=256 groups=24 incompat=0x42 (FILETYPE|EXTENTS)
    ro_compat=0x13 (SPARSE_SUPER|LARGE_FILE|HUGE_FILE) volume="system"`

2. **直接按文件名数字顺序拼接是错的 —— chunk 之间有空洞。**
   36 个文件合计 3,096,330,240 B，但 fs 声明 774,155 块 = 3,170,938,880 B。
   按数字顺序拼完，根目录的 extent 指向 block 766,269，落在数据之外，解不出来。

3. **真正的布局在 `rawprogram_unsparse.xml` 的 `start_sector` 里。**
   （注意：同一个文件里的 `num_partition_sectors` 是**错的**，和文件大小对不上，别用。）

   | chunk 之间 | gap |
   |---|---|
   | 大 chunk 之后 | 2,068,480 B（505 块） |
   | 大 chunk 之后（另一档） | 782,336 B（191 块） |
   | `system_30` 之后 | 73,334,784 B（17,904 块，大空洞） |

   8 KiB 的那些 chunk（system_2/5/8/11/14/17/23/25/29/31/33/35）正好落在各 group 的
   **block bitmap + inode bitmap**（2 个块 = 8192 B）上——这是典型的 Android sparse 图特征。

   按 `start_sector` 重建后：总长 **3,221,225,472 B = 正好 3.000 GiB**（system 分区大小），
   group 1/3/5/7/9 的 5 个备份超级块**全部校验通过**，根目录正常读出。✅

4. 工具：`tmp/rom-video-probe/ext4map.py`（读 XML 建映射）+ `ext4ro.py`（只读 ext4）
   + `sysfs.py`（ls / cat / find）。**全程只读，不拼接、不落 3 GB 临时文件。**

```sh
python3 tmp/rom-video-probe/sysfs.py ls  /vendor/firmware
python3 tmp/rom-video-probe/sysfs.py cat /etc/media_codecs.xml  out.xml
python3 tmp/rom-video-probe/sysfs.py find omxv /lib
```

### 7.1 报错点的语义

调用链 `core.c:472 → hfi_core_init() → 等 HFI_MSG_SYS_INIT_DONE → hfi_msgs.c:276`：

```c

if (error != HFI_ERR_NONE) goto done;                    /* 固件报的 error_type == 0，正常 */
if (!pkt->num_properties) { error = …INVALID_PARAMETER; } /* num_properties != 0 */
```

**关键推论**：这不是"固件没起来导致超时"。超时会走 `wait_for_completion_timeout`
并报 -ETIMEDOUT。既然走到了 `hfi_parser` 并且 `error_type == 0`、
`num_properties != 0`，说明**固件确实回了 SYS_INIT_DONE 包**，只是包的
payload 第一个 u32 是 0 —— 也就是 **payload 是空的 / 被零填充的**。

（`struct hfi_pkt_hdr { u32 size; u32 pkt_type; }` 8 字节，与下游 `vidc_hal_hdr` 一致；
`hfi_msg_sys_init_done_pkt` = hdr + error_type + num_properties + data[] = 16 字节头，
结构对齐没问题，不是结构体偏移错位。）

### 7.2 嫌疑 ①：venus 固件的内存窗口跟原厂不符（最高嫌疑）

| | 原厂 | 主线 6.19 (`msm8953.dtsi`) |
|---|---|---|
| 大小 | **8 MiB** (`size = <0 0x800000>`) | **7 MiB** (`reg = <0 0x91400000 0 0x700000>`) |
| 地址 | **动态**，alloc-ranges **0x80000000..0x90000000** | **固定 0x91400000**（在原厂是 splash 之后的空白区） |
| 属性 | `shared-dma-pool` + **`reusable`** | `no-map` |
| 归属 | 独立的 PIL 设备 `qcom,venus@1de0000` | venus 节点自己 |

固件实际跨度 0x502000 = 5.008 MiB，两边都装得下，
**但地址窗口完全不重叠**。TZ（SBL）对 venus PAS 的可加载地址白名单是写死在 TZ 镜像里的，
原厂把 venus 固件池严格圈在 `0x80000000..0x90000000`（和 `gpu_region` 共用同一窗口）。
主线把它搬到 `0x91400000` 之后：

- 如果 TZ 拒绝 → 会报 `qcom_scm_pas_auth_and_reset` 错误（不是现在这个错）
- 如果 TZ **接受但把 ARM9 的取指地址算错** → ARM9 跑飞 → HFI 队列里是全 0 →
  `num_properties != 0` 但 `data[0] == 0` → **`Unsupported property: 0`** ✅ 与现象吻合

**建议验证**：把 `venus_mem` 改成跟原厂一致的参数试试：

```dts
/ {
	reserved-memory {
		venus_mem: venus@91400000 {   /* 改名/改属性 */
			compatible = "shared-dma-pool";
			reusable;
			alloc-ranges = <0x0 0x80000000 0x0 0x10000000>;
			alignment = <0x0 0x400000>;
			size = <0x0 0x800000>;
		};
	};
};
```

### 7.3 嫌疑 ②：主线走 `use_tz` 的 SCM PAS，且 OPP 表压根没挂上

**(a) `use_tz = true`（firmware.c:314）**

```c
np = of_get_child_by_name(core->dev->of_node, "video-firmware");
if (!np) { core->use_tz = true; return 0; }     /* msm8953.dtsi 里没有 video-firmware 子节点 */
```

于是走 `qcom_scm_pas_auth_and_reset(VENUS_PAS_ID /* 9 */)` +
`qcom_scm_mem_protect_video_var(0, 0x5dc00000, 0x1000000, 0x24800000)`。
PAS_ID 9 与原厂 `qcom,pas-id = <0x09>` 一致 ✅；
`cp_size = 0x5dc00000` 正好等于原厂 `venus_ns` 的 pool[0]，
`cp_nonpixel_* = 0x1000000 / 0x24800000` 正好等于原厂 `venus_sec_non_pixel` 的 pool ✅
（这两个值主线是从原厂 DT 抄过来的，对得上）。

**但原厂 PIL 设备额外做了三件主线完全没做的事**：

| 原厂 PIL 做的事 | 主线 |
|---|---|
| `scm_core_clk_src` 钉 **80 MHz**（`qcom,scm_core_clk_src-freq = <0x4c4b400>`） | 无 |
| 7 个代理时钟（多出 `scm_core_clk` / `scm_iface_clk` / `scm_bus_clk`） | 只有 3 个 |
| `qcom,msm-bus` 投票 **304,000 KBps**（`0x3f → 0x200`） | 走 `interconnects`，值不同 |
| `qcom,proxy-timeout-ms = 100` | 无 |

**(b) OPP 表是个孤儿（这是实打实的上游 bug）**

`msm8953.dtsi` 定义了 `venus_opp_table`（114.29 / 228.57 / 310 / 360 / 400 / 465 / **540** MHz），
但**整个 venus 节点里没有 `operating-points-v2 = <&venus_opp_table>`**。
对照组：sdm845 / sc7180 / agatti / talos / kodiak **全都写了这一行**，
**只有 msm8953 漏了**。

而且 `msm8953_res` **没有 `.opp_pmdomain` 成员**，所以
`pm_helpers.c:1000` 的这段**根本不会执行**：

```c
if (core->res->opp_pmdomain) {          /* msm8953 为 NULL → 整段跳过 */
	ret = devm_pm_opp_of_add_table(dev);
	…
}
```

连锁后果：

```c
/* core_clks_enable()  pm_helpers.c:41 */
opp = dev_pm_opp_find_freq_ceil(dev, &freq);
if (IS_ERR(opp)) {                       /* ← 必然走到这里 */
	if (!freq_tbl) return -ENODEV;
	freq = freq_tbl[freq_tbl_size - 1].freq;   /* freq_tbl 还是 sdm660_freq_table（源码带 FIXME） */
} else { dev_pm_opp_put(opp); }

for (i = 0; i < res->clks_num; i++) {
	if (IS_V6(core) || (IS_V4(core) && is_lite(core))) {
		ret = clk_set_rate(core->clks[i], freq);   /* ← msm8953 是 V3，不会调！ */
		…
	}
	ret = clk_prepare_enable(core->clks[i]);
}
```

**⇒ msm8953 的 venus 核心时钟在初始化阶段完全不设频率，跑在 bootloader 默认值上。**
如果默认值很低，ARM9 会跑得极慢，HFI 握手可能读到还没写完的队列内容（全 0）。

**建议验证/修复**：给 `msm8953.dtsi` 的 venus 节点补上
`operating-points-v2 = <&venus_opp_table>;`，并核对
`/sys/kernel/debug/clk/gcc_venus0_vcodec0_clk/clk_rate` 的实际值
（原厂可用档位：114.29 / 228.57 / 310 / 360 / 400 / 465 MHz）。

### 7.4 嫌疑 ③：固件文件本身不对（成本最低，先验掉）

主线 `venus_boot()`：

```c
ret = of_property_read_string_index(dev->of_node, "firmware-name", 0, &fwpath);
if (ret) fwpath = core->res->fwname;      /* "venus.mdt" —— 源码里带着 /* FIXME */ */
```

需要 `/lib/firmware/` 下有 `venus.mdt` + `venus.b00` … `venus.b04`，
**逐字节对一遍 §1.2 的表**（尤其 `venus.b04` 只有 32 字节，是 `0xdeadadd0` 填充，
极容易被当成空文件丢掉）。真机上：

```sh
md5sum /lib/firmware/venus.*
# 应为
# 3ae53e72639241af332066d4acc04bd4  venus.b00     (212)
# 6349df477c3bb07cf3f1d078d815eb44  venus.b01    (6600)
# f9fb73a1eeab7434fe8a204060176e73  venus.b02  (903464)
# 42a9b3b157465aa7cb0bc631528b2400  venus.b03   (29048)
```

### 7.5 已排除（别再重复）

| 项 | 为什么排除 |
|---|---|
| 固件尺寸超过 `venus_mem` | 固件 5.008 MiB < 7 MiB，也 < `VENUS_FW_MEM_SIZE` 6 MiB。真超了会报 `fail to load video firmware` |
| `qcom,reg-presets` 不对 | 原厂 `<0xe0020 0x5555556 0xe0024 0x5555556 0x80124 0x03>` 与主线 `msm8953_reg_preset[]` **完全一致** |
| IOMMU context 选错 | 主线 `iommus = <&apps_iommu 0x16>`，`0x16` = `0x16000 >> 12` = `iommu-ctx@16000`（base 0x1e20000 + 0x16000 = **0x1e36000**）= 原厂 `venus_ns` ✅ |
| 中断号不对 | 原厂 `<0 0x2c 0>` = GIC_SPI 44 = 主线 `GIC_SPI 44` ✅ |
| `hfi-version` 选错 | 原厂 `"3xx"`、固件里 `Venus332`、主线 `HFI_VERSION_3XX` 三者一致 ✅ |
| PAS_ID 不对 | 原厂 `qcom,pas-id = <0x09>` = 主线 `VENUS_PAS_ID 9` ✅ |
| cp_* 窗口不对 | `cp_size 0x5dc00000` / `cp_nonpixel 0x1000000+0x24800000` 与原厂 pool 完全吻合 ✅ |
| `venus_core1` 缺失 | 原厂 `gdsc_venus_core1` 是 `disabled`，主线 `vcodec_num = 1` ✅ |

### 7.6 下一步建议（按性价比排序）

1. **核对 `/lib/firmware/venus.*` 的 md5**（5 秒钟，§7.4）
2. **读时钟实际值**：`cat /sys/kernel/debug/clk/gcc_venus0_vcodec0_clk/clk_rate`，
   看看是不是异常低
3. **补 `operating-points-v2 = <&venus_opp_table>;`** 到 venus 节点（§7.3b）
4. **把 `venus_mem` 改成原厂参数**（8 MiB / reusable / alloc-ranges 0x80000000..0x10000000，§7.2）
5. 真机上跑原厂自测程序 `/bin/mm-vidc-omx-test`（已随 ROM 提供）做交叉验证
6. 打开 `hfi_parser.c` 的动态调试，把 SYS_INIT_DONE 包的原始 16+ 个 word 打出来，
   确认 payload 到底是全 0 还是有别的内容
