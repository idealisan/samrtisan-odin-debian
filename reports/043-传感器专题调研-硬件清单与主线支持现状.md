### 1.2 真机 i2c 扫描（决定性证据）

在真机装 `i2c-tools` 后逐总线扫描：

```
i2c-0 (= 78b7000)：只有 0x38  ← 触摸屏
i2c-1 (= 7af6000)：只有 0x25  ← FUSB301
```

**我方 DTB 只开了 2 条 i2c**，另外 6 条全是 `status=disabled`：
`7af5000`、`7af7000`、`7af8000`、`78b5000`、`78b6000`、`78b8000`。

**两个直接结论：**
1. **没扫到任何加速度 / 陀螺 / 地磁 / 光感 / 距离 / 霍尔。**
2. 但注意 —— 原厂说 i2c_3 上还有 `0x29`(tcs3400) 和 `0x44`(nxu8010)，
   我们的 i2c-0 就是 78b7000（i2c_3），**这条总线我们开着，却只扫到 0x38**
   ⇒ **这两颗芯片在这台机器上大概率没焊**（或没供电）。

## 二、逐项结论

### 2.1 加速度 / 陀螺 / 地磁 / 光感 / 距离 —— 原厂全在 SLPI 闭源固件里

证据：
- 原厂 DTS 只有一个**空壳**节点 `qcom,msm-ssc-sensors`（`msm8953.dtsi:2003-2005`）
- 它的"驱动" `drivers/sensors/sensors_ssc.c` **不是传感器驱动**，而是 **SLPI 固件加载器**：
  `slpi_boot_store()` + `__ATTR(boot)`，通过 sysfs 写 `boot` 触发加载
- 原厂 `msm8953.dtsi` 的 PIL 节点只有 `modem / adsp / venus / wcnss` 四个，**没有 slpi**
  ⇒ SLPI 是另一套加载机制，固件文件（`slpi.b*`/`slpi.mdt`）来自 vendor 分区
- 我们镜像里没有 SLPI 固件

**⇒ 这些传感器 AP 侧看不到，是因为它们挂在 SLPI 独占的通道上。**
主线上没有 SLPI 传感器固件可用，**不能走原厂那条路**。

主线能给的路只有一条：**确认芯片是否挂在 AP 可达的 i2c 上，是的话直接挂 IIO 驱动**。
这需要先把那 6 条 disabled 的 i2c 打开扫一遍 —— **这是本专题第一个该做的实验**。

### 2.2 环境光 / 色温 —— 硬件大概率不存在

原厂声明 `tcs3400@0x29`、`nxu8010@0x44`，都在 **i2c_3 = 78b7000** 上，
而这条总线我们开着、只扫到 0x38 ⇒ **两颗都没扫到**。
即便有，主线**两颗都没有驱动**（全树 grep 零命中）。替代 `tcs3472` 存在但配置关闭。

### 2.3 霍尔传感器 —— 原厂没有，硬件大概率不存在

grep `hall|cover|flip|lid` 于原厂 odin 与 msm8953 DTS，只有 `valid-status-check`、
`vbus-valid-override` 两处误命中。gpio_keys 只有音量/主页
（`u3-p1-msm8953-key-odin.dtsi:25-55`：vol_up 85/115、vol_down 86/114、key_home 87/102）。

### 2.4 GPS / GNSS —— 无独立芯片，只能走 WCNSS

证据：
- `arch/arm64/boot/dts/` 全目录 grep `gps|gnss` → **0 命中**
- WCNSS 节点存在（`msm8953.dtsi:1486-1566`，`qcom,is-pronto-v3`，iris 四路电 l7/l19/l9/l5，
  gpio 76-80，时钟 xo/rf_clk2/wcnss_m），但**里面没有任何 GNSS 子节点**，
  没有 LNA 使能、没有 GPS 专用 regulator / clock / pinctrl
- `smdtty`（`msm8953.dtsi:1388-1446`）枚举的口只有
  `APPS_FM / APPS_RIVA_BT_ACL / APPS_RIVA_BT_CMD / APPS_RIVA_ANT_CMD / APPS_RIVA_ANT_DATA /
   DATA1,4,11,21 / LOOPBACK` —— **没有 GPS 端口**
- defconfig 无 `CONFIG_GPS`、`CONFIG_QTI_*GNSS`

**⇒ 若硬件有 GPS，只能是 WCNSS/Pronto 里集成的 GNSS，靠 `wcnss.mdt` 固件 + 用户态
LOC/QMI 服务。我们已经在跑 `wcnss.mdt`（remoteproc0 running），所以这条路**理论上是通的**，
但需要移植/部署一套 QMI LOC 用户态服务，工作量大且依赖闭源固件行为。**

主线 `# CONFIG_GNSS is not set`，`GNSS_SIRF/MTK/SERIAL` 都不导出。

### 2.5 震动马达 —— **最现成的一项，直接可做**

原厂：`pmi_haptic` / `qcom,qpnp-haptic`，SPMI `pmi8950@3`，`reg <0xc000 0x100>`，
LRA 线性马达，`vmax-mv=2545`、`ilim-ma=80`、`wave-shape=sine`、`play-mode=buffer`
（`u3-p1-msm8953-haptics.dtsi:13-37`）。

主线对得上：
- 驱动：`drivers/input/misc/qcom-spmi-haptics.c:999` → `.compatible = "qcom,spmi-haptics"`
  （Kconfig `INPUT_QCOM_SPMI_HAPTICS`）
- 节点：**`pmi8950.dtsi:207-217` 已有 `pmi8950_haptics: haptics@c000`**，
  compatible `"qcom,pmi8950-haptics","qcom,spmi-haptics"`，`reg=<0xc000>`，
  中断 short/play，`HAP_PLAY_DIRECT`，默认 disabled
  ⇒ **和我们的硬件地址完全吻合，不用新建节点**

**缺口只有两个：**
1. `CONFIG_INPUT_QCOM_SPMI_HAPTICS` 在我们的配置里**一个匹配都没有** ⇒ 驱动不编译
   （依赖 `ARCH_QCOM=y`、`SPMI=y` 都已满足）
2. DTS 需要 `&pmi8950_haptics { status = "okay"; ... }`

主线 13 块 msm8953 板全部启用它（potter:217、milan:265、vince:212、mido:237、markw:285、
daisy:214、ysl:207、tissot:175、rimob:191），通行写法：
```
qcom,actuator-type = <HAP_TYPE_ERM>;
qcom,play-mode = <HAP_PLAY_DIRECT>;       /* potter 等另加 brake-pattern */
qcom,wave-play-rate-us = <5263>;
qcom,wave-shape = <HAP_WAVE_SQUARE>;
qcom,vmax-millivolt = <2600>;             /* 部分板子 */
status = "okay";
```
⚠️ 注意：原厂写的是 **LRA**（`actuator-type="lra"`、vmax 2545mV、wave sine），
而主线其它板子多是 **ERM**。我们这台是 LRA，参数要照原厂来，别照抄主线板子的 ERM。

### 2.6 指示灯 LED —— 两颗，一颗好做一颗难做

原厂 `u3-p1-msm8953-leds-odin.dtsi`（全文只有两个节点，无 GPIO，走 SPMI MPP/PWM）：

| 灯 | 位置 | compatible | 名字 / 触发 | 参数 |
|---|---|---|---|---|
| 绿 | `pmi8950@2` → `qcom,leds@a200` | `qcom,leds-qpnp` | `green`，`batter-full` → **充电指示（充满）** | `qcom,id=6`，max-current 40，mode manual，source-sel 1，mode-ctrl 0x10 |
| 蓝 | `pm8953@0` → `qcom,leds@a300` | `qcom,leds-qpnp` | `blue`，`none` → **通知灯（用户态控制）** | mode pwm，source-sel 0x0A，`pwms=<&pm8953_pwm 0 0>`，pwm-us 2400000，pwm-channel 0 |

无按键背光节点。

主线侧：
- **`qcom,leds-qpnp` 没有主线驱动**（原厂那个 `leds-qpnp.c` 是下游的）
- 主线 LPG 驱动 `drivers/leds/rgb/leds-qcom-lpg.c`，match 表含 **`qcom,pmi8950-pwm`**
  （行 1835），但**没有 `qcom,pm8953-pwm`** —— 蓝灯用的正是 pm8953 0xbc00 PWM
- 配置：`CONFIG_LEDS_QCOM_LPG=m` **已开**；`LEDS_GPIO`、`LEDS_PWM` **关**；
  `LEDS_AW2013=m`、`LEDS_ATC=m`、`LEDS_CLASS_FLASH=m`、`LEDS_CLASS_MULTICOLOR=m` 已开
- 主线 msm8953 做法：potter 用 `&atc_leds`（`qcom,leds-atc`，`pmi8950.dtsi:169-173`）；
  mido / markw 用 `&aw2013_led`（i2c `awinic,aw2013`@0x45）挂 `led@0/1/2`

**⇒ 绿灯（pmi8950 MPP）可以用 LPG 试；蓝灯（pm8953 PWM）主线 LPG 不匹配，
需要给 LPG 补 compatible 或换方案。**

### 2.7 NFC / 指纹（顺带记录）

- NFC：NXP `qcom,nq-nci` @ i2c_5 0x28，IRQ gpio17、VEN gpio16、FIRM gpio62、CLKREQ pm8953_gpios 2
- 指纹：Goodix GF3208，SPI gpio135-140。**两处异常**：节点挂在 `&soc` 下而非 `&spi_7` 下
  且无 `reg`；`spi_7`(7AF7000) 默认 `disabled` 且未被 odin 打开 ⇒ 驱动须自建 master。
  另外 `u3-p1-msm8953-idex-odin.dtsi:29/41/54` 与 `goodix-odin.dtsi:40/52/65`
  **重复定义**三个同名 pinctrl label（两者都被 `special-odin.dtsi` include），
  而 `CONFIG_FINGERPRINT_IDEX=n` —— 死代码但有隐患。

## 三点五、**重大发现：传感器都在 i2c-gpio 上，而且 pmOS 早就跑通过**

### 3.5.1 证据：`evidence/device-probe/` 里存着原厂 pmOS 系统的探测记录

之前那轮扫描的结论（"没扫到任何传感器"）**原因是错的** —— 不是硬件不存在，
是我们扫错了地方。`evidence/device-probe/08-peripherals-firmware.txt` 与
`05-hardware-full.txt` 保留了这台机器跑 **pmOS**（主机名 `u2pro`）时的实测记录：

```
--- i2c 设备与驱动绑定 ---
0-0023   name=ltr559    driver=driver        ← 光感 + 距离
0-002e   name=yas537    driver=driver        ← 地磁（Yamaha YAS537）
0-0068   name=bmi120    driver=bmi160_i2c    ← 加速度 + 陀螺（BMI120，用 bmi160 驱动）
1-0045   name=aw2013    driver=driver        ← LED 控制器
3-002d   name=s5k3l8    driver=driver        ← 摄像头
4-0036   name=ov5670    driver=driver        ← 摄像头

--- i2c adapter 映射 ---
i2c-0   i2c-gpio            ← ★ 传感器都在这条上
i2c-1   QUP I2C adapter     ← aw2013
i2c-2   QUP I2C adapter
i2c-3   Qualcomm-CCI        ← 摄像头
i2c-4   Qualcomm-CCI        ← 摄像头

--- IIO ---
iio:device1  bmi120
iio:device2  200f000.spmi:pmic@0:adc@3100
iio:device3  200f000.spmi:pmic@2:adc@3100
```

`04-dmesg-systemd.txt:210` 更给出关键一行：
```
i2c-gpio i2c-gpio: using lines 526 (SDA) and 527 (SCL)
```

### 3.5.2 为什么 BLSP 扫描一无所获

主线 msm8953 板（mido）的设备树给出了答案 —— 传感器**不在 BLSP QUP 上**，
而是挂在 **GPIO 软件模拟的 i2c** 上：
```c
/* msm8953-xiaomi-mido.dts:57-65，注释原文：
 * normally proxied via ADSP firmware. GPIOs aren't protected. */
i2c-sensors {
        compatible = "i2c-gpio";
        sda-gpios = <&tlmm 14 (GPIO_ACTIVE_HIGH|GPIO_OPEN_DRAIN)>;
        scl-gpios = <&tlmm 15 (GPIO_ACTIVE_HIGH|GPIO_OPEN_DRAIN)>;
        i2c-gpio,delay-us = <2>;   /* ~100 kHz */

        imu@68 { compatible = "bosch,bmi160"; reg = <0x68>;
                 vdd-supply = <&pm8953_l10>; vddio-supply = <&pm8953_l6>;
                 mount-matrix = "0", "1", "0",  "1", "0", "0",  "0", "0", "1"; };
        ...
};
```
**"平时由 ADSP 固件代理"** —— 这正是原厂 `sensors_ssc.c` + SLPI 那条路。
主线改用 `i2c-gpio` 让 AP 直接访问。**而 GPIO 14/15 与我们的 526/527 对得上**：
内核给 gpiochip 动态分配基址 512 ⇒ 526−512=**14**(SDA)、527−512=**15**(SCL)，
与 mido 用的 GPIO 完全一致（待实测确认）。

### 3.5.3 结论反转

| 项 | 之前的判断 | 现在的判断 |
|---|---|---|
| 加速度/陀螺 | 挂在 SLPI，主线无解 | **bmi120 @0x68，可走 i2c-gpio + bmi160 驱动（`CONFIG_BMI160_I2C` 已开 =m）** |
| 地磁 | 挂在 SLPI，主线无解 | **yas537 @0x2e，查 `CONFIG_YAMAHA_YAS530`（已开 =m）是否覆盖 537** |
| 光感/距离 | 硬件没焊 | **ltr559 @0x23，主线 `ltr501` 驱动同时支持 559（`CONFIG_LTR501` 已开 =m）** |
| 指示灯 | 难做（LPG 不匹配） | **aw2013 @0x45 是 I2C LED 控制器，主线 `LEDS_AW2013` 已开 =m，mido/markw 就这么用** |
| 环境光 tcs3400 / nxu8010 | — | 仍然没扫到，**确实没焊**，放弃 |

### 3.5.4 待确认

1. GPIO 14/15 是否是本机的 SDA/SCL（加节点后扫 0x68 看 bmi120 出不出来）
2. `aw2013` 在哪个 QUP 总线上（pmOS 记为 i2c-1）—— 开全 8 条总线扫 0x45 即知
3. `yas537` 与主线 `YAMAHA_YAS530` 驱动的匹配情况
4. 各芯片的供电（`vdd-supply` / `vddio-supply`）—— mido 用 `pm8953_l10` / `pm8953_l6`

# 六、2026-09-06 动手实测结果（**这一节是结论**；上面第四节的部分预判已被实测推翻或修正。

## 6.1 最重要的发现：BLSP 被 TrustZone 保护，乱开总线会死循环

主线 daisy 的 DTS 原话（`msm8953-xiaomi-daisy.dts:62-63`）：

```c
/*
 * We bitbang on &i2c_4 because BLSP is protected by TZ as sensors are
 * normally proxied via ADSP firmware. GPIOs aren't protected.
 */
```

翻译：传感器**物理上接在 QUP4（78b8000）的脚上**，但那组 BLSP 寄存器受 TrustZone 保护。主线驱动去访问 ⇒ 触发复位 ⇒ lk2nd 起不来 Linux ⇒ **真机无限重启**。

实测对照（同一台机器）：

| 设备树内容 | 结果 |
|---|---|
| `i2c-gpio`(GPIO 14/15) **+** `&i2c_4` enabled | ❌ 死循环（lk2nd 起不来 Linux） |
| 只开 `i2c-gpio` | ✅ 正常启动，传感器能读到数据 |

⚠️ **这个坑在 08-30 排查触摸屏时就已经记过一次**（「单独只开 i2c_3、不带任何设备节点，一样循环」），当时怀疑 TZ 但没坐实。今天坐实了：**其余没验证过的 BLSP QUP 也不要随便开，一次只能试一条。**

## 6.2 传感器总线：GPIO 14/15 —— 猜测正确，且已实测坐实

加了 `i2c-gpio`（`sda-gpios=<&tlmm 14>`、`scl-gpios=<&tlmm 15>`、`i2c-gpio,delay-us=<2>`）之后 dmesg 打出：

```
i2c-gpio i2c-sensors: using lines 526 (SDA) and 527 (SCL)
```

**与 pmOS 时代的记录一字不差**，说明这条总线就是 pmOS 用的那条。

⚠️ 顺带纠正一个我差点犯的错：原厂设备树里 `pins = "gpio12", "gpio13", "gpio14", "gpio15"; function = "blsp_uart4"` —— 12~15 在 UART 模式下是 4 根脚；I2C 只用其中 2 根（14/15），两者不矛盾。

## 6.3 三条总线的裸 I2C 扫描结果（读写两种探针，结论一致）

新镜像没网装不了 `i2c-tools`，于是交叉编译了两个小工具：

- `tmp/i2cscan2.c`（quick write 和 1 字节读都试，避免探针方式单一漏掉芯片）
- `tmp/i2cdump8.c`（读寄存器，用来辨认芯片）

结果：

| 总线 | 有应答的地址 | 说明 |
|---|---|---|
| **i2c-0（i2c-gpio，GPIO 14/15）** | **0x48、0x68** | 传感器总线 |
| i2c-1（78b7000） | 0x38、0x44 | 0x38=触摸屏；0x44 原厂标 `nxu8010` |
| i2c-2（7af6000） | 0x25 | FUSB301 |

**没有 0x23，也没有 0x2e。** 也就是说 **pmOS 那份记录里 `0-0023 ltr559`、`0-002e yas537` 对这台机器不适用** —— 我一开始照抄它填了 `liteon,ltr559@0x23`，结果驱动 probe 到一半静默失败、创建不出 IIO 设备。（教训：历史记录是线索，不是结论。）

## 6.4 0x48 是谁：STK3311A（光感 + 距离）

读 0x48 的寄存器：`0x3E = 0x15`。

主线 `drivers/iio/light/stk3310.c` 里：

```c
#define STK3310_REG_ID            0x3E
#define STK3311A_CHIP_ID_VAL      0x15
```

正好对上。走 `sensortek,stk3311`（`CONFIG_STK3310=m` 已开）。先用运行时 `new_device` 零风险验证（`tmp/test_stk3311.py`），确认能绑上、能读数，再写进设备树。

## 6.7 两个必须记下的过程教训

1. **单次启动失败不能当结论。** 我把「加 `light-sensor@48` 后起不来」当成了因果关系，后来重试一次就正常启动了 —— 那次是偶发。跟用户之前纠正我的「别凭一次结果下结论」是同一类错误。
2. **历史记录是线索不是结论。** pmOS 记录的 `ltr559@0x23`、`yas537@0x2e` 在这台机器上全都不适用，照抄只会得到一个"probe 静默失败"的假节点。

## 七、2026-09-06 夜间真机验收：震动马达 ✅、传感器 8/8 ✅、GPS（modem）差最后一步

判据（用户定的）：**任何一个真实传感器都一定有值、一定不为 0、并且会波动。**

### 7.1 震动马达 —— ✅ 通过（用户当场确认）

- 官方 sensors5 内核**确实带** `qcom-spmi-haptics`（内建，没有 .ko）。真机上第一次出现：
  `event0 name=spmi_haptics ff=107030000`（支持力反馈）。
- 触发方式：`tmp/ffvib` 走 input 子系统的 **FF_RUMBLE** 接口：
  `找到 FF 设备 /dev/input/event0 → 效果已上传 → 振 3 秒`，**用户在旁边确认"确实震动成功"**。
- ⚠️ 麦克风录音这条验证路没走通：`arecord -D plughw:CARD=smartisanodin,DEV=1` 报
  `audio open error: Invalid argument`（capture 通路没配好，与马达无关）。所以没有 RMS 数值对比证据，
  本次结论靠人耳确认。

### 7.2 传感器 —— ✅ 8/8，全部"非 0 且有波动"

| 通道 | 采样 8 次 | 结论 |
|---|---|---|
| 光感 lux | 38~39（另一次 24→31） | 非 0 且波动 |
| 距离 prox | 672~676 | 非 0 且波动 |
| 加速度 x / y / z | 402~462 / −1355~−1304 / −16170~−16096 | 非 0 且波动 |
| 陀螺 x / y / z | 2~3 / −13~−11 / −10~−8 | 非 0 且波动 |

- 重力自检：`z × scale = −16139 × 0.000598 ≈ −9.65 m/s²`（静止时应接近 9.8）—— 量级对，
  差异来自 mount-matrix 还是**照抄 daisy 的占位值**（见 7.4）。
- **关于"lux 一动不动"**：室内恒定灯光下 lux 稳定在 40 不跳，这是**环境光真的稳定**，不是传感器死了 ——
  同一时刻加速度 z 一直在 −16082~−16202 之间跳，证明传感器在正常工作。环境光一变（开灯/遮挡）lux 立刻跟着变。

### 7.3 GPS —— modem 本身通了，但 LOC 服务还没出现

完整链条见 WORKLOG「2026-09-06 夜间总结」。两个根因都已解决：

1. `mss-supply` 接错轨 —— 之前死磕 s2（RPM 轨，不能 set_voltage）。
   **正解是照抄同芯片的 Asus Zenfone 3（Snapdragon 625 = MSM8953）**：`pm8953_s1`（0.87~1.156V，覆盖 1.05V）。
2. **镜像里没有 rmtfs 用户态守护进程** —— modem 起来后靠它读写 EFS（modemst1/2）。
   以 root 跑 `rmtfs -r -P -s -o /var/lib/rmtfs`，并预先建好 4 个 EFS 文件（modem_fs1/2、modem_fsc、modem_fsg）。
   效果：崩溃计数 35 → 60 秒后仍是 35（0 次新崩溃），三个 remoteproc 全 running。

**QRTR 上的服务**（modem 真的在工作）：
```
0 CTL  1 WDS  2 DMS  3 NAS  4  5 WMS  7  8  11 12 14(RMTFS) 15 17 22 23 24 26 29 34 36 42 46 47 48 54 68 71 769
```
❗**没有 16（LOC，就是 GPS），也没有 6（PDS 老 GPS）。** 所以 modem 通了，GPS 还没通。
