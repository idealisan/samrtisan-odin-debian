# 024 — 电池与温度：pmOS 在小米 msm8953 上的全链路做法

调研日期：2026-08-31
目的：把"用户态读取 → 内核 → 硬件 → 回到用户态"整条链路摸清，作为本机电池/温度适配的依据。

---

## 0. 结论先行（三句话）

1. **没有固件**。电池/充电/温度这条链路**不涉及任何固件文件**，PMI8950 里的 FG 与 SMBC 是纯硬件状态机，
   驱动里连 `request_firmware()` 都没有。pmOS 给 markw 的固件包只有一个 GPU zap shader。
2. **驱动不在 torvalds 主线**。`pmi8994_fg.c` / `qcom-smbchg.c` 是 msm8953-mainline 的**下游补丁**，
   主线 6.19 里 grep 不到。但**我们用的就是那棵树**（`origin = msm8953-mainline/linux`），
   所以驱动已经在手里，只差 Kconfig 与设备树。
3. **本机硬件完全可用，已有铁证**：`evidence/device-probe/` 是 pmOS `6.17.7-msm8953` 跑在**本机硬件上**的实测，
   电量和 11 个温区全部读出正常值（见 §5）。现在读不到，纯粹是**我们没开**。

## 1. 电池链路全链路

```
用户态                                                                  硬件
────────────────────────────────────────────────────────────────────────────
KDE powerdevil / Phosh 电量图标
   ▲ D-Bus org.freedesktop.UPower.Device {Percentage, State, TimeToEmpty}
upowerd  ← 监听 uevent(POWER_SUPPLY_*) + 轮询 sysfs
   ▲ udevd（打 tag，power_supply core 自动发 uevent）
   │
   │  sysfs  /sys/class/power_supply/qcom-battery/{capacity,status,
   │                 voltage_now,current_now,temp,constant_charge_current_max}
   │         /sys/class/power_supply/qcom-smbchg-usb/{online,input_current_limit,usb_type}
   ▲
power_supply core（属性数组 + uevent）
   ▲
   ├── drivers/power/supply/pmi8994_fg.c   → psy 名 "qcom-battery"（:703）
   │      compatible qcom,pmi8996-fg，SPMI pmic@2 基址 0x4000
   │      读 BATT_MONOTONIC_SOC(0x009) 拿 SOC；库仑计数 + OCV 校正全在硬件里
   │
   └── drivers/power/supply/qcom-smbchg.c  → psy 名 "qcom-smbchg-usb"
          compatible qcom,pmi8996-smbchg，SPMI pmic@2 基址 0x1000
          充电路径/输入限流/OTG boost；过温时 hw_protection_trigger()（:1139）
   ▲
SPMI regmap（200f000.spmi）
   ▲
PMI8950 内部：FG gen3（库仑计数器 + SRAM 参数区）/ SMBC（充电相位状态机）
```

**电量（SOC）怎么来的**：FG gen3 在 PMIC 内部做库仑计数，驱动**只读** `BATT_MONOTONIC_SOC` 寄存器。
主线版 `pmi8994_fg.c` 对 SRAM 的全部写操作只有 4 类：SRAM 访问控制位（`MEM_INTF_IMA_CFG`、
`RIF_MEM_ACCESS_REQ`）、IACS 清错序列、JEITA 温度阈值（`TEMP_THRESHOLD 0x454`）、DMA 错误清除。
**没有任何 OCV 表 / 容量 / 内阻的写入** —— 这点与 Android 下游不同（下游会把 `qcom,battery-data`、
`qcom,pc-temp-ocv-lut` 写进 FG SRAM，我们的驱动里没有这套）。

**电池参数里真正被消费的**（其余只是给 UPower 估算剩余时间用）：

| 驱动 | 消费的属性 | 强制？ |
|---|---|---|
| FG | `charge-full-design-microamp-hours`、`voltage-min-design-microvolt`、`voltage-max-design-microvolt` | 绑定要求 `monitored-battery` |
| smbchg | `constant-charge-current-max-microamp`、`voltage-max-design-microvolt`（**必须**）、`charge-term-current-microamp` | 是 |

小米 markw 的取值（`msm8953-xiaomi-markw.dts`）：4000000 µAh / 1000000 µA / 3400000–4380000 µV。
pmOS 的 msm8953 机型（vince 4000mAh/2.5A、tissot 3080、mido 4100、daisy 4000、ysl 3080）
电压一律 3400000 / 4380000 或 4400000。**ODIN 的实际容量待确认**（见 §7）。

**没有 ac/dc psy**：smbchg 只注册 usb 一个 psy（外加 `otg-vbus` regulator）。

## 2. "固件"到底在哪一层（重点回答用户的问题）

逐条查证结果：

| 可能的含义 | 结论 | 依据 |
|---|---|---|
| 给 PMIC 加载 .mbn / .elf | **不需要**。SMBC/FG 是硬逻辑状态机，不是可编程 MCU | 对 `pmi8994_fg.c`、`qcom-smbchg.c` 全文件 grep `firmware`/`request_firmware` —— **零匹配** |
| 电池曲线 / battery profile 算固件？ | **不算内核固件**，它是 DT 数据（下游编进 dtb）或 Android `batteryd` 经 QMI 下发。**msm8953 两条都不走** | 主线版驱动不写任何 OCV/SRAM profile |
| QMI / ADSP / Modem 路径 | **不适用于 msm8953**。主线 `qcom_battmgr.c` 走 PMIC GLINK，compatible 只有 sc8180x/sc8280xp/sm8550/x1e80100，全是新平台 | msm8953 无 PMIC GLINK 节点 |
| pmOS 给 markw 装了什么固件 | **只有** `a506_zap.mdt` + `a506_zap.b02`（Adreno 506 GPU shader）。全机型范围也只有 GPU zap、WiFi `WCNSS_qcom_wlan_nv.bin`、蓝牙 nvm/rampatch、ath10k、`tas5728m_dsp` | `firmware-qcom-msm8953/APKBUILD` |

**所以"固件如何适配"这个问题的答案是：这条链路不需要适配固件。**

Modem/ADSP 固件走 `msm-firmware-loader` + `tqftpserv` 从 modem 分区取，与电量链路无关。

## 3. 温度链路全链路

```
用户态
 cat /sys/class/thermal/thermal_zone*/temp          ← 主路径（唯一当前可用）
 cat /sys/bus/iio/devices/iio:device*/in_temp*_input ← 裸 ADC（电池 NTC / PMIC 结温）
 (无) /sys/class/hwmon/*                             ← CONFIG_HWMON 未开
   │
thermal core（thermal_of.c）
 devm_thermal_of_zone_register()（旧 thermal_zone_of_sensor_register 在 6.19 已删除）
   │
 thermal-sensors = <&phandle id>
   ├── &tsens0 <0..15>  → drivers/thermal/qcom/tsens.c + tsens-v2.c
   │       MMIO 0x4a9000(TM) / 0x4a8000(SROT) → SoC 内 16 个测温点
   │
   └── &pm8953_temp     → drivers/thermal/qcom/qcom-spmi-temp-alarm.c
           io-channels = <&pm8953_vadc VADC_DIE_TEMP> 走 IIO 拿真实温度
             └─ drivers/iio/adc/qcom-spmi-vadc.c + qcom-vadc-common.c
                  └─ SPMI → PM8953 adc@3100 / PMI8950 adc@3100
   │
 超 trip → governor（step_wise / bang_bang）
   ▼
cooling：cpu0..cpu7（cpufreq）/ gpu（devfreq）降频；critical → 关机
```

**三个温度源**：

| 源 | 驱动 / compatible | 内核里的位置 | 用户态可见 |
|---|---|---|---|
| SoC TSENS（CPU×8 + GPU） | `qcom,msm8953-tsens`, `qcom,tsens-v2` | `msm8953.dtsi:918`，MMIO `4a9000`/`4a8000` | thermal_zone0..8 |
| PM8953 过温告警 | `qcom,spmi-temp-alarm` | `pm8953.dtsi:69` `temp-alarm@2400`，带 `io-channels` | thermal_zone10 `pm8953-thermal` |
| PM8953 结温 / 电池 NTC | `qcom,spmi-vadc`（IIO，非 thermal zone） | `pm8953.dtsi:78` `adc@3100` 通道 8；`pmi8950.dtsi:54` 通道 `d`(VADC_SPARE2) `label="chg_temp"` | `iio:device2 in_temp8_input`、`iio:device3 in_temp13_input` |

TSENS zone 映射（`msm8953.dtsi:3211-3423`）：cpu0..3 → sensor 9,10,11,12；cpu4..7 → 4,5,6,7；
gpu → 15。CPU/GPU 均 80°C passive / 100°C critical（GPU 70/90）。PM8953 zone 三层 105000/125000/145000。

**TSENS 校准这一环不会断（关键）**：msm8953 属 TSENS **v2**，`tsens.c:1158` 的 of_match 表里
**没有** `qcom,msm8953-tsens` 条目，回落到 `qcom,tsens-v2` → `data_tsens_v2` → `ops_generic_v2`，
而 **`ops_generic_v2` 没有 `.calibrate` 成员**，`tsens.c:1355` 只在 `ops->calibrate` 存在时才调用。
所以 msm8953 **从不读 nvmem**：没有校准 cell 也能正常注册，slope 用默认值 3200、offset 0。
⇒ **不要给 tsens0 补 nvmem-cells**，补了反而会走 `tsens_v2_calibration` 那条会失败的分支。
代价：绝对温度可能有若干 °C 偏差，相对变化可信。

**两个死模块**（本地 `modules.order` 里有，但 odin 上无 compatible、无节点）：
`lmh.ko`（只支持 sc8180x/sdm845/sm8150）、`qcom-spmi-adc5.ko`（只用于 pm6150/pm8150 等新 PMIC，msm8953 走 VADC 不是 ADC5）。

## 4. pmOS 的适配清单（小米 markw）

设备包 `device/archived/device-xiaomi-markw/APKBUILD` 依赖全文：
`firmware-qcom-adreno-a530 / firmware-xiaomi-markw / linux-postmarketos-qcom-msm8953 / lk2nd-msm8953 /
mkbootimg / msm-firmware-loader / postmarketos-base / soc-qcom-msm8953 / soc-qcom-msm8953-modem`

- **依赖树里没有任何 battery / upower / 充电相关包**。`modules-initfs` 只列触摸屏与 panel 模块，也没有电池模块。
- **无额外 udev 规则 / 服务 / 配置文件**：设备包只装 goodix 触摸校准 rules 与 wakeup hwdb；SoC 包只装
  wireplumber conf、adreno quirks、q6voiced.conf、modem openrc。
- **upower 是传进来的**，不是设备包装的：Plasma Mobile 经 `powerdevil → upower`，phosh 经 `phosh → upower-dev`。
- 设备树只需三处：
  ```dts
  battery: battery { compatible = "simple-battery"; };            /* 顶层，msm8953-xiaomi-common.dtsi:14 */
  &pmi8950_fg { monitored-battery = <&battery>; power-supplies = <&pmi8950_smbcharger>; status = "okay"; };
  &pmi8950_smbcharger { monitored-battery = <&battery>; status = "okay"; };
  ```
  节点本体在**被下游改过的** `pmi8950.dtsi`（主线版本只有 vadc/mpp/gpio/labibb/pwm/wled，没有 fg 与 smbcharger）。
- 内核配置：`CONFIG_BATTERY_PMI8994_FG=y`、`CONFIG_CHARGER_QCOM_SMBCHG=y`、`CONFIG_QCOM_PMIC_SEC_WRITE=y`、
  `CONFIG_QCOM_SPMI_VADC=m`、`CONFIG_QCOM_SPMI_ADC5=m`；关掉 `BATTERY_PM8916_BMS_VM` / `CHARGER_PM8916_LBC` / `CHARGER_QCOM_SMBB`。

## 7. 待确认 / 风险

1. **ODIN 电池的实际参数未知** —— `charge-full-design-microamp-hours`、
   `constant-charge-current-max-microamp`、`voltage-max-design-microvolt` 三项需要真值。
   markw 是 4000 mAh / 1 A / 4.38 V，不能直接套。FG 的 SOC 不依赖它（硬件直出），
   但这三项影响**充电电流**与 UPower 的剩余时间估算，抄错可能导致充电过流。
   ⇒ 建议先从 `qcom-battery` 的 `voltage_now` 实测确定电池类型，再定电压上下限。
2. **FG SRAM profile 的来源未确认** —— 主线驱动不写 OCV/容量，那硬件里的标定数据是谁写的？
   推测由 OEM bootloader 或 Android 内核首次写入、由 always-on 域维持。
   **风险**：彻底断电或换电池后 SOC 可能失准。需真机实测（充满→放空看 SOC 是否线性）。
3. **`thermal_zone9 type=qcom-battery`（27.5°C）出处未确认** —— 在 6.19.5 树里查无出处
   （`drivers/` 全树只有 `pmi8994_fg.c:703` 的 psy 名命中；dts 里无此温区）。
   本地树是 `--depth=1` 浅克隆，无法做 git 考古。怀疑是 pmOS 6.17 那版的额外驱动或 dts 残留。
   **不影响行动**：FG 已经通过 power_supply 的 `TEMP` 属性把电池温度送出来了。
4. **`dist/stage` 是跨构建复用的**（见 WORKLOG 那条坑），其产物状态不能作为"现在编成什么样"的证据，
   一切以 **CI 构建**为准。

## 8. 行动清单（按依赖排序）

1. 内核配置开 `CONFIG_BATTERY_PMI8994_FG=y`（依赖 `MFD_SPMI_PMIC` + `SPMI` + `OF` + `EXTCON` + `REGULATOR`）。
2. `patches/0007` 的 odin.dts 补三个节点：`battery`（simple-battery）、
   `&pmi8950_fg`（`monitored-battery` + `power-supplies`）、`&pmi8950_smbcharger`（`status = "okay"`）。
   电池参数先按保守值填，实测后校正（见 §7-1）。
3. rootfs 装 `upower` + `policykit-1`。
4. 真机验证：`cat /sys/class/power_supply/qcom-battery/{capacity,voltage_now,current_now,temp}`、
   `upower -d`，与 §5 的 pmOS 实测值对照。
5. 可选：开 `CONFIG_HWMON=y`（`CONFIG_THERMAL_HWMON` 会随之生效）让桌面温度小程序有数据；
   或直接从 `thermal_zone*` / IIO 读。
6. 可选清理：`qcom-spmi-adc5.ko`、`lmh.ko` 在 odin 上是死模块。
