## 叁、实施过程中推翻/修正的结论

### 3.1 【高危】lk2nd 的 DTB 选择可能落空 —— 已修

**发现**：从 `dist/lk2nd.img` 解出全部 31 条 QCDT 条目后比对：

| 条目 | msm-id | board-id |
|---|---|---|
| `msm8953-smartisan-odin` | `0x125 0x00` | **`<0x0b 0x01>`** |
| `msm8953-xiaomi-markw` | `0x125 0x00` | **`<0x1000b 0x01>`** |

`dev_tree.h:56-58` 定义 `VARIANT_MASK=0x000000ff`、`VARIANT_MINOR_MASK=0x0000ff00`、
`VARIANT_MAJOR_MASK=0x00ff0000` ⇒ **两者 variant_id 都是 `0x0b`**，高位 `0x10` 只是 major。
按 `dev_tree.c:448-500` 的匹配规则（变体相等即为候选，major 只影响打分），
lk2nd **可能把票投给 markw**。

**原设计的后果**：`l0` 用 `fdtdir /boot/dtbs`，若选中 markw，lk2nd 会用它的
`lk2nd,dtb-files`（= `msm8953-xiaomi-markw`）去找 `/boot/dtbs/qcom/msm8953-xiaomi-markw.dtb`
—— 而镜像里只有 odin 的两个 DTB ⇒ **加载 DTB 失败，启动失败**。

**修正**：`l0` 与 `l0-safe` **全部改为显式 `fdt`**，不再使用 `fdtdir`
（`lk2nd/boot/extlinux.c:394-434`：`fdt` 与 `fdtdir` 互斥，有 `fdtdir` 时会覆盖 `fdt`）。
现在无论 lk2nd 选中谁都能起：选中 odin → 有屏 + 全功能；选中 markw → 无屏但 SSH 可用。

**同时纠正一处我自己的误判**：真机 DT 里的 `qcom,board-id = <0x1000b 0x01>`
**不是硬件 ID**。全树 grep 确认 lk2nd **没有任何写 `qcom,board-id` 的代码**
（只有 `dev_tree.c` 里的读取与校验），那个值只是 markw 内核 DTB 自己的声明。
原厂 `evidence/stock_dtb_1.dtb` 明确写着 `qcom,board-id = <0x0b 0x01>`
（model = `Qualcomm Technologies, Inc. MSM8953 ODIN`）⇒ **项目 DTS 的值是正确的**，
不需要改 board-id。

**残余风险**：面板占位 compatible `smartisan,odin-panel` 只有在 lk2nd **选中 odin 条目**
时才会被替换成真实面板 —— 这是屏幕能否点亮的唯一开关，只能真机判定。
若首刷后无屏而 SSH 正常，下一步是**精简 lk2nd（只保留 odin 条目）**强制命中。

### 3.2 systemd 252 不读 `SYSTEMD_MOUNT_OPTIONS` —— 实测证伪

`reports/015 §3.2` 的方案是"udev 里 `IMPORT{program}` 注入 `SYSTEMD_MOUNT_OPTIONS`，
由 systemd-mount 从环境读取"。实测（QEMU 内手工复现）：

| 传参方式 | 结果 |
|---|---|
| `env SYSTEMD_MOUNT_OPTIONS=... systemd-mount ...` | ❌ 挂出来是**默认选项**，环境变量被忽略 |
| `systemd-mount --options=... ...` | ✅ 完全生效 |

且 `udevadm info -q property` 里根本没有 `SYSTEMD_MOUNT_OPTIONS` 属性，
`strings /usr/lib/systemd/systemd` 也搜不到任何 `SYSTEMD_MOUNT_*`（只有
`/usr/bin/systemd-mount` 里有，且只读 `WHERE`/`OPTIONS` 两个）。

⇒ **结论**：`TAG+="systemd"` 本身不会挂载任何东西，必须显式调 `systemd-mount`；
且选项必须用 `--options=` 传。改为包装脚本 `odin-automount.sh` 统一处理。

**同时放弃 `--owner=`**：systemd-mount 的 `--owner` 会对挂载点做 chown，
vfat/exfat 不支持 chown 会失败 → 改为在挂载选项里给 `uid=/gid=`。

### 3.3 superfloppy（无分区表）U 盘会被原规则排除

实测 4 个 superfloppy 测试盘的 udev 属性里**没有** `ID_PART_ENTRY_NUMBER`。
原规则要求该属性非空 ⇒ 这类盘全部不挂载。已放宽为只要求
`ID_BUS=usb` + `ID_FS_USAGE=filesystem`，有分区表的盘同样适用（整盘自身
`ID_FS_USAGE` 不是 filesystem，不会重复挂；各分区各自挂载）。

### 3.4 exFAT 不依赖 `nls_utf8` —— 用户决策成立（源码级坐实）

`CONFIG_EXFAT_DEFAULT_IOCHARSET="utf8"`，而：

```c
/* fs/exfat/super.c:38-41 */
opts->iocharset = iocharset;
if (!strcmp(opts->iocharset, "utf8")) opts->utf8 = 1;   /* 走内建快路径 */

/* fs/exfat/super.c:691-697 */
if (sbi->options.utf8)
        set_default_d_op(sb, &exfat_utf8_dentry_ops);    /* 不 load_nls */
else
        sbi->nls_io = load_nls(sbi->options.iocharset);
```

⇒ iocharset=utf8 时**根本不调用 `load_nls()`**，用内核内建 `utf16s_to_utf8s()`。
**exFAT 中文文件名开箱正常，"放弃 FAT32、靠 exFAT" 的决策成立。**

顺带修正：`CONFIG_EXFAT_FS=m`（**是模块不是内建**，与 015 §4.5 的表述不同）。
镜像内 `kernel/fs/exfat/exfat.ko` 确实存在（594 KB，`modules.dep` 无依赖），
挂载时由内核 `request_module("fs-exfat")` 自动加载，无需额外处理。
`CONFIG_NTFS3_FS=y` 内建；`CONFIG_NLS_UTF8` 确认未编译。

### 3.5 镜像内核跑不了 QEMU

`.config` 只有 `VIRTIO_BLK/NET/CONSOLE=y`，`VIRTIO_PCI`、`VIRTIO_MMIO` **均未设置**
⇒ virt 机器上没有块设备与网卡。印证 015 #12：**QEMU 只能验用户态**，
内核/硬件相关项必须真机。

## 肆、验证结果

### 4.1 QEMU 回归（`odin-qemu/test-automount.sh`）

4 个 USB  superfloppy 测试盘（vfat / exfat / ntfs / ext4）全部被识别，
`ID_BUS=usb` + `ID_FS_USAGE=filesystem` 正确。

| 项 | 结果 |
|---|---|
| vfat 自动挂载 | ✅ `/run/media/sda`，选项 `noatime,uid=1000,gid=1000,fmask=0133,dmask=0022` |
| NTFS 自动挂载 | ✅ `/run/media/sdc`（ntfs-3g → fuseblk），选项 `noatime` + `default_permissions,allow_other` |
| ext4 自动挂载 | ✅ `/run/media/sdd`，选项 `noatime` |
| exFAT | ⚠️ QEMU 内核无 exfat 支持，无法验证（静态已确认：模块在、不依赖 nls_utf8） |
| **user 可写性** | ✅ sda、sdc 用 user 直接写成功，文件属主 `1000:1000` |
| `systemctl --failed` | ✅ 0 个 |
| 两个 DTB + 双 label 配置 | ✅ 正确落到镜像内 |
| 角色脚本（无 typec/无 UDC 环境） | ✅ 立即返回，不空等 |
